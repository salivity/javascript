unhandledRejection vs uncaughtException in Node.js

Node.js provides the unhandledRejection and uncaughtException process events to capture unhandled errors and prevent unexpected application failures. While both events monitor unhandled failures within an application, they target fundamentally different types of errors: uncaughtException handles traditional synchronous exceptions that bubble up through the call stack without being caught, whereas unhandledRejection captures asynchronous Promise rejections that lack a corresponding rejection handler. Understanding the operational differences between these two events is essential for writing resilient Node.js applications and implementing robust error-handling workflows.

Understanding uncaughtException

The uncaughtException event is emitted when an unhandled JavaScript exception bubbles all the way back to the event loop. If an error is thrown within a synchronous block of code—or directly inside an asynchronous callback without an enclosing try...catch statement—Node.js emits this event.

process.on('uncaughtException', (error) => {
  console.error('An uncaught exception occurred:', error);
  process.exit(1);
});

// Triggers uncaughtException
function runCode() {
  throw new Error('Synchronous error occurred');
}
runCode();

When uncaughtException fires, the application enters an inherently undefined state. Because the stack has unwound unpredictably, memory leaks may occur, network sockets may remain open, and references may be corrupted. As a result, using uncaughtException as a catch-all to keep the process running is strongly discouraged. The recommended practice is to log the error, release allocated resources, and terminate the process using process.exit(1).

Understanding unhandledRejection

The unhandledRejection event is emitted whenever a Promise is rejected and no error handler, such as .catch() or an asynchronous try...catch wrapper, is attached to it within the same turn of the event loop.

process.on('unhandledRejection', (reason, promise) => {
  console.error('Unhandled Rejection at:', promise, 'reason:', reason);
});

// Triggers unhandledRejection
function asyncOperation() {
  return Promise.reject(new Error('Promise failed'));
}
asyncOperation();

Unlike classic exceptions, a rejected promise represents an asynchronous operation that failed. Modern versions of Node.js terminate the process with a non-zero exit code by default if an unhandled rejection occurs, aligning their behavior closer to uncaught exceptions. However, listening for unhandledRejection allows you to track and trace which asynchronous operations are failing silently or missing appropriate rejection logic.

Key Differences

Feature uncaughtException unhandledRejection
Origin Thrown exceptions in synchronous code or untracked callback stacks. Rejected Promises missing a rejection handler.
Trigger Mechanism throw new Error() outside of try...catch. Promise.reject() or throwing an error inside an async function.
Event Arguments Receives the Error object and an origin string. Receives the rejection reason and the rejected promise.
State Integrity Application state is heavily compromised and unpredictable. Application state may still be intact depending on the async context.
Recommended Action Log, perform cleanup, and exit the process immediately. Log the error, locate missing .catch() blocks, and terminate if the state is unknown.

Best Practices

To handle both events effectively in a production environment:

  1. Avoid Ignoring Failures: Never register these listeners simply to swallow errors and keep the server running. Continuing to run after an unhandled exception can lead to corrupted data or infinite hanging requests.
  2. Implement Graceful Shutdowns: Use these events to trigger a graceful shutdown sequence. Stop accepting new traffic, close database pools and active HTTP connections, and exit the process so process managers like PM2, Docker, or Kubernetes can restart a clean instance.
  3. Use Async/Await Properly: Always wrap await calls in try...catch blocks or chain .catch() onto returning Promises to prevent operations from escalating to an unhandledRejection event.
