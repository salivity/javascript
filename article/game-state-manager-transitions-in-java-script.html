Game State Manager Transitions in JavaScript

A game state manager (GSM) controls the flow of a video game by treating screens—such as the main menu, active gameplay, and pause overlays—as modular states. By decoupling screen logic from the core game loop, a GSM ensures that input processing, asset updates, and canvas rendering dynamically adapt to the active context. This article breaks down how a JavaScript game state manager orchestrates seamless transitions between the main menu, gameplay, and pause screens using finite state machines and stack-based architectures.

The Role of a Game State Interface

To allow smooth transitions, every screen must adhere to a standardized interface. In JavaScript, this is typically implemented using ES6 classes where each state defines lifecycle hooks:

  • enter(): Allocates memory, initializes entities, binds specific event listeners, or starts audio.
  • exit(): Cleans up listeners, pauses audio, or frees resources.
  • update(deltaTime): Executes game logic, physics, and input processing specific to that screen.
  • render(context): Draws visual elements to the HTML5 <canvas>.

By establishing this contract, the main game loop only needs to call update() and render() on whichever state is currently active, without needing to know the implementation details of that state.

Finite State Machine vs. State Stack

Game state transitions generally use one of two architectures: a standard Finite State Machine (FSM) or a State Stack (Pushdown Automaton).

1. Direct Switching (Finite State Machine)

Direct switching replaces the active state entirely. This approach is ideal for transitions like moving from the Main Menu to Gameplay:

class StateManager {
  constructor() {
    this.currentState = null;
  }

  changeState(newState) {
    if (this.currentState && this.currentState.exit) {
      this.currentState.exit();
    }
    this.currentState = newState;
    if (this.currentState && this.currentState.enter) {
      this.currentState.enter();
    }
  }
}

When switching from the menu to the game, changeState(new GameplayState()) invokes MenuState.exit() to destroy menu DOM overlays or clean up button listeners, followed by GameplayState.enter() to generate the world, spawn the player, and start the physics engine.

2. The Stack Approach (Pushdown Automaton)

A stack-based approach preserves previous states in memory by pushing new states onto an array and popping them off when finished. This is the standard method for handling a Pause Screen:

class StackStateManager {
  constructor() {
    this.states = [];
  }

  pushState(state) {
    this.states.push(state);
    state.enter();
  }

  popState() {
    const state = this.states.pop();
    if (state) state.exit();
  }

  getCurrentState() {
    return this.states[this.states.length - 1];
  }
}

When a player pauses:

  1. The game pushes PauseState onto the stack above GameplayState.
  2. The GameplayState is not exited or destroyed; its entities remain frozen in their current positions.
  3. When the player unpauses, the manager calls popState(), discarding the PauseState and immediately resuming GameplayState without re-instantiating the level.

Layered Rendering and Updating for Pause Screens

A primary benefit of the stack pattern is handling background visibility. While you want game updates (such as physics and AI routines) to halt during a pause, you often want the frozen gameplay world to remain visible beneath a semi-transparent pause menu.

The state manager handles this by splitting the loop delegation:

update(deltaTime) {
  // Only update the topmost active state
  const activeState = this.getCurrentState();
  if (activeState) {
    activeState.update(deltaTime);
  }
}

render(context) {
  // Render all active states from bottom to top if transparency is enabled
  for (const state of this.states) {
    state.render(context);
  }
}

During a pause, GameplayState.render(context) draws the frozen game scene, and immediately afterward, PauseState.render(context) draws a dark translucent overlay and UI options on top.

Transition Routing and Cleanup

Handling transitions between states requires centralized control to prevent memory leaks and dangling events:

  • Input Context Switching: Menu states often listen for clicks or UI keyboard navigation, while gameplay states listen for continuous physics-based inputs (keydown/keyup). The GSM must ensure input handlers are either reassigned during transitions or delegated purely through the active state's lifecycle methods.
  • Data Persistence: When transitioning from a "Game Over" state back to the "Main Menu", the state manager should fully clear the stack and instantiate a fresh MenuState, ensuring accumulated gameplay data is garbage-collected.
  • Visual Fades and Delays: Smooth transitions, such as screen fades, are managed by inserting an intermediary transition state or using asynchronous promises inside changeState(). The manager triggers a visual fade-out, waits for completion, swaps the states, and executes a fade-in before relinquishing input control to the player.
