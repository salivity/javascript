Fixed-Step Game Loop Accumulators in JavaScript

A cumulative time accumulator in a fixed-step game loop decouples game logic updates from the display rendering rate, ensuring that physics and gameplay mechanics behave deterministically across different hardware and monitor refresh rates. This article explains how variable frame rates cause physics instabilities in JavaScript, how the accumulator pattern solves this problem by slicing elapsed time into fixed intervals, and how to implement the pattern efficiently alongside requestAnimationFrame.

The Problem with Variable Timesteps

Browser-based games typically use requestAnimationFrame to drive their main loop. This API invokes a callback function just before the browser performs a repaint, running at the display's refresh rate (commonly 60Hz, 120Hz, or 144Hz).

Relying directly on the variable delta time (\(\Delta t\)) between repaints for physics calculations causes significant problems. If a browser tab stutters or drops frames, \(\Delta t\) spikes. A large \(\Delta t\) can cause moving entities to pass entirely through colliders—a phenomenon known as tunneling—or cause numerical drift in numerical integrators like Verlet or Euler. Conversely, running physics faster on high-refresh-rate displays can alter the speed or behavior of the game if not properly normalized.

The Accumulator Pattern Explained

A fixed-step game loop resolves these issues by updating game logic in consistent, discrete increments (such as 16.67 milliseconds for a target of 60 physics updates per second), regardless of how frequently the browser renders.

The cumulative time accumulator acts as a reservoir for elapsed real-world time:

  1. Measure Real Time: Calculate the delta time elapsed since the previous render frame.
  2. Accumulate Time: Add that elapsed time into a running total variable (the accumulator).
  3. Consume Time in Slices: While the accumulator contains at least one fixed time-step worth of time, execute a game logic update and subtract the fixed step from the accumulator.
  4. Render: Once the accumulator holds less time than a single fixed step, draw the current state of the game.

JavaScript Implementation

Below is a minimal, robust implementation of an accumulator-based loop:

let lastTime = performance.now();
let accumulator = 0;

// Target 60 updates per second (in milliseconds)
const TIMESTEP = 1000 / 60; 

function gameLoop(currentTime) {
    // 1. Calculate time passed since the last render frame
    let frameTime = currentTime - lastTime;
    lastTime = currentTime;

    // 2. Prevent the "Spiral of Death" by clamping maximum frame time
    if (frameTime > 250) {
        frameTime = 250;
    }

    // 3. Accumulate elapsed real time
    accumulator += frameTime;

    // 4. Consume the accumulator in fixed steps
    while (accumulator >= TIMESTEP) {
        update(TIMESTEP);
        accumulator -= TIMESTEP;
    }

    // 5. Render the state
    render();

    requestAnimationFrame(gameLoop);
}

function update(dt) {
    // Update game physics and logic by a fixed dt
}

function render() {
    // Draw entities to screen
}

requestAnimationFrame(gameLoop);

Avoiding the "Spiral of Death"

If the simulation takes longer to process an update than the allocated TIMESTEP, the accumulator continues to grow larger on subsequent frames. The engine is then forced to simulate even more fixed steps to catch up, consuming more CPU time, leading to a freeze known as the "spiral of death."

Clamping frameTime (as shown above with if (frameTime > 250) frameTime = 250;) limits the maximum number of simulation steps processed in a single cycle. If a large lag spike occurs or the user minimizes the tab, the game simulation falls behind slightly rather than freezing the browser indefinitely.

Eliminating Jitter with State Interpolation

Because the accumulator consumes time in discrete steps, a remainder always stays behind (accumulator < TIMESTEP). Rendering the most recent physics state directly can create a subtle visual stutter, because the render time rarely aligns perfectly with the physics time.

To achieve fluid visuals, calculate a blending factor \(\alpha\) (alpha) from the remaining time:

\[\alpha = \frac{\text{accumulator}}{\text{TIMESTEP}}\]

The value of \(\alpha\) ranges from 0.0 to 1.0. Pass this value to the render function to linearly interpolate visual positions between an entity's previous physics state and its current physics state:

\[\text{renderPosition} = \text{previousPosition} \times (1 - \alpha) + \text{currentPosition} \times \alpha\]

This combination of a fixed-step logic update, an accumulator, and rendering interpolation guarantees stable, deterministic physics calculations while presenting smooth motion at any monitor refresh rate.
