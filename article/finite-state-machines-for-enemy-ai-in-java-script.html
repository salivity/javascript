Finite State Machines for Enemy AI in JavaScript

A Finite State Machine (FSM) is an architectural design pattern that structures an entity's behavior into a defined set of states, allowing only one active state at any given time. In JavaScript game programming, an FSM manages enemy artificial intelligence (AI) by cleanly separating distinct behaviors—such as patrolling, chasing, and attacking—and governing the transitions between them based on game events. This approach replaces complex, bug-prone conditional chains with a scalable, modular system that makes non-player characters (NPCs) behave realistically and predictably.

Understanding the Core Components of an FSM

An FSM relies on three fundamental elements:

  1. States: The distinct modes of execution for an entity. For an enemy AI, common states include Idle, Patrol, Chase, and Attack.
  2. Transitions: The conditions or triggers that force an entity to move from one state to another (for example, moving from Patrol to Chase when the player enters detection range).
  3. Execution Context: The current active state that receives update ticks from the main game loop to alter enemy properties such as position, animations, and health.

Without an FSM, enemy behavior is often written using deeply nested if-else or switch statements inside the main game loop. As enemy logic expands, this approach leads to tightly coupled "spaghetti code" that is difficult to debug and extend. An FSM solves this by isolating state-specific logic into independent units.

The Structure of a JavaScript FSM

In modern JavaScript (ES6+), an FSM is typically implemented using an object-oriented approach composed of a base State interface, concrete state implementations, and a controller class (the enemy entity).

1. The State Interface

Each state defines methods for lifecycle hooks: enter(), update(), and exit().

class State {
  constructor(enemy) {
    this.enemy = enemy;
  }
  enter() {}
  update(deltaTime) {}
  exit() {}
}
  • enter(): Executes setup tasks, such as triggering an animation or resetting a timer when entering the state.
  • update(): Executes per-frame logic, such as calculating movement vector adjustments or checking transition thresholds.
  • exit(): Cleans up temporary variables or stops running animations before the enemy switches to a new state.

2. Concrete States

Concrete classes inherit from the base state and implement their own logic and transition rules.

class PatrolState extends State {
  enter() {
    this.enemy.speed = 2;
  }

  update(deltaTime) {
    this.enemy.moveAlongPath(deltaTime);

    // Transition Condition
    if (this.enemy.getDistanceToPlayer() < this.enemy.detectionRadius) {
      this.enemy.changeState('CHASE');
    }
  }

  exit() {}
}

class ChaseState extends State {
  enter() {
    this.enemy.speed = 5;
  }

  update(deltaTime) {
    this.enemy.moveTowards(this.enemy.player.position, deltaTime);

    // Transition Conditions
    const distance = this.enemy.getDistanceToPlayer();
    if (distance <= this.enemy.attackRadius) {
      this.enemy.changeState('ATTACK');
    } else if (distance > this.enemy.detectionRadius * 1.5) {
      this.enemy.changeState('PATROL');
    }
  }

  exit() {}
}

3. The Enemy Controller

The enemy entity maintains references to available states and the currently active state. It delegates frame updates to the active state.

class Enemy {
  constructor(player) {
    this.player = player;
    this.position = { x: 0, y: 0 };
    this.speed = 2;
    this.detectionRadius = 150;
    this.attackRadius = 20;

    // Register states
    this.states = {
      PATROL: new PatrolState(this),
      CHASE: new ChaseState(this)
    };

    this.currentState = this.states.PATROL;
    this.currentState.enter();
  }

  changeState(stateKey) {
    if (!this.states[stateKey] || this.currentState === this.states[stateKey]) {
      return;
    }

    this.currentState.exit();
    this.currentState = this.states[stateKey];
    this.currentState.enter();
  }

  update(deltaTime) {
    this.currentState.update(deltaTime);
  }

  getDistanceToPlayer() {
    const dx = this.player.position.x - this.position.x;
    const dy = this.player.position.y - this.position.y;
    return Math.hypot(dx, dy);
  }

  moveAlongPath(deltaTime) {
    // Patrol movement logic
  }

  moveTowards(targetPosition, deltaTime) {
    // Chase movement logic
  }
}

Integrating the FSM into the JavaScript Game Loop

In a standard JavaScript game loop using requestAnimationFrame, the enemy's update() method is invoked on every frame, passing the elapsed time (deltaTime):

let lastTime = 0;
const enemy = new Enemy(playerInstance);

function gameLoop(timestamp) {
  const deltaTime = (timestamp - lastTime) / 1000;
  lastTime = timestamp;

  // Update enemy AI via FSM delegation
  enemy.update(deltaTime);

  // Render game objects
  render();

  requestAnimationFrame(gameLoop);
}

requestAnimationFrame(gameLoop);

On every tick, the active state evaluates environmental inputs (such as distances, line of sight, or health levels). When conditions meet a transition threshold, changeState() is triggered, closing out the current behavior cleanly and starting the next.

Advantages of Using FSMs for JavaScript Game AI

  • Modularity: New states (such as Flee or Stunned) can be added as standalone classes without modifying existing state logic.
  • Predictability: Because an enemy cannot be in two states simultaneously, conflicting actions (like playing a walk cycle while attacking) are prevented.
  • Maintainability: Bugs are isolated to specific state classes, making it straightforward to identify and fix issues with enemy logic.
