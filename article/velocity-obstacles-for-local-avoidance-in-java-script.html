Velocity Obstacles for Local Avoidance in JavaScript

This article provides a comprehensive guide to understanding and implementing local avoidance in multi-agent simulations using Velocity Obstacles (VO) within JavaScript game programming. It breaks down the fundamental distinction between global pathfinding and local navigation, explores the geometric mathematics behind Velocity Obstacles and Reciprocal Velocity Obstacles (RVO), and outlines how to translate these concepts into clean, high-performance JavaScript code for real-time browser games.

Understanding Local Avoidance vs. Global Navigation

In game development, multi-agent navigation is typically divided into two distinct layers:

  1. Global Pathfinding: Algorithms such as A* or Dijkstra calculate a static route around immovable terrain (e.g., walls, buildings) from a start point to a destination, producing a sequence of waypoints.
  2. Local Avoidance: A reactive, frame-by-frame steering mechanism that allows agents to bypass dynamic obstacles and other moving agents while still progressing toward their next global waypoint.

Without local avoidance, agents moving along intersecting global paths collide, overlap, or enter deadlocks. Velocity Obstacles solve this by operating in velocity space rather than coordinate space, predicting potential future collisions and altering the agent’s velocity vector proactively.

The Velocity Obstacle (VO) Concept

A Velocity Obstacle is the set of all relative velocities between two agents that will result in a collision at some future point in time, assuming both agents maintain their current course and speed.

Given two circular agents, Agent \(A\) and Agent \(B\), with positions \(p_A, p_B\), radii \(r_A, r_B\), and current velocities \(v_A, v_B\):

  • Minkowski Sum: Agent \(B\) is treated as an enlarged stationary disc centered at \(p_B\) with a combined radius of \(r_A + r_B\), while Agent \(A\) is reduced to a single point at \(p_A\).
  • Collision Cone: A cone is projected from \(p_A\) tangent to the enlarged boundary of Agent \(B\). Any relative velocity vector (\(v_A - v_B\)) falling inside this cone guarantees a collision.
  • Velocity Obstacle (\(VO_{A|B}\)): By translating this cone by Agent \(B\)'s current velocity (\(v_B\)), the absolute velocities that Agent \(A\) must avoid are defined.

If Agent \(A\) chooses a velocity vector \(v_A\) that lies outside \(VO_{A|B}\), no collision will occur within the defined time horizon.

The Reciprocal Velocity Obstacle (RVO) Improvement

When standard Velocity Obstacles are applied symmetrically to two active agents, both agents see the other as a passive obstacle. Both rapidly adjust their velocities to opposite sides, leading to unnatural oscillations ("jitter") because each agent's correction invalidates the other's prediction.

Reciprocal Velocity Obstacles (RVO) resolve this by assuming that both agents share equal responsibility for avoiding collision. Instead of Agent \(A\) taking 100% of the evasive action, Agent \(A\) adjusts its velocity by half of the required correction:

\[v_{new} = \frac{v_{pref} + v_{avoid}}{2}\]

This cooperative model yields smooth, human-like passing trajectories without requiring inter-agent network communication, making it ideal for decentralized simulations.

Implementing Velocity Obstacles in JavaScript

To implement a VO or RVO system in a JavaScript game loop, developers use a multi-step process involving vector math, cone calculation, and velocity selection.

1. Vector Math Foundation

A lightweight 2D vector class is essential for computing dot products, projections, and distances:

class Vector2 {
  constructor(x = 0, y = 0) {
    this.x = x;
    this.y = y;
  }
  add(v) { return new Vector2(this.x + v.x, this.y + v.y); }
  sub(v) { return new Vector2(this.x - v.x, this.y - v.y); }
  mult(n) { return new Vector2(this.x * n, this.y * n); }
  magSq() { return this.x * this.x + this.y * this.y; }
  mag() { return Math.sqrt(this.magSq()); }
  normalize() {
    const m = this.mag();
    return m > 0 ? this.mult(1 / m) : new Vector2();
  }
  dot(v) { return this.x * v.x + this.y * v.y; }
  dist(v) { return this.sub(v).mag(); }
}

2. Candidate Velocity Sampling

While complex solutions like Optimal Reciprocal Collision Avoidance (ORCA) use linear programming to find the optimal velocity, JavaScript game engines often use a performant sampling-based approach:

  1. Calculate Preferred Velocity (\(v_{pref}\)): Direct the agent toward its target at its maximum speed.
  2. Generate Candidates: Generate a set of candidate velocity vectors radially around \(v_{pref}\), varying in direction and magnitude.
  3. Filter and Score: For each candidate velocity:
    • Check if the velocity falls inside any nearby agent's Velocity Obstacle within a time window (\(\tau\)).
    • Assign a penalty based on how far the candidate deviates from \(v_{pref}\).
  4. Select Best Velocity: Choose the candidate with the lowest penalty that does not produce an imminent collision.
function selectVelocity(agent, neighbors, timeHorizon = 2.0) {
  const preferredVelocity = agent.target.sub(agent.position).normalize().mult(agent.maxSpeed);
  let bestVelocity = preferredVelocity;
  let minPenalty = Infinity;

  // Generate candidate velocities (concentric rings and angles)
  const candidateVelocities = [preferredVelocity];
  const numAngles = 16;
  const numSpeeds = 4;

  for (let s = 1; s <= numSpeeds; s++) {
    const speed = (agent.maxSpeed / numSpeeds) * s;
    for (let a = 0; a < numAngles; a++) {
      const angle = (Math.PI * 2 / numAngles) * a;
      candidateVelocities.push(new Vector2(Math.cos(angle) * speed, Math.sin(angle) * speed));
    }
  }

  for (const v of candidateVelocities) {
    let collides = false;

    for (const other of neighbors) {
      if (other === agent) continue;

      // Relative calculations for RVO
      const combinedRadius = agent.radius + other.radius;
      const relativePosition = other.position.sub(agent.position);
      const relativeVelocity = v.mult(2).sub(agent.velocity).sub(other.velocity);

      // Ray-sphere intersection check within timeHorizon
      const timeToClosestPoint = relativePosition.dot(relativeVelocity) / relativeVelocity.magSq();

      if (timeToClosestPoint > 0 && timeToClosestPoint < timeHorizon) {
        const closestPoint = relativeVelocity.mult(timeToClosestPoint);
        if (relativePosition.dist(closestPoint) < combinedRadius) {
          collides = true;
          break;
        }
      }
    }

    if (!collides) {
      const penalty = v.dist(preferredVelocity);
      if (penalty < minPenalty) {
        minPenalty = penalty;
        bestVelocity = v;
      }
    }
  }

  return bestVelocity;
}

3. Integrating with the Game Loop

In standard 2D canvas or WebGL game loops, update positions using the calculated velocities:

function gameLoop(deltaTime) {
  // 1. Spatial partitioning (e.g., Quadtree or Grid) to query neighbors efficiently
  for (const agent of agents) {
    const neighbors = spatialGrid.query(agent.position, agent.sensorRadius);
    agent.nextVelocity = selectVelocity(agent, neighbors);
  }

  // 2. Apply movement updates
  for (const agent of agents) {
    agent.velocity = agent.nextVelocity;
    agent.position = agent.position.add(agent.velocity.mult(deltaTime));
  }

  render();
  requestAnimationFrame(gameLoop);
}

Performance Considerations in JavaScript

  • Spatial Partitioning: Avoid checking all agent pairs (\(O(n^2)\) complexity). Use a spatial hash grid or quadtree to limit collision checks strictly to nearby agents within a local radius.
  • Garbage Collection Optimization: Avoid instantiating temporary vector objects inside tight sampling loops. Use pre-allocated vector pools or primitive arrays (\(x, y\) coordinates) to prevent memory allocation spikes and garbage collection frame drops.
  • Adaptive Time Horizon: Reduce the time horizon (\(\tau\)) in dense crowds to prevent agents from becoming overly cautious and freezing when surrounded.
