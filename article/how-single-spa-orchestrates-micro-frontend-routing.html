How single-spa Orchestrates Micro-Frontend Routing

This article explores how the single-spa framework coordinates routing across independent JavaScript micro-frontends. It details how the library intercepts browser history events, evaluates custom activity functions to determine which applications should be visible, and manages the asynchronous mounting and unmounting lifecycles without requiring a full page reload or forcing all applications to use the same underlying framework.

Hijacking Browser Navigation Events

At the core of single-spa's routing orchestration is its ability to listen to and manipulate browser navigation. In standard single-page applications (SPAs), individual framework routers (such as React Router or Angular Router) independently listen for history and hash changes. In a micro-frontend setup, multiple routers listening simultaneously can cause race conditions or conflict with one another.

To prevent this, single-spa monkey-patches the native browser history APIs—specifically window.history.pushState and window.history.replaceState—and attaches event listeners to window.addEventListener('popstate', ...) and window.addEventListener('hashchange', ...).

When a URL change occurs via user interaction or programmatic navigation:

  1. single-spa intercepts the navigation event before any individual micro-frontend can process it.
  2. It pauses the event propagation temporarily.
  3. It performs its own routing evaluations.
  4. Once the appropriate micro-frontends are transitioned, it reroutes the captured DOM events back down to the active applications so their internal routers can update their views.

Application Registration and Route Predicates

For single-spa to route correctly, each micro-frontend must be registered using the registerApplication API. When registering an application, developers provide three primary configurations:

  • Name: A unique identifier for the micro-frontend.
  • Loading Function: A function returning a dynamic import (promise) that fetches and loads the application bundle.
  • ActiveWhen (Route Matching Rule): An activity function or path pattern that returns a boolean indicating whether the application should be active at the current URL.

The activeWhen argument can be a simple string prefix (such as '/users'), an array of path patterns, or a custom JavaScript function that receives the window.location object as an argument:

single-spa.registerApplication({
  name: 'user-dashboard',
  app: () => import('./user-dashboard.js'),
  activeWhen: (location) => location.pathname.startsWith('/dashboard')
});

Because this rule relies on simple boolean logic against the URL, multiple micro-frontends can be active at the same time on the same route—such as a persistent global navbar application alongside a dynamic page application.

The Lifecycle Management Pipeline

Once single-spa detects a change in the URL, it evaluates the activeWhen function of every registered application to calculate two distinct lists:

  • Applications that need to be unmounted.
  • Applications that need to be mounted.

Routing state changes are processed sequentially to prevent layout thrashing and DOM conflicts:

  1. Unmounting Inactive Apps: single-spa calls the unmount lifecycle function of any application that is currently mounted but no longer satisfies its activeWhen criteria. The application tears down its DOM tree, cancels active network subscriptions, and cleans up event listeners.
  2. Loading New Apps: Applications that are transitioning to an active state for the first time have their loading functions executed to fetch the code bundles over the network.
  3. Bootstrapping Apps: The newly fetched applications run their bootstrap lifecycle once for initial setup.
  4. Mounting Active Apps: single-spa invokes the mount lifecycle of all newly active applications, attaching them to their designated DOM containers.

Coexisting with Internal Framework Routers

single-spa does not manage the internal component trees of individual micro-frontends. Instead, it operates as a top-level meta-router.

Once single-spa mounts an application to the DOM, that application's internal routing engine (like Vue Router or React Router) handles deep links, sub-paths, and nested views relative to its base path. Because single-spa re-dispatches the intercepted popstate events after the micro-frontend lifecycle transitions finish, internal routers continue to function natively without needing to be heavily rewritten.
