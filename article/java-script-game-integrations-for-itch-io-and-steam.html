JavaScript Game Integrations for itch.io and Steam

Deploying JavaScript games to digital storefronts requires distinct architectural approaches depending on whether the target platform supports in-browser play or requires native desktop binaries. This article explains how itch.io executes web builds directly within the browser ecosystem and how Steam handles JavaScript projects by packaging web runtimes with desktop-level native API wrappers.

itch.io: Native Web Hosting and Sandboxing

itch.io natively supports HTML5 and JavaScript games without requiring external wrappers. Developers compress their build directory—containing an index.html file alongside accompanying JavaScript, CSS, and asset files—into a .zip archive and upload it directly through the itch.io dashboard.

Once uploaded, itch.io serves the build using an embedded <iframe> on the game's product page or in a dedicated fullscreen view. Platform handling on itch.io involves specific technical considerations:

  • Sandboxing and Storage: The embedded <iframe> operates in a sandboxed browser context. Persistent data, such as save states and settings, must rely on web storage standards like localStorage or IndexedDB. Developers must account for storage limitations and ensure data persistence remains bound to the hosting domain.
  • Cross-Origin Policies: Modern JavaScript engines leveraging multi-threading or high-resolution timers via SharedArrayBuffer require strict Cross-Origin Opener Policy (COOP) and Cross-Origin Embedder Policy (COEP) headers. itch.io provides toggles in the project configuration to enforce these headers for WebAssembly- and WebGL-intensive builds.
  • Platform APIs: itch.io exposes a REST API for authentication and purchase verification, but it does not require a native bridge. JavaScript games can make standard fetch() or XMLHttpRequest calls to interact with backend services or itch.io’s server-side endpoints when credentials are provided.

Steam: Desktop Packaging and Steamworks Integration

Steam does not natively host or stream browser-based HTML5 games. To distribute a JavaScript game on Steam, developers must convert the web build into an executable desktop application using a runtime wrapper such as Electron, NW.js, or Tauri.

These frameworks package the JavaScript codebase with a dedicated instance of Chromium (or the OS's native webview) and Node.js, allowing the game to run as a native windowed or fullscreen desktop process.

Bridging JavaScript to the Steamworks SDK

Because Steam features (such as Achievements, Cloud Saves, Leaderboards, and the Steam Overlay) are built on the C++ Steamworks SDK, a purely browser-based JavaScript environment cannot access them directly. Packaging tools resolve this via native Node.js addons:

  1. Native Bindings: Tools such as steamworks.js or greenworks act as dynamic bridges between Node.js and the steam_api.dll (or macOS/Linux equivalents).
  2. Initialization: The JavaScript runtime initializes the Steam API during the game's boot sequence. If the Steam client is not running, the wrapper can trigger a restart through Steam or gracefully shut down.
  3. Feature Implementation: JavaScript games interact with Steam features asynchronously through JavaScript promises or callbacks. For example, unlocking an achievement involves calling a JavaScript function that executes the underlying C++ SteamUserStats()->SetAchievement() method.

Architectural Comparison

The fundamental difference lies in execution context. itch.io treats JavaScript builds as native web applications, handling hosting, asset delivery, and execution entirely through standard web browser protocols. Steam treats JavaScript builds as internal logic for an encapsulated desktop binary, requiring developers to bundle a web runtime and utilize C++ bindings to communicate with the Steam client ecosystem.
