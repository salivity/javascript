Entity Interpolation in JavaScript Game Development

Entity interpolation is a networking technique used in multiplayer games to create fluid, continuous visual movement of remote players despite receiving infrequent and irregular positional updates from a server. In multiplayer web games, physics ticks and network transmissions occur at discrete intervals, which often results in jittery, teleporting characters if drawn directly upon arrival. By artificially delaying the rendering of remote entities by a small window of time, the client can smoothly blend between past known states, ensuring continuous motion across screen refreshes.

The Problem: Network Latency and Packet Jitter

In multiplayer game architecture, the authoritative server dictates the game state. Rather than sending data at the monitor's refresh rate (typically 60Hz to 144Hz), game servers broadcast snapshots at a lower tick rate—often between 10Hz and 30Hz—to conserve network bandwidth.

When a client receives a new packet containing a remote player's position, simply snapping the character to the new coordinates makes the entity teleport across the screen. Furthermore, unpredictable network conditions (jitter) cause packets to arrive out of cadence. If a frame renders before the next network packet arrives, the remote entity pauses; when the delayed packet finally lands, the entity abruptly jumps forward.

What is Entity Interpolation?

Entity interpolation solves this issue by buffering incoming server updates and rendering the remote entity slightly in the past.

Instead of showing the remote player's current hypothetical position, the client introduces an artificial delay—typically equal to the server's update interval plus a small safety margin (often 50ms to 100ms). Because the client renders the past, it reliably has at least two recorded positions: one that occurred immediately before the chosen render time, and one that occurred immediately after. The client calculates the exact position between those two points using mathematical interpolation, typically linear interpolation (lerp).

How Interpolation Works Step-by-Step

To smooth movement, a JavaScript game client performs the following loop on each frame:

  1. Record Snapshots: Whenever the client receives a server state message, it stores the remote entity's position alongside the server timestamp in a local history buffer.
  2. Calculate Render Time: On each requestAnimationFrame loop, the game determines the target render time: renderTime = performance.now() - interpolationDelay.
  3. Locate Bounding States: The client scans the buffer to find two snapshots: \(S_0\) (the last state before renderTime) and \(S_1\) (the first state after renderTime).
  4. Determine the Alpha (\(t\)): The client calculates a normalized progress value between 0 and 1: \[\alpha = \frac{\text{renderTime} - S_0.\text{timestamp}}{S_1.\text{timestamp} - S_0.\text{timestamp}}\]
  5. Compute the Interpolated Position: Using the \(\alpha\) value, the client calculates the rendered coordinates: \[\text{position} = S_0.\text{position} + (S_1.\text{position} - S_0.\text{position}) \times \alpha\]

Implementing Interpolation in JavaScript

Below is a simplified implementation showing how a client stores incoming packets and calculates the rendered position inside the client's draw loop.

// Linear interpolation utility
function lerp(start, end, alpha) {
  return start + (end - start) * alpha;
}

class RemotePlayer {
  constructor() {
    this.serverUpdates = [];
    this.renderDelay = 100; // 100ms render buffer
    this.x = 0;
    this.y = 0;
  }

  // Called whenever a WebSocket/WebRTC message arrives
  onServerUpdate(x, y, timestamp) {
    this.serverUpdates.push({ x, y, timestamp });
    
    // Prune updates older than 1 second to avoid memory leaks
    const cutoff = timestamp - 1000;
    while (this.serverUpdates.length > 2 && this.serverUpdates[0].timestamp < cutoff) {
      this.serverUpdates.shift();
    }
  }

  // Called every requestAnimationFrame
  update(currentTime) {
    const renderTime = currentTime - this.renderDelay;

    // Find the two snapshots that surround renderTime
    let previous = null;
    let target = null;

    for (let i = 0; i < this.serverUpdates.length; i++) {
      if (this.serverUpdates[i].timestamp <= renderTime) {
        previous = this.serverUpdates[i];
      }
      if (this.serverUpdates[i].timestamp > renderTime) {
        target = this.serverUpdates[i];
        break;
      }
    }

    if (previous && target) {
      // Calculate normalized time between the two snapshots
      const totalSpan = target.timestamp - previous.timestamp;
      const progress = renderTime - previous.timestamp;
      const alpha = Math.max(0, Math.min(1, progress / totalSpan));

      // Calculate smoothed position
      this.x = lerp(previous.x, target.x, alpha);
      this.y = lerp(previous.y, target.y, alpha);
    } else if (previous) {
      // Fallback: If network lag exceeds buffer, use the latest known state
      this.x = previous.x;
      this.y = previous.y;
    }
  }
}

Handling Edge Cases and Trade-offs

While entity interpolation provides smooth visuals, developers must manage specific trade-offs:

  • Visual Latency: Because remote players are intentionally rendered in the past, their visual representation lags behind their real-time server position. In fast-paced competitive shooters, this delay requires the server to implement lag compensation (rewinding server state during hit verification) so players can aim at what they actually see.
  • Buffer Starvation: If network packets drop or arrival latency exceeds the renderDelay, the client runs out of future snapshots. In this scenario, the entity can either freeze at the latest known position or switch to extrapolation (dead reckoning), which predicts the entity's path based on its last known velocity until the next update arrives.
