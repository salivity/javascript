How to Smooth Grid Pathfinding in JavaScript

Standard grid-based pathfinding algorithms like A* yield functional routes, but the resulting paths are constrained to discrete steps across tiles, creating unnatural, jagged 45-degree or 90-degree corner turns. In JavaScript game programming, path smoothing resolves this by treating the grid-derived path as a rough draft rather than an absolute route. By applying post-processing techniques—primarily line-of-sight raycasting, node pruning, and spline interpolation—developers can eliminate unnecessary waypoints and round out sharp angles, transforming rigid grid traversal into fluid, realistic character movement.

The Cause of Jagged Paths

Grid algorithms evaluate movement from the center of one tile to an adjacent neighbor. When navigating diagonals or turning around obstacles, entities snap from one discrete coordinate to another. Even with 8-directional movement, an entity traveling across an open room will zigzag along diagonal and orthogonal axes rather than walking in a straight line toward the destination. This stepping behavior looks robotic and wastes movement cycles.

Line-of-Sight Pruning (Raycasting)

The most efficient method to remove jagged corners in 2D JavaScript games is line-of-sight pruning. Once the A* search returns an array of coordinate nodes, a post-processing pass checks whether the entity can travel directly between non-adjacent nodes without colliding with obstacles.

The algorithm works as follows:

  1. Set a reference point at the start node (index \(i = 0\)).
  2. Test a straight line from index \(i\) to index \(i + 2\) using a line-drawing algorithm (such as Bresenham’s algorithm or an orthogonal raycast).
  3. If the ray does not intersect any blocked grid cells, remove node \(i + 1\) from the path array.
  4. Continue extending the check to \(i + 3\), \(i + 4\), and so on, until an obstacle intersects the line.
  5. When a collision is detected, advance the reference index \(i\) to the last valid visible node and repeat the process until the destination is reached.

In JavaScript, this can be implemented cleanly:

function smoothPath(path, isWalkable) {
    if (path.length <= 2) return path;

    const smoothed = [path[0]];
    let current = 0;

    while (current < path.length - 1) {
        let furthestVisible = current + 1;

        for (let next = current + 2; next < path.length; next++) {
            if (hasLineOfSight(path[current], path[next], isWalkable)) {
                furthestVisible = next;
            } else {
                break;
            }
        }

        smoothed.push(path[furthestVisible]);
        current = furthestVisible;
    }

    return smoothed;
}

The hasLineOfSight function samples points between two coordinates at intervals equal to the tile size, verifying that isWalkable(x, y) returns true for each sample.

Corner Cutting and Clearance Checks

A common pitfall with pure line-of-sight smoothing is "corner cutting," where a smoothed vector clips the edge of a wall tile because it only checks a single-pixel line. To prevent an entity's bounding box from colliding with obstacle corners, clearance checks must be incorporated:

  • Padded Rays: Cast two parallel rays offset by the entity's half-width along the normal of the movement vector.
  • Tile Inflation: Temporarily treat tiles directly adjacent to obstacles as unwalkable during the line-of-sight phase, ensuring paths maintain a safe turning radius.

Curving Paths with Spline Interpolation

Node pruning reduces a 20-node zigzagging path into a 3-node direct path, but turns around remaining corners will still be sharp angles. To create natural, sweeping turns, the remaining waypoints can be interpolated using Catmull-Rom splines or Bézier curves.

Instead of moving linearly from node to node, the entity evaluates its position along a parametric curve:

function getSplinePoint(p0, p1, p2, p3, t) {
    const t2 = t * t;
    const t3 = t2 * t;

    const x = 0.5 * ((2 * p1.x) +
        (-p0.x + p2.x) * t +
        (2 * p0.x - 5 * p1.x + 4 * p2.x - p3.x) * t2 +
        (-p0.x + 3 * p1.x - 3 * p2.x + p3.x) * t3);

    const y = 0.5 * ((2 * p1.y) +
        (-p0.y + p2.y) * t +
        (2 * p0.y - 5 * p1.y + 4 * p2.y - p3.y) * t2 +
        (-p0.y + 3 * p1.y - 3 * p2.y + p3.y) * t3);

    return { x, y };
}

By passing four consecutive waypoints into the spline function and incrementing \(t\) from 0 to 1, the entity rounds off sharp turns dynamically without clipping the environment.

Performance Optimization for the JavaScript Event Loop

Path smoothing adds computational overhead to path generation. To maintain a steady 60 frames per second:

  • Execute Smoothing Only Once: Run the smoothing function once upon path creation, not on every animation frame.
  • Bresenham Grid Stepping: Avoid expensive floating-point trigonometric functions (Math.sin, Math.cos) during raycasting; use integer-based grid traversal algorithms like Amanatides-Woo or Bresenham.
  • Early Exits: Cap the maximum lookahead distance during line-of-sight checks so the loop does not test dozens of distant nodes unnecessarily.
