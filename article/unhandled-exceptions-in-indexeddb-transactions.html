Unhandled Exceptions in IndexedDB Transactions

When an unhandled JavaScript exception occurs inside an IndexedDB request callback (such as onsuccess or onerror), the browser immediately aborts the active transaction. All database modifications made during that transaction are rolled back, the transaction fires an abort event, and the exception continues to propagate to the global execution context.

Automatic Transaction Abort

Under the W3C IndexedDB specification, transactions remain active as long as requests are pending or their corresponding event listeners are running. If an exception is thrown inside an event listener and is not caught within that callback using a try...catch block, the browser treats the operation as a failure.

To maintain data integrity, the IndexedDB engine automatically initiates the transaction abort steps. The transaction immediately shifts to an inactive state, and no further requests can be placed on it.

Rollback of Database Changes

IndexedDB transactions adhere to standard ACID properties, specifically atomicity. When the unhandled exception forces an abort:

  • Any add(), put(), or delete() operations executed earlier in the same transaction are completely reverted.
  • Pending requests that have not yet executed are cancelled.
  • The underlying database remains in the state it occupied prior to the start of the transaction.

Event Dispatch and Error Reporting

Once an unhandled exception causes an abort, the following sequence of events occurs:

  1. Global Error Handling: The uncaught exception bubbles up to the global scope, triggering window.onerror or any window.addEventListener('error', ...) handlers.
  2. Transaction Abort Event: The transaction object dispatches an abort event to its onabort handler.
  3. Error Property: The transaction's error property is typically set to a DOMException named AbortError, indicating that the transaction was terminated prematurely.

Preventing Unintended Aborts

If an error inside a callback should not cancel the entire transaction, the code inside the listener must explicitly catch the error:

request.onsuccess = (event) => {
  try {
    // Risky application logic
    processData(event.target.result);
  } catch (err) {
    console.error("Recovered from error without aborting transaction:", err);
    // Transaction remains active for remaining operations
  }
};

Wrapping vulnerable operations in try...catch ensures that unexpected application errors do not unintentionally discard valid database writes executed within the same transaction.
