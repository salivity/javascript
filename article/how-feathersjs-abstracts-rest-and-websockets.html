How FeathersJS Abstracts REST and WebSockets

FeathersJS simplifies modern web and API development by providing a unified, transport-agnostic service interface that decouples application business logic from communication protocols. Instead of requiring developers to write distinct handlers for HTTP endpoints and real-time WebSocket connections, FeathersJS routes requests from REST APIs and WebSocket libraries through a standardized set of service methods and application hooks. This architecture allows developers to build functionality once and expose it across multiple protocols simultaneously without modifying underlying code.

The Uniform Service Interface

At the core of FeathersJS's protocol abstraction is the Service. A service is a simple JavaScript class or plain object that implements standard, predefined CRUD-like methods:

  • find(params): Retrieves a list of resources.
  • get(id, params): Retrieves a single resource by identifier.
  • create(data, params): Creates a new resource.
  • update(id, data, params): Replaces an existing resource.
  • patch(id, data, params): Merges updates into an existing resource.
  • remove(id, params): Deletes an existing resource.

Because service methods only accept standardized data arguments and return promises, they remain completely unaware of protocol-specific objects such as Node.js HTTP IncomingMessage, Express/Koa req and res, or WebSocket socket instances.

Protocol Adapters and Mapping

FeathersJS uses transport adapters (such as @feathersjs/koa, @feathersjs/express, and @feathersjs/socketio) to bridge the gap between network protocols and service methods.

REST Mapping

When configured with an HTTP transport, the framework maps standard HTTP verbs and URL paths to service methods:

  • GET /messages invokes messages.find()
  • GET /messages/123 invokes messages.get('123')
  • POST /messages invokes messages.create(body)
  • PUT /messages/123 invokes messages.update('123', body)
  • PATCH /messages/123 invokes messages.patch('123', body)
  • DELETE /messages/123 invokes messages.remove('123')

The REST transport handles extracting query parameters, parsing request bodies, setting headers, and sending serialized JSON responses back to the client.

WebSocket Mapping

When configured with WebSockets (such as Socket.io), FeathersJS listens for structured socket events instead of HTTP requests. By default, it uses a convention like <service-path>::<method>:

  • Emitting messages::find calls messages.find().
  • Emitting messages::create with payload data calls messages.create(data).

The response or error is sent back via the standard WebSocket acknowledgment callback. The service itself runs the exact same code path whether the trigger came from an HTTP request or a WebSocket message.

The Hook Context: Universal Request State

To handle cross-cutting concerns like authentication, validation, and logging across different transports, FeathersJS uses a pipeline called Hooks.

Every incoming request generates a unified HookContext object containing:

  • context.data: The payload submitted for creation or modification.
  • context.params: Additional parameters, including query filters (params.query) and authenticated user data (params.user).
  • context.id: The resource ID, if applicable.
  • context.result: The returned result from the service method.
  • context.provider: The transport used for the request (e.g., 'rest', 'socketio', or undefined for internal calls).

Transport adapters convert their protocol-specific metadata (such as HTTP headers or WebSocket handshake data) into context.params before the service method executes. This standardizes authentication checks and authorization logic, making security policies identical across protocols.

Unified Real-Time Event Dispatching

The transport abstraction also extends to outgoing events. Whenever a mutation method (create, update, patch, or remove) succeeds, the service automatically emits an internal event (e.g., created, updated, patched, removed).

FeathersJS channels (app.channel) manage which connected WebSocket clients receive these events. Even if a resource is created through a traditional REST POST request, the framework still fires the service event. The WebSocket transport adapter listens to that event and automatically pushes the newly created data in real time to all subscribed clients. This removes the need to write manual pub/sub code to bridge standard HTTP mutations with WebSocket notifications.
