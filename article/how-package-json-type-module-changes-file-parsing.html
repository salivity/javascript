How package.json Type Module Changes File Parsing

Adding "type": "module" to a package.json file fundamentally alters how Node.js parses and executes JavaScript files within that project's scope. By default, Node.js treats standard .js files as CommonJS modules; setting this property shifts the runtime environment to parse all .js files as modern ECMAScript Modules (ESM). This guide breaks down the core parsing changes this configuration introduces, including syntax rules, global scope alterations, and module resolution mechanics.

The Default CommonJS Environment

Without the "type": "module" setting, Node.js defaults to "type": "commonjs". In this standard mode:

  • Files ending in .js are parsed synchronously using CommonJS.
  • Modules are imported using require() and exported using module.exports or exports.
  • Built-in CommonJS wrapper variables such as __dirname, __filename, exports, and module are injected into the file scope.

Key Parsing Changes Under "type": "module"

When you explicitly define "type": "module" in the root package.json, Node.js updates its parsing pipeline for all .js files located in that directory and its subdirectories.

1. ESM Syntax Becomes Standard

The runtime parser expects native ECMAScript module syntax. You must use import and export statements instead of require() and module.exports. Attempting to call require() inside a .js file will throw a ReferenceError: require is not defined.

2. Automatic Strict Mode

In CommonJS, files run in "sloppy mode" unless you explicitly declare "use strict"; at the top of the file. Under ESM, the JavaScript engine parses every module in strict mode automatically. Behaviors like assigning values to undeclared variables or using duplicate parameter names will immediately throw syntax or runtime errors.

3. Removal of CommonJS Globals

The module wrapper functions used by CommonJS are not applied to ES modules. Consequently, several legacy variables become unavailable:

  • __dirname and __filename are no longer defined. To reconstruct path data, you must use import.meta.url along with Node's url and path utilities.
  • require.resolve() cannot be called directly; dynamic imports via import() or createRequire must be used instead.

4. Mandatory File Extensions for Relative Imports

When parsing module specifiers, the ESM loader enforces strict resolution algorithms. Unlike CommonJS, which automatically resolves paths without extensions or searches for index.js, ESM requires explicit file extensions in relative and absolute paths:

// Valid in ESM
import { helper } from './utils.js';

// Throws ERR_MODULE_NOT_FOUND in standard ESM parsing
import { helper } from './utils';

5. Asynchronous Module Loading

CommonJS loads modules synchronously on demand. ESM parses imports statically before executing the module body, loading dependencies asynchronously. This architectural shift enables top-level await, allowing you to use the await keyword outside of async functions directly in the module body.

Explicit Overrides: .cjs and .mjs

The "type": "module" field only dictates how .js files are parsed. Node.js provides explicit file extensions that bypass the package.json configuration:

  • .mjs: Always parsed as ECMAScript Modules, regardless of the package.json setting.
  • .cjs: Always parsed as CommonJS modules, allowing you to maintain legacy CommonJS files within an ESM-configured project.
