How Webpack SplitChunksPlugin Creates Vendor Bundles

This article explains how Webpack’s SplitChunksPlugin identifies shared dependencies and extracts them into dedicated vendor bundles. It covers the module graph analysis, the role of cache groups, evaluation heuristics like file sizes and chunk thresholds, and the actual extraction process that results in optimized, cacheable JavaScript assets for the browser.

The Role of SplitChunksPlugin

In a typical Webpack build without code splitting, third-party libraries (such as React, Lodash, or Axios) are duplicated across different entry points or embedded directly into application code. When application code updates, users must re-download the entire bundle—including the unchanged third-party libraries.

SplitChunksPlugin prevents code duplication and enables long-term browser caching by scanning module dependencies and isolating heavy, infrequently changing third-party code into separate "vendor" chunks.

1. Module Graph Traversal and Identification

During the compilation phase, Webpack builds a dependency graph of all imports. SplitChunksPlugin hooks into the optimization phase to evaluate every module in this graph:

  • It detects which modules originate from the node_modules directory.
  • It tracks how many chunks or entry points require each module.
  • It calculates the uncompressed and compressed size contributions of each candidate dependency.

2. Cache Group Matching

The primary engine behind chunk splitting is the cacheGroups configuration. Webpack evaluates every candidate module against a set of predefined and user-defined rules.

By default, Webpack ships with two built-in cache groups:

  • defaultVendors (formerly vendors): Matches any module imported from node_modules. If a module matches this pattern, it is queued for extraction into a vendor chunk (e.g., vendors-node_modules_...js).
  • default: Matches modules shared between two or more chunks, even if they are local application code rather than external dependencies.

Developers can define custom cache groups to fine-tune grouping, such as isolating specific large libraries (e.g., separating heavy charting libraries from standard UI libraries).

3. Threshold Evaluation

Before a chunk is generated, SplitChunksPlugin applies heuristic constraints to ensure that splitting code actually improves performance rather than creating unnecessary HTTP overhead:

  • minSize: The module or group of modules must meet a minimum byte size threshold (defaulting to 20 KiB in production) before it qualifies for its own chunk.
  • minChunks: The minimum number of entry points or chunks that must share a module before it is split out.
  • maxInitialRequests / maxAsyncRequests: Upper limits on the number of simultaneous HTTP requests allowed when loading an entry point or an on-demand bundle. If creating a new vendor chunk would exceed this limit, Webpack will suppress the split.
  • reuseExistingChunk: If a split chunk containing the exact same modules already exists, Webpack reuses it instead of creating a duplicate file.

4. Extraction and Bundle Generation

Once the plugin matches modules to a cache group and verifies all thresholds:

  1. Decoupling: The selected modules are detached from their original parent chunks.
  2. New Chunk Creation: A new Chunk object is initialized (such as vendors~main.js).
  3. Graph Rewiring: Webpack updates the runtime manifest. The original application chunks receive references indicating that they depend on the newly created vendor chunk.
  4. HTML/Manifest Emission: Plugins like HtmlWebpackPlugin read these dependencies and inject the appropriate <script> tags in the correct dependency order, ensuring vendor bundles execute before dependent application code.
