Efficient ECS Component Iteration in JavaScript

Efficiently iterating over filtered component pools is a core performance hurdle in JavaScript-based Entity Component System (ECS) game engines. Because JavaScript relies on automatic garbage collection and dynamic typing, naive iteration strategies like calling Array.prototype.filter every frame cause severe frame drops and memory churn. High-performance game loops achieve consistent 60+ FPS by bypassing dynamic object lookups using pre-computed query caches, bitmasks, sparse sets, archetype storage layouts, and contiguous typed arrays.

The Pitfalls of Naive Filtering

In a standard game loop, systems must process only the entities containing a specific set of components (for example, a MovementSystem needs entities with both Position and Velocity).

Iterating through all entities and checking if component properties exist creates two major bottlenecks:

  1. Garbage Collection Pressure: Using functional helpers like .filter() creates temporary array allocations every tick, triggering V8's garbage collector.
  2. Poor Cache Locality: Chasing pointers across scattered JavaScript objects leads to CPU cache misses and prevents JavaScript engines from optimizing hidden classes.

Bitmasks for Instant Component Evaluation

Instead of checking object properties with strings or hasOwnProperty, engines assign each component type a unique bit flag.

const POSITION = 1 << 0; // 0001
const VELOCITY = 1 << 1; // 0010
const RENDER   = 1 << 2; // 0100

const MOVEMENT_MASK = POSITION | VELOCITY; // 0011

Each entity stores a single integer or BigInt representing its active components. A system determines eligibility using a bitwise AND operation:

if ((entityMask & MOVEMENT_MASK) === MOVEMENT_MASK) {
  // Entity matches the system criteria
}

Bitwise checks execute in a single CPU cycle, dramatically reducing the overhead of testing entity qualifications.

Pre-Computed Reactive Query Lists

Evaluating masks across thousands of entities inside the update loop remains suboptimal if done every frame. Efficient engines move filtering logic out of the update loop entirely using reactive query caches.

  1. System Registration: Systems define required components once during initialization.
  2. Event-Driven Updates: When an entity adds or removes a component, the engine recalculates that entity's mask and notifies query listeners.
  3. Cached Dense Arrays: Systems maintain a flat array of matching entity IDs.

During the tick phase, the system iterates over an already filtered, dense array:

// Inside the system update loop: zero filtering needed
for (let i = 0, len = movementQuery.entities.length; i < len; i++) {
  const entityId = movementQuery.entities[i];
  // Process entity components
}

Archetype-Based Memory Layouts

Modern ECS engines (such as Flecs or BiteCS) utilize archetypes. An archetype represents a unique combination of components. All entities sharing the exact same component signature reside within the same storage block.

  • Entities with [Position, Velocity] are stored in Archetype A.
  • Entities with [Position, Velocity, Render] are stored in Archetype B.

Systems maintain pointers to the specific archetype tables matching their criteria. During the update step, the system iterates sequentially through these tables. This completely eliminates entity-level filtering, transforming the update loop into a continuous memory sweep.

Sparse Sets for Fast Lookups and Iteration

When entity compositions change frequently, archetype migration can introduce overhead. Sparse sets offer a balanced alternative:

  • Dense Array: Stores active entity IDs contiguously to guarantee cache-friendly, uninterrupted iteration.
  • Sparse Array: Maps entity IDs directly to their indices in the dense array for \(O(1)\) additions and removals.

Systems loop over the dense array directly, ensuring \(O(N)\) iteration performance with zero empty slots, while component lookups remain instant.

Struct of Arrays (SoA) via TypedArrays

JavaScript objects incur pointer overhead. Struct of Arrays (SoA) architectures replace object pools with flat TypedArrays (Float32Array, Int32Array). Component data is aligned sequentially by component property rather than grouped by entity:

// Contiguous memory blocks
const posX = new Float32Array(MAX_ENTITIES);
const posY = new Float32Array(MAX_ENTITIES);
const velX = new Float32Array(MAX_ENTITIES);
const velY = new Float32Array(MAX_ENTITIES);

function updateMovement(denseEntities) {
  for (let i = 0, len = denseEntities.length; i < len; i++) {
    const eid = denseEntities[i];
    posX[eid] += velX[eid];
    posY[eid] += velY[eid];
  }
}

This structure allows the JavaScript engine to leverage sequential CPU prefetching, avoid pointer dereferencing, and avoid hidden-class deoptimizations. Combined with pre-filtered dense query lists, it provides the fastest possible execution model for JavaScript game update loops.
