Understanding Recoil Dependency Graph in JavaScript

This article explores the dependency graph mechanism underlying Recoil, Facebook’s state management library for React. It details how atoms and selectors establish a Directed Acyclic Graph (DAG) to represent application state, how dynamic dependency tracking works during runtime, and how state updates propagate through downstream subscribers to achieve fine-grained reactivity.

The Directed Acyclic Graph (DAG) Architecture

Recoil represents its state tree as a Directed Acyclic Graph (DAG). In this graph structure, state is not kept in a monolithic centralized store, but rather decentralized across individual nodes. The graph consists of two primary types of nodes:

  • Atoms: The root (source) nodes of the graph. Atoms represent units of writeable, primary state. They have no upstream dependencies within Recoil.
  • Selectors: Pure functions that represent derived or computed state. Selectors serve as intermediate or terminal nodes in the graph, consuming data from atoms or other selectors and transforming it.

Because the graph is strictly acyclic, Recoil prevents circular references. If Selector A depends on Selector B, Selector B cannot depend on Selector A, preventing infinite computation loops.

Dynamic Dependency Discovery

Unlike state management systems that require explicit, static dependency declarations, Recoil builds and updates its dependency graph dynamically at runtime.

When a selector executes its get method, it receives a helper function typically named get:

const userProfileSelector = selector({
  key: 'userProfileSelector',
  get: ({ get }) => {
    const userId = get(currentUserIdAtom);
    return get(userDatabaseAtom(userId));
  },
});

Whenever get(node) is invoked inside this execution context:

  1. Subscription Registration: Recoil intercepts the read call and creates a directed edge in the dependency graph from the referenced node (currentUserIdAtom) to the consumer (userProfileSelector).
  2. Dynamic Pruning: If a selector contains conditional logic (such as an if/else block), dependencies evaluated in one execution may not be evaluated in the next. Recoil dynamically drops edges for nodes that were not read during the most recent execution, ensuring that unused nodes do not trigger unnecessary recomputations.

Propagation and Invalidation

When an atom's value changes via a setter function, Recoil leverages the dependency graph to propagate changes efficiently:

  1. Dirty Marking: The updated atom marks itself as dirty and notifies all direct downstream selectors attached to it in the graph.
  2. Topological Invalidation: Recoil traverses the graph downstream from the modified atom. Intermediate selectors invalidate their internal memoization caches.
  3. Lazy Evaluation: Selectors are generally computed lazily. When invalidated, they do not necessarily recompute immediately; instead, they recompute when a mounted React component or another active selector explicitly requests their value.
  4. Targeted Component Re-rendering: React components subscribe directly to specific nodes (either atoms or selectors) using hooks like useRecoilValue. When an atom updates, only the components subscribed to that atom or to invalidated downstream selectors will re-render. Unrelated components remain untouched, avoiding root-level re-render cycles common in classic React Context architectures.

Asynchronous Dependencies and Suspense

Selectors support asynchronous evaluation by returning Promises. The dependency graph mechanism seamlessly handles async dependencies by pausing execution and integrating with React Suspense. While a selector waits for an asynchronous node to resolve, the edge remains recorded in the graph, ensuring that subsequent resolutions or errors propagate down the exact same dependency path.
