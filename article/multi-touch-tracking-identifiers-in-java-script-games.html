Multi-Touch Tracking Identifiers in JavaScript Games

In JavaScript game programming, handling multi-touch input relies on the Touch Events API, where each active contact point is assigned a unique tracking identifier. This article explains how the Touch.identifier property functions, how browsers manage separate touch lists, and how game developers use these identifiers in a state-tracking loop to process simultaneous inputs—such as a virtual joystick and action buttons—without state collisions.

The Role of Touch.identifier

When a user places a finger on a touch-enabled screen, the browser generates a Touch object. A critical property of this object is identifier, a unique integer assigned to that specific point of contact for its entire lifecycle.

As long as that finger remains on the display, its identifier does not change. Even when multiple fingers land, move, and lift at varying times, the identifier guarantees that input logic can differentiate finger A from finger B, eliminating the cross-talk inherent to single-pointer models.

Understanding Touch Lists

Touch events (touchstart, touchmove, touchend, and touchcancel) expose three distinct lists of Touch objects:

  1. touches: Every contact point currently on the screen.
  2. targetTouches: Contact points that originated on the same DOM element (e.g., a <canvas>).
  3. changedTouches: Only the contact points responsible for triggering the current event.

To track continuous movement, games evaluate the changedTouches list during touchmove and touchend events. By matching the identifier of each altered touch against active game controls, the engine updates only the systems associated with that specific touch.

Managing Input States with a Touch Map

The standard pattern for tracking touch points in an engine is using a Map or hash table where the key is the Touch.identifier:

const activeTouches = new Map();

canvas.addEventListener('touchstart', (e) => {
  for (let i = 0; i < e.changedTouches.length; i++) {
    const touch = e.changedTouches[i];
    activeTouches.set(touch.identifier, {
      startX: touch.clientX,
      startY: touch.clientY,
      currentX: touch.clientX,
      currentY: touch.clientY,
      role: assignRole(touch.clientX) // e.g., 'joystick' or 'action'
    });
  }
});

canvas.addEventListener('touchmove', (e) => {
  for (let i = 0; i < e.changedTouches.length; i++) {
    const touch = e.changedTouches[i];
    const tracked = activeTouches.get(touch.identifier);
    if (tracked) {
      tracked.currentX = touch.clientX;
      tracked.currentY = touch.clientY;
    }
  }
});

function removeTouch(e) {
  for (let i = 0; i < e.changedTouches.length; i++) {
    activeTouches.delete(e.changedTouches[i].identifier);
  }
}

canvas.addEventListener('touchend', removeTouch);
canvas.addEventListener('touchcancel', removeTouch);

Isolating Independent Game Controls

In complex UI setups, such as a twin-stick shooter, identifiers prevent one control from hijacking another. During touchstart, the code determines the touch's spatial role—for instance, assigning touches with clientX < screenWidth / 2 to movement, and touches on the right half to aiming.

By storing this role alongside the identifier, any future touchmove events check the role mapped to that identifier rather than relying on current coordinates. If a player drags the movement thumbstick far into the right side of the screen, the game continues to route the coordinate deltas to the movement system, preventing the aim system from misinterpreting the gesture.

Handling touchcancel

Touch tracking can break if an interruption occurs—such as an incoming phone call, an OS gesture (like swiping down a notification bar), or too many fingers exceeding hardware limits. These trigger the touchcancel event instead of touchend.

To maintain state integrity, game engines treat touchcancel with the same cleanup logic as touchend. Failing to remove identifiers on cancellation results in "ghost" inputs, where the game acts as though a finger is permanently pressed down. Listening to both events ensures that identifier mappings stay clean and synchronized with actual screen contacts.
