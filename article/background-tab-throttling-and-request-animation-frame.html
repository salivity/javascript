Background Tab Throttling and requestAnimationFrame

Modern web browsers optimize system resources by throttling or completely pausing requestAnimationFrame (rAF) when a browser tab loses focus. In JavaScript game programming, this behavior directly disrupts the game loop, leading to massive delta time spikes, physics simulation breakdowns, and desynchronization between rendering, audio, and network states. Understanding how browsers handle background tabs and implementing proper state-handling strategies are essential steps to preventing game crashes and maintaining a seamless player experience.

Why Browsers Throttle requestAnimationFrame

To conserve battery life and CPU usage, browsers such as Chrome, Firefox, and Safari deprioritize inactive tabs. While an active tab typically fires requestAnimationFrame callbacks at the display's native refresh rate (usually 60Hz to 144Hz), switching to another tab causes the browser to either lower the execution frequency to as low as once per second (1Hz) or stop invoking the callback entirely until the user returns.

Core Issues Caused by Throttling

The Delta Time "Spiral of Death"

Most modern game engines compute game logic using a variable delta time (dt)—the elapsed time between the current frame and the previous frame. When a user switches tabs and returns a minute later, the next requestAnimationFrame callback receives a timestamp showing an elapsed time of 60 seconds instead of the usual ~16.6 milliseconds.

If this raw dt is fed into physics or collision systems, several problems occur:

  • Tunneling: High-speed objects skip past collision boundaries entirely because their single-frame displacement is massive.
  • CPU Freezes: If the loop uses a fixed timestep with a sub-stepping catch-up mechanism, the engine will attempt to simulate thousands of iterations in a single frame to catch up with wall-clock time, hanging the browser thread.

Audio and Visual Desynchronization

Audio systems powered by the Web Audio API or standard HTML5 audio elements run on separate browser threads that often continue playing while rendering is paused. Without intervention, background music, scheduled sound effects, and voice lines continue progressing while the visual scene freezes, completely ruining pacing and cinematic timing.

Multiplayer and Network Timeouts

For multiplayer games relying on WebSockets or WebRTC, pausing the main thread can prevent heartbeats/pings from sending. Servers may treat the stalled connection as a disconnect and drop the client. When the player returns, the accumulated server state can flood the client, causing a massive processing lag spike.

How to Handle Background Throttling

1. Clamp Delta Time

Never pass an unbounded delta time directly to your simulation. Set an upper limit on how large a single frame's time step can be.

let lastTime = performance.now();

function gameLoop(currentTime) {
  let dt = (currentTime - lastTime) / 1000;
  lastTime = currentTime;

  // Cap delta time to a maximum of 100ms (0.1s)
  dt = Math.min(dt, 0.1);

  update(dt);
  render();

  requestAnimationFrame(gameLoop);
}

requestAnimationFrame(gameLoop);

Clamping prevents physics simulations from breaking and avoids lockups in fixed-timestep accumulators.

2. Use the Page Visibility API

The standard approach to tab switching is to explicitly pause the game when the tab is hidden and resume when it becomes visible again.

document.addEventListener("visibilitychange", () => {
  if (document.hidden) {
    pauseGame();
    muteAudio();
  } else {
    // Reset lastTime to avoid a large dt jump upon resumption
    lastTime = performance.now();
    resumeGame();
    unmuteAudio();
  }
});

Using document.visibilityState allows you to open a pause menu, halt non-essential network updates, and suspend the Web Audio context using audioCtx.suspend() and audioCtx.resume().

3. Offload Game Logic to Web Workers

For applications requiring continuous background execution—such as idle games or deterministic real-time multiplayer titles—run game logic inside a Web Worker.

Web Workers run on a background thread and are not tied to the display refresh cycle. While timers like setInterval can still face mild throttling in workers, they are throttled much less aggressively than requestAnimationFrame. The worker handles time accumulation and physics updates, while the main thread's requestAnimationFrame loop purely reads the latest state for rendering.
