How MSW Intercepts Traffic via Service Workers

This article explains how Mock Service Worker (MSW) intercepts network traffic at the browser's Service Worker level during JavaScript tests. It covers the end-to-end mechanism: initializing the worker, listening for native fetch events, delegating request matching between the worker thread and client test runners via messaging channels, and returning synthesized mock responses without modifying application code.

The Service Worker Foundation

MSW leverages the browser’s native Service Worker API, an event-driven programmable network proxy that runs on a separate execution thread from the web application.

To enable this, MSW provides a static worker script (mockServiceWorker.js) generated via the MSW CLI (npx msw init). In browser-based test runners (such as Cypress, Playwright, or Vitest in browser mode), the testing setup executes setupWorker(...handlers).start(). This registers mockServiceWorker.js with the browser’s Service Worker container and grants it scope over all outgoing HTTP traffic within the application’s origin.

Intercepting the Fetch Event

Once registered and activated, the Service Worker automatically captures every outbound network call generated by the application, including requests initiated by window.fetch, XMLHttpRequest, or third-party HTTP clients like Axios.

The worker script attaches a listener to the global fetch event:

self.addEventListener('fetch', (event) => {
  event.respondWith(handleRequest(event));
});

Because the Service Worker operates at the operating system/network boundary of the browser engine, interception occurs at the network level rather than via monkey-patching window.fetch or modifying application code.

Cross-Thread Communication via MessageChannel

Service Workers run in a distinct context without direct access to the DOM, window object, or client-side JavaScript memory where test handlers are defined. To resolve how a request should be handled, the Service Worker communicates with the client thread using the MessageChannel API or client postMessage:

  1. Request Serialization: The Service Worker intercepts the request and serializes its metadata (URL, HTTP method, headers, and body).
  2. Client Notification: The Service Worker sends this serialized payload to the client-side MSW instance via a messaging port.
  3. Handler Matching: The client-side instance evaluates the request against the declared request handlers (e.g., http.get('/api/user', ...)).
  4. Resolution: The handler executes any custom resolver logic and returns a mock response structure back to the Service Worker over the same message channel.

Mock Response Construction

When the Service Worker receives the response instructions from the client thread:

  • Mocked Requests: If a matching handler provided a mock response, the Service Worker instantiates a native Response object containing the specified status code, headers, and body stream. It passes this object into event.respondWith(), instantly fulfilling the browser's original request.
  • Passthrough Requests: If no matching handler exists or the handler explicitly calls passthrough(), the Service Worker omits event.respondWith(). The browser bypasses the worker and forwards the request to the actual network.

Difference Between Browser and Node.js Testing

In headless environments without full browser engines (such as standard Jest or Node-based Vitest runs), Service Workers do not exist natively. In these cases, MSW uses setupServer instead of setupWorker.

Rather than using the Service Worker API, setupServer uses low-level interception libraries (@mswjs/interceptors) to intercept network traffic by patching Node.js core modules (http, https) or polyfilled globals. The underlying handler syntax remains identical, but true Service Worker interception requires a real browser runtime.
