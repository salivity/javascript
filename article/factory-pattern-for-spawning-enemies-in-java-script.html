Factory Pattern for Spawning Enemies in JavaScript

The Factory pattern is a creational design pattern that provides a centralized interface for instantiating objects without exposing the specific creation logic to the rest of the game. In JavaScript game programming, this pattern plays a critical role in dynamically spawning enemy entities by decoupling game loops and wave managers from concrete enemy classes. By delegating instantiation to a dedicated factory, developers can generate diverse, configurable, and scalable enemy encounters at runtime based on game conditions, difficulty levels, or procedural generation rules.

The Problem with Direct Instantiation

In simple game architectures, enemies are often created directly using concrete class constructors, such as new Goblin() or new Skeleton(). As a game scales, this approach creates tight coupling between the spawner and every individual enemy class. If wave logic needs to spawn a different enemy based on player progression, the spawner code quickly becomes cluttered with large switch statements or nested conditionals. Adding new enemy types or modifying existing parameters requires editing the core spawning systems, which increases the likelihood of introducing bugs.

How the Factory Pattern Works

The Factory pattern solves this problem by introducing an intermediary: an EnemyFactory. Instead of calling constructors directly, the spawning system requests an enemy by passing an identifier, such as a string, configuration object, or difficulty tier. The factory evaluates the request, creates the appropriate instance, configures its initial state, and returns it to the caller.

// Base Enemy Class
class Enemy {
  constructor(name, health, speed) {
    this.name = name;
    this.health = health;
    this.speed = speed;
  }

  update() {
    // Shared update logic
  }
}

// Concrete Enemy Types
class Goblin extends Enemy {
  constructor() {
    super("Goblin", 30, 4);
  }
}

class Orc extends Enemy {
  constructor() {
    super("Orc", 80, 2);
  }
}

class Dragon extends Enemy {
  constructor() {
    super("Dragon", 300, 1);
  }
}

// Enemy Factory
class EnemyFactory {
  static createEnemy(type) {
    switch (type.toLowerCase()) {
      case "goblin":
        return new Goblin();
      case "orc":
        return new Orc();
      case "dragon":
        return new Dragon();
      default:
        throw new Error(`Enemy type '${type}' is not recognized.`);
    }
  }
}

Enabling Dynamic Spawning

Using the factory, dynamic spawning becomes clean and modular. A wave manager or spawner can select enemy types dynamically using random selection, difficulty scaling algorithms, or external data such as JSON files:

class WaveSpawner {
  constructor(factory) {
    this.factory = factory;
    this.enemyPool = ["goblin", "orc", "dragon"];
  }

  spawnRandomEnemy(spawnX, spawnY) {
    const randomIndex = Math.floor(Math.random() * this.enemyPool.length);
    const enemyType = this.enemyPool[randomIndex];
    
    const enemy = this.factory.createEnemy(enemyType);
    enemy.x = spawnX;
    enemy.y = spawnY;
    
    return enemy;
  }
}

Key Advantages in JavaScript Game Development

  • Decoupling and Maintainability: The game loop and spawn managers only need to know how to interact with the generic Enemy interface, not the implementation details of each specific enemy subclass.
  • Extensibility: Adding a new enemy type requires creating the class and registering it with the factory. Existing spawner systems require zero code modifications.
  • Data-Driven Design: Factories allow games to read spawn tables directly from JSON or remote APIs, mapping strings to classes dynamically.
  • Object Pooling Integration: The Factory pattern works seamlessly with object pools. Instead of allocating a new instance each time, the factory can pull inactive entities from a pool to minimize garbage collection pauses in JavaScript engines.
