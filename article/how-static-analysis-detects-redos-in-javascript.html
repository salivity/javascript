How Static Analysis Detects ReDoS in JavaScript

Regular Expression Denial of Service (ReDoS) occurs when a poorly constructed regular expression takes exponential or polynomial time to evaluate an input string, leading to thread-blocking behavior in single-threaded environments like Node.js. Static analysis tools detect ReDoS vulnerabilities in JavaScript by parsing source code, translating regular expressions into theoretical automata, and analyzing those automata for catastrophic backtracking patterns without executing the code.

1. Extracting Regex via Abstract Syntax Trees (AST)

The detection process begins with parsing JavaScript source code into an Abstract Syntax Tree (AST) using parsers like Babel, Acorn, or Espree. The static analysis tool traverses the AST to locate regular expressions defined in two forms:

  • Regex Literals: Expressions declared directly in code, such as /^(a+)+$/.
  • RegExp Constructors: Expressions created dynamically using new RegExp("...").

For RegExp constructors, the tool uses string analysis and constant folding to evaluate statically resolvable string arguments. If the regular expression is concatenated from dynamic variables, the tool may employ taint analysis to flag it as potentially vulnerable due to unpredictability.

2. Converting Regex into Finite Automata

Once an expression is isolated, the analyzer parses the pattern string itself into an internal regex AST. It then converts this structure into a Non-deterministic Finite Automaton (NFA) or a Directed Graph representing state transitions.

Because JavaScript uses traditional NFA engines (specifically backtracking engines that support features like lookaheads and backreferences), evaluating matching paths involves backtracking when a match fails. The static analysis tool models this exact behavior mathematically by plotting states, transitions, and character classes.

3. Detecting Ambiguity and Catastrophic Backtracking

The core of ReDoS static detection relies on determining the "degree of ambiguity" in the state graph. Catastrophic backtracking happens when the engine has multiple non-deterministic paths it can take to match the same sequence of characters. Static analyzers evaluate the automaton for specific conditions:

  • Exponential Ambiguity: The tool searches for nested quantifiers where repetition applies to a repeated group, such as (a+)+ or ([a-zA-Z]+)*. In automaton terms, this creates multiple nested loops that accept overlapping sets of characters, leading to \(O(2^n)\) time complexity.
  • Polynomial Ambiguity: The tool checks for consecutive or overlapping repeated alternations, such as (a|a)+ or (a|ab)+. While less severe than exponential patterns, these can still result in \(O(n^2)\) or higher polynomial matching times.

Tools calculate the product automaton (pairing the NFA with itself) to formally prove whether two distinct paths can process the exact same sequence of input characters. If an unbounded cycle exists within these overlapping paths, the expression is marked as vulnerable.

4. Pattern-Based Heuristics and Linters

Not all static tools construct full automata due to the computational cost during continuous integration (CI) workflows. Lighter-weight tools and linter plugins (such as ESLint rules like clean-regex or no-unsafe-regex) rely on heuristic pattern matching.

These linters match regex AST nodes against known vulnerable anti-patterns, including:

  • Repeated groups containing repetition: (x+)+
  • Alternations with overlapping prefixes followed by repetition: (a|a+)+
  • Overlapping tokens inside repeating groups: (\d|\s)+

While heuristic checks are significantly faster, they carry a higher rate of false positives and false negatives compared to formal automata analysis.

5. Taint Tracking and Contextual Reachability

Advanced static application security testing (SAST) engines combine automata analysis with data-flow analysis. Identifying a vulnerable regex is only half the problem; the analyzer must determine if the regex actually processes untrusted user data.

Taint tracking maps the flow of external inputs (such as HTTP request parameters, headers, or body payloads) to regex execution sinks like .test(), .match(), .search(), or .replace(). If an untrusted input can reach a regular expression proven to have super-linear time complexity, the scanner flags the finding as a high-priority ReDoS vulnerability.
