Node.js Permission Model Filesystem Restrictions

The Node.js experimental permission model provides native security mechanisms to restrict application access to system resources, with a primary focus on filesystem operations. Introduced in Node.js v20, this feature allows developers to execute untrusted code or secure dependencies by explicitly defining read and write boundaries. This article outlines the core capabilities of the permission model, the specific flags used to restrict filesystem access, runtime permission querying, and the boundaries of this security layer.

Enabling the Permission Model

By default, Node.js applications inherit all system privileges of the executing user. The permission model is activated by passing the --experimental-permission flag during startup. Once enabled, Node.js shifts to a zero-trust default stance: all filesystem access is completely revoked unless explicitly granted via configuration flags. Attempting an unauthorized filesystem call triggers an ERR_ACCESS_DENIED exception.

Granular Read and Write Controls

The model separates file access into distinct read and write permissions, preventing common attack vectors such as malicious data exfiltration or unauthorized file modification.

  • Restricting Read Access (--allow-fs-read): Passing --allow-fs-read=* grants read access to the entire disk. Alternatively, passing specific paths restricts access to defined directories or files. For example, --allow-fs-read=/etc/app/config.json --allow-fs-read=./public/ restricts read operations strictly to that configuration file and public directory.
  • Restricting Write Access (--allow-fs-write): Similar to read controls, --allow-fs-write accepts wildcards or targeted paths. For instance, --allow-fs-write=/tmp/logs/ ensures the application can only alter or generate files inside the designated log directory.

Read and write boundaries operate independently. An application can be granted permission to write temporary files without having access to read source code or sensitive system directories.

Path Resolution and Traversal Protection

The permission model resolves paths into absolute canonical representations before evaluating access. This design automatically guards against basic path-traversal attacks (such as ../ sequences) designed to escape a directory jail. The permission checks intercept core module calls across node:fs, node:fs/promises, and related file-handling operations.

Runtime Permission Checking

Applications can inspect their permissions programmatically using the process.permission API. This allows developers to check whether a capability is present before executing an operation, preventing abrupt runtime errors:

// Check if read access to a specific directory is available
const canRead = process.permission.has('fs.read', '/data/records');

if (canRead) {
  // Execute file access logic
}

The process.permission.has() method accepts the resource type (such as fs.read or fs.write) along with the target path.

Native Addon and Child Process Enforcement

Filesystem access restrictions cannot be enforced effectively if an application can spawn uncontrolled child processes or load arbitrary native C++ addons. Consequently, enabling --experimental-permission automatically disables the loading of native addons (equivalent to --no-addons) and disables process spawning unless explicitly overridden with --allow-child-process. This containment ensures that code cannot bypass Node.js runtime checks via underlying system binaries or native bindings.
