heapTotal vs heapUsed vs external in Node.js

In Node.js, monitoring application performance requires understanding how the V8 engine allocates and tracks system resources. The process.memoryUsage() method provides a snapshot of memory utilization across several key metrics, most notably heapTotal, heapUsed, and external. This article explains the technical distinctions among these three metrics, detailing what each value measures, how the V8 garbage collector interacts with them, and how to use them to diagnose memory leaks and optimize your application.

Understanding the Metrics

When you call process.memoryUsage(), the Node.js runtime returns an object containing byte measurements for different memory segments:

{
  rss: 35979264,
  heapTotal: 7127040,
  heapUsed: 4467360,
  external: 1395898,
  arrayBuffers: 11158
}

1. heapTotal

heapTotal represents the total amount of memory allocated by the operating system for the V8 JavaScript execution heap.

V8 pre-allocates memory chunks from the OS to avoid the overhead of requesting memory every time a new object or variable is instantiated. Therefore, heapTotal reflects both the memory currently in use and the reserved, empty space waiting for future allocations. As your application demands more memory, V8 expands heapTotal in increments up to the maximum heap limit (configured via --max-old-space-size).

2. heapUsed

heapUsed represents the actual memory currently occupied by JavaScript objects, primitives, strings, and closures running in your application.

This value is always smaller than or equal to heapTotal. The gap between heapTotal and heapUsed is the available headroom that V8 can write to before needing to either run garbage collection or request another chunk of memory from the OS. A continuously rising heapUsed metric that does not drop after garbage collection cycles typically indicates a JavaScript memory leak.

3. external

external represents memory allocated outside the V8 heap by C++ objects that are bound to JavaScript objects.

Node.js is built on top of C++, and many native operations allocate memory directly via native bindings rather than through the V8 engine. The primary contributor to external memory is Node.js Buffer instances. When you create a Buffer, the raw binary data resides in C++ memory outside the V8 heap, but a small JavaScript wrapper object resides inside the V8 heap (heapUsed) to reference it. Other contributors to external include native C++ add-ons and WebAssembly memory instances.

Key Differences and Relationships

  • Allocation Target: heapTotal and heapUsed measure standard JavaScript objects managed entirely within the V8 heap. external measures native memory allocated outside the V8 heap via C++ bindings.
  • Capacity vs. Utilization: heapTotal represents allocated capacity, whereas heapUsed represents current utilization.
  • Garbage Collection Behavior: When V8 triggers garbage collection, it scans heapUsed to free unreferenced objects. When a JavaScript object referencing an external resource (like a Buffer) is garbage-collected, V8 triggers the corresponding C++ destructor to deallocate the memory tracked under external.

Diagnosing Memory Issues

  • Standard JS Leak: If heapUsed constantly climbs alongside heapTotal until the process crashes with an "out of memory" error, the application is retaining references to JavaScript objects (such as growing arrays, caches, or uncleaned event listeners).
  • Buffer/Stream Leak: If heapUsed remains low and stable, but external (and rss) continues to climb, the application is leaking native bindings, often caused by unclosed streams, unhandled file descriptors, or excessive Buffer allocations that remain referenced.
