How Moddable XS Runs JavaScript on Microcontrollers

The Moddable SDK enables resource-constrained microcontrollers to run modern, standard ECMAScript using its XS JavaScript engine. By shifting the heavy lifting of parsing, optimization, and initial object creation to compile time, XS allows devices with as little as a few tens of kilobytes of RAM to execute full-featured JavaScript. This article explains how the XS engine achieves modern language support on embedded hardware through flash-memory residency, ahead-of-time pre-compilation, compact data structures, and optimized memory management.

Ahead-of-Time Pre-Compilation and Flash Execution

Traditional JavaScript engines like V8 or SpiderMonkey rely on dynamic Just-In-Time (JIT) compilation and in-memory parsing, which consume tens or hundreds of megabytes of RAM. Microcontrollers typically provide only 32 KB to 512 KB of volatile RAM paired with a few megabytes of flash memory (ROM).

The XS engine circumvents this constraint by moving the parsing and instantiation phase to the developer’s host machine. During the build process, the Moddable SDK's toolchain (specifically mcrun and mcconfig) runs an instance of XS to parse the JavaScript source code, validate it, and execute module initializers. The resulting heap state—including bytecode, symbol tables, functions, and static objects—is serialized into an image that is flashed directly into the microcontroller's read-only flash memory.

Because flash memory is memory-mapped on most modern microcontrollers (such as the ESP32 or RP2040), the XS runtime executes bytecode and references immutable objects directly from flash (ROM) via standard pointer access, requiring zero RAM overhead for statically compiled code.

Strict ECMAScript Compliance Without Subsets

Many embedded runtimes limit developers to an outdated or non-standard subset of JavaScript. The XS engine, by contrast, provides nearly 100% compliance with the official ECMAScript specification, regularly passing the industry-standard Test262 test suite.

XS supports modern features directly on embedded chips, including:

  • Classes, private fields, and inheritance
  • Async/await, Promises, and event loops
  • Standard ECMAScript modules (import / export)
  • Arrow functions, rest/spread parameters, and destructuring
  • TypedArrays, ArrayBuffers, and DataViews for low-level binary manipulation

XS implements these features via a lightweight, deterministic bytecode interpreter written in standard ANSI C, avoiding runtime JIT compilers that require executable RAM pages—a feature most microcontrollers lack.

Compact Memory Layout and Garbage Collection

To operate inside microcontrollers, XS uses a compact internal representation for JavaScript values.

Every JavaScript value in XS is represented as an 8-byte or 16-byte slot, depending on whether the architecture is 32-bit or 64-bit. These slots contain union types that encode integers, booleans, floating-point numbers, and pointers. By packing object properties into tightly contiguous slot arrays, pointer overhead is significantly reduced compared to desktop runtimes.

The XS memory space is divided into distinct zones:

  • ROM Heap: Holds pre-compiled, frozen objects and built-in prototypes (such as Array.prototype or Math). These slots are read-only and never consume volatile RAM.
  • RAM Heap: Houses mutable variables, new object instances, closures, and dynamic buffers created while the device runs.

Garbage collection in XS is designed for real-time predictability. XS employs a mark-and-sweep collector tailored for small heaps. Because immutable objects residing in flash memory do not need to be tracked for deallocation, the garbage collector only scans and traverses the active RAM heap. This drastically cuts pause times and prevents memory fragmentation.

Native C Integration and Hardware Control

The XS engine integrates directly with low-level microcontrollers using minimal-overhead C bindings called the XS in C (XSC) interface. Built-in modules allow JavaScript code to directly drive hardware buses—such as GPIO, I2C, SPI, and UART—as well as graphic displays and touch controllers.

Buffers, sensor readings, and peripheral registers can be read into ArrayBuffer objects without intermediate copying, allowing developers to build responsive IoT user interfaces, network clients, and sensor nodes using high-level JavaScript code while maintaining near-native C execution speeds.
