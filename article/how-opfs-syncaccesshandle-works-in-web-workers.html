How OPFS SyncAccessHandle Works in Web Workers

The Origin Private File System (OPFS) provides a private, highly optimized storage endpoint for web applications, highlighted by the FileSystemSyncAccessHandle. This article explores how SyncAccessHandle enables fast, synchronous file reading and writing within Web Workers. You will learn the mechanics behind its performance, how it bypasses typical web asynchronous overhead, its locking mechanisms, and why it is an essential component for demanding workloads like SQLite compiled to WebAssembly.

What Is the OPFS SyncAccessHandle?

The Origin Private File System is part of the File System Access API, offering an origin-isolated storage area that users cannot directly view or access through the host OS file explorer. While standard OPFS operations rely on asynchronous Promises (like getFile() and createWritable()), the FileSystemSyncAccessHandle provides synchronous read and write primitives.

Because synchronous I/O operations block execution until completion, the browser strictly restricts the creation and use of SyncAccessHandle to dedicated Web Workers. This prevents the main execution thread from freezing, keeping the user interface responsive.

How Synchronous I/O Is Achieved

To read and write synchronously, a Web Worker must request an access handle from a standard OPFS file handle using await fileHandle.createSyncAccessHandle(). Once opened, all subsequent file operations on that handle execute synchronously.

1. Direct In-Place Modification

Traditional web file writing often requires generating an entire Blob or stream and replacing the file via a temporary copy. In contrast, SyncAccessHandle maps directly to OS-level file primitives (such as read and pwrite in POSIX environments). It operates on raw memory via typed arrays like ArrayBuffer or Uint8Array, allowing developers to overwrite specific byte offsets in-place without loading the entire file into memory.

2. Exclusive Locking Mechanism

To ensure data integrity and avoid concurrency issues, calling createSyncAccessHandle() places an exclusive lock on the associated file. As long as the handle remains open:

  • No other execution context (neither the main thread nor other workers) can open another SyncAccessHandle or a standard asynchronous writable stream on that file.
  • Any attempt to do so throws a NoModificationAllowedError.

Once the worker finishes file operations and calls accessHandle.close(), the lock is released.

3. Native File System Performance

Because JavaScript execution in the worker halts sequentially during a synchronous call, the browser can bypass the overhead of creating Promises, microtask queue scheduling, and inter-process communication (IPC) for every individual chunk of data. This brings read and write throughput close to native file system speeds.

Core Synchronous Methods

The FileSystemSyncAccessHandle interface exposes a concise set of synchronous methods:

  • read(buffer, options): Reads bytes from the file at a specified offset into a given ArrayBufferView and returns the number of bytes read.
  • write(buffer, options): Writes bytes from an ArrayBufferView into the file at a specified offset and returns the number of bytes written.
  • truncate(newSize): Resizes the file to the specified byte length.
  • getSize(): Returns the current size of the file in bytes.
  • flush(): Flushes any modified cached data to the underlying persistent storage device.
  • close(): Closes the handle and releases the exclusive lock on the file.

Primary Use Cases

The synchronous nature of SyncAccessHandle makes it ideal for ports of C, C++, and Rust applications via WebAssembly (Wasm). Applications such as SQLite's official Wasm build, video editors, and game engines rely heavily on synchronous POSIX-like system calls to maintain internal data structures (such as B-trees) and achieve low-latency persistence on the web.
