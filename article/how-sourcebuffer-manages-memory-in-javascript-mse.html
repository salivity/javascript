How SourceBuffer Manages Memory in JavaScript MSE

The Media Source Extensions (MSE) API enables dynamic, adaptive streaming in modern web browsers by allowing JavaScript to pass media segments directly to an HTML5 media element via the SourceBuffer interface. Managing memory during this process is critical because browsers operate under strict memory constraints, and unbounded buffering can quickly lead to crashes or playback stalls. Memory management in a SourceBuffer relies on a combination of automatic browser-level garbage collection and manual memory eviction driven by the application using methods like SourceBuffer.remove() to maintain a stable, sliding playback window.

The SourceBuffer Memory Model

When media chunks are fetched over the network, JavaScript feeds this binary data into the SourceBuffer using the appendBuffer() method. The browser’s media engine decodes the container metadata, parses the elementary audio or video streams, and stores them in an internal decoding buffer in uncompressed or semi-demuxed formats.

Because these decoded samples consume significantly more memory than raw network packets, the browser allocates a dedicated, capped memory pool for each SourceBuffer. Depending on the browser, operating system, and whether the device is mobile or desktop, this limit typically ranges from 30 MB to several hundred megabytes.

Automatic Browser Eviction

Browsers implement native garbage collection mechanisms to prevent streaming video from consuming all available system RAM. When a SourceBuffer approaches its internal memory ceiling, the user agent attempts to automatically evict unneeded media segments.

Typically, the browser's eviction algorithm prioritizes removing:

  1. Distant past data: Media segments that have already been played and are far behind the current HTMLMediaElement.currentTime.
  2. Distant future data: Media segments buffered too far ahead of the current playhead, usually beyond the immediate lookahead threshold.

However, native eviction policies are non-standardized and unpredictable. Some browsers aggressively prune past data, while others retain it to enable instant seeking backward. On lower-memory mobile devices, native eviction may fail to trigger before the allocation limit is breached.

Manual Memory Eviction via SourceBuffer.remove()

To ensure consistent performance across all platforms, media players such as HLS.js and Shaka Player manually manage memory using the SourceBuffer.remove() method. This method removes media segments across a specified time range:

// Remove buffered data from the beginning of the stream up to 30 seconds behind the playhead
const safeRemovalTime = Math.max(0, videoElement.currentTime - 30);
if (!sourceBuffer.updating && safeRemovalTime > 0) {
  sourceBuffer.remove(0, safeRemovalTime);
}

The remove() operation is asynchronous. While it is executing, the SourceBuffer.updating flag is set to true. Attempting to call appendBuffer() or another remove() while updating is true throws an InvalidStateError. Developers must wait for the updateend event before performing subsequent buffer operations.

Handling QuotaExceededError

If new data is appended faster than the browser can allocate memory—or if manual cleanup is not performed—the browser throws a QuotaExceededError DOMException. This indicates that the SourceBuffer is full and cannot accept more data.

Robust players handle this error through a fallback eviction loop:

  1. Catch the QuotaExceededError during appendBuffer().
  2. Query sourceBuffer.buffered to identify currently buffered ranges.
  3. Execute an aggressive remove() call targeting media further away from currentTime.
  4. Listen for the updateend event, then retry appending the failed chunk.

Implementing a Sliding Window Strategy

The industry-standard approach for steady-state memory management is a sliding window algorithm. The application monitors the currentTime of the media element and maintains two thresholds:

  • Back-buffer limit: Usually 10 to 30 seconds of historical media kept to allow smooth recovery from minor user scrub-backs.
  • Forward-buffer limit: Usually 20 to 60 seconds of future media to withstand network fluctuations without unnecessarily bloating memory.

By routinely evicting data outside this window and only fetching new chunks when the forward buffer drops below its threshold, the SourceBuffer maintains a flat, deterministic memory footprint throughout streams of arbitrary duration.
