How Jasmine spyOn Intercepts and Verifies Calls

Jasmine’s spyOn function intercepts and verifies JavaScript function calls by dynamically replacing an object's target method with a wrapper function. This wrapper records execution metadata—such as invocation count, arguments, and return values—while offering options to stub the method, delegate back to the original implementation, or return custom data. This article explores the underlying mechanisms that allow spyOn to wrap functions, record execution details, and support test assertions.

Dynamic Method Replacement

JavaScript objects are mutable by default, meaning their properties and methods can be reassigned at runtime. When you execute spyOn(object, 'methodName'), Jasmine uses this dynamic nature to intercept execution:

  1. Caching the Original Function: Jasmine creates an internal closure that holds a direct reference to the original method: const originalMethod = object[methodName];.
  2. Assigning the Spy Wrapper: Jasmine replaces object[methodName] with a newly generated spy function.
  3. Registering the Spy: The spy is added to Jasmine’s current execution context so it can be tracked and later cleaned up.

Because the reference on the target object is replaced directly, any other module or service holding a reference to object will invoke the spy whenever they call object.methodName().

Call Tracking via Closures

Every spy instance includes a tracking object (accessible via spy.calls). When the spy function is invoked, it intercepts the incoming call and gathers information before deciding whether to execute the original logic:

  • Arguments: Captures Array.from(arguments) for each call.
  • Context: Records the this value used during invocation.
  • Count: Increments an internal counter tracking the total number of invocations.
  • Return Values and Errors: Captures the outcome of the call, whether it produced a result or threw an exception.

This data is stored chronologically in an array of call records inside the spy's closure, enabling assertions on past executions at any point in the test.

Execution Strategies

By default, calling spyOn(target, 'method') stubs the target method, preventing the original code from running and returning undefined. However, Jasmine provides chainable strategy modifiers that dictate how the spy behaves when invoked:

  • .and.callThrough(): Executes the cached originalMethod using originalMethod.apply(this, arguments), allowing the real behavior to run while still recording call metrics.
  • .and.returnValue(value): Halts execution of the underlying logic and immediately returns a predefined stubbed value.
  • .and.callFake(customFn): Redirects the call to a mock function provided by the developer.
  • .and.throwError(message): Automatically throws a specified error when the method is invoked.

Regardless of which execution strategy is selected, the call tracking step always runs first.

Verification and Assertions

Jasmine matchers (such as toHaveBeenCalled() and toHaveBeenCalledWith()) do not perform complex runtime inspections. Instead, they read the metadata stored in the spy's calls tracker:

  • expect(spy).toHaveBeenCalled() checks if spy.calls.count() > 0.
  • expect(spy).toHaveBeenCalledWith(a, b) searches spy.calls.allArgs() to determine if any invocation's argument array deeply equals [a, b].
  • expect(spy).toHaveBeenCalledTimes(n) checks if spy.calls.count() === n.

If the condition fails, Jasmine uses the recorded call data to construct a descriptive error message showing expected calls versus actual calls.

Automatic Teardown

To prevent test pollution across specifications, Jasmine tracks all active spies created within an it or beforeEach block. When the test spec finishes, Jasmine's test runner iterates through all tracked spies and restores the original function pointers (object[methodName] = originalMethod). This ensures the target object is returned to its pristine state for subsequent tests.
