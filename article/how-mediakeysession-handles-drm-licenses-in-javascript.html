How MediaKeySession Handles DRM Licenses in JavaScript

The Encrypted Media Extensions (EME) API enables web browsers to play DRM-protected content without external plugins. At the core of this API is the MediaKeySession interface, which acts as the communication pipeline between the browser's JavaScript environment, the underlying Content Decryption Module (CDM), and the DRM license server. This article details the lifecycle of a MediaKeySession and how it coordinates challenge generation, network delivery, and license ingestion to decrypt protected media.

1. Triggering Encrypted Playback

The process begins when an HTMLMediaElement (<video> or <audio>) encounters encrypted streaming data—typically delivered via Media Source Extensions (MSE). The media element cannot decrypt the stream and fires an encrypted event. This event provides the initialization metadata:

  • initDataType: The format of the metadata (such as cenc for Common Encryption or keyids).
  • initData: Container-specific data, such as Key IDs (PSSH boxes in MP4 streams), required to identify which keys are needed.

2. Creating the MediaKeySession

Before requesting a license, the web application must obtain access to a CDM by resolving a MediaKeySystemAccess object via navigator.requestMediaKeySystemAccess() and creating a MediaKeys instance attached to the media element.

Once configured, the application instantiates a session:

const session = mediaKeys.createSession('temporary');

The session type is typically 'temporary' for streaming media where keys are discarded when the session ends, or 'persistent-license' if the license needs to be stored offline for later playback.

3. Generating the License Request

To begin the license acquisition workflow, the application passes the media's initialization metadata into the session:

session.generateRequest(event.initDataType, event.initData);

Behind the scenes, the browser hands this data to the CDM. The CDM parses the metadata, creates a cryptographic challenge (a license request containing hardware identifiers, client capabilities, and required key IDs), and queues this challenge for the application.

4. Handling the message Event and Server Exchange

Because the EME specification intentionally separates the CDM from direct network operations, the CDM cannot make network requests directly. Instead, MediaKeySession dispatches a message event:

session.addEventListener('message', async (event) => {
  const licenseRequest = event.message; // ArrayBuffer containing the challenge
  
  const response = await fetch('https://drm-license-server.example.com/rights', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/octet-stream'
    },
    body: licenseRequest
  });

  const license = await response.arrayBuffer();
  await session.update(license);
});

The JavaScript application acts as an intermediary: it intercepts the event.message, adds any required authentication headers (such as user tokens or authorization cookies), and sends it to the DRM license acquisition server.

5. Updating the Session with the License

When the license server responds with the encrypted license payload, the application passes this buffer back into the CDM via the update() method:

await session.update(license);

The CDM validates the payload, extracts the decryption keys, and stores them in secure memory. If the license is invalid, expired, or corrupted, the promise returned by update() rejects with an error.

6. Monitoring Key Status and Playback

Once the license is successfully loaded, MediaKeySession updates its keyStatuses map and fires a keystatuseschange event. The application can inspect the status of individual keys:

  • usable: The key is valid and currently decrypting media.
  • expired: The license duration has lapsed.
  • output-restricted: Output protection (e.g., HDCP) requirements are not met.
  • internal-error: The CDM encountered a failure processing the key.

With the keys marked as usable, the CDM automatically decrypts incoming media samples directly in the media pipeline, allowing seamless and secure video playback.

7. Session Teardown

When the media item finishes, or when the user navigates away, the session should be cleaned up using session.close(). This releases system memory and notifies the CDM to discard the active decryption keys.
