Timing Attacks in JavaScript Authentication

Standard string equality checks in JavaScript authentication workflows are vulnerable to timing attacks because built-in comparison operators use short-circuit evaluation, returning immediately upon finding the first mismatched character. This behavior causes the execution time of the comparison to correlate directly with the number of consecutive characters that match between the user's input and the stored secret. Over time, an attacker can measure these subtle time differences across repeated requests to infer sensitive secrets—such as API keys, authentication tokens, and password hashes—character by character.

How JavaScript Compares Strings

JavaScript engines like V8 and SpiderMonkey are heavily optimized for performance. When evaluating an equality expression such as secret === userInput, the engine executes several sequential steps:

  1. Reference and Length Check: If the strings occupy the same memory location, the check returns true. If their lengths differ, it immediately returns false.
  2. Sequential Character Comparison: The engine compares characters from left to right, one by one.
  3. Early Exit Optimization: As soon as an index is reached where the characters do not match, the operation stops and returns false. The remaining characters are never evaluated.

Because the engine terminates the loop early, comparing two strings that match in zero characters takes measurably less CPU time than comparing two strings that match in ten characters.

How Attackers Exploit the Timing Difference

A timing attack transforms a brute-force problem with exponential complexity into one with linear complexity. Instead of guessing an entire secret at once, the attacker guesses one character at a time:

  • Guessing the First Character: The attacker sends inputs starting with different characters (e.g., a..., b..., c...). When the input's first character matches the secret's first character, the comparison must check at least the second character before failing, taking slightly longer.
  • Iterating Through the String: After determining the first character based on the highest average response latency, the attacker repeats the process for the second character, then the third, and so on.

Although network jitter, Node.js event loop latency, and garbage collection introduce noise, attackers overcome this by sending hundreds or thousands of requests and applying statistical analysis (such as calculating the mean and standard deviation) to extract the timing signal.

Preventing Timing Attacks in JavaScript

To eliminate this vulnerability, authentication routines must use constant-time comparisons. A constant-time algorithm always evaluates every single byte of the input regardless of where a mismatch occurs, ensuring that the execution duration remains identical whether the strings match completely or not at all.

In Node.js, the built-in crypto module provides a dedicated function for this purpose:

const crypto = require('crypto');

function safeCompare(a, b) {
  const bufferA = Buffer.from(a);
  const bufferB = Buffer.from(b);

  if (bufferA.length !== bufferB.length) {
    return false;
  }

  return crypto.timingSafeEqual(bufferA, bufferB);
}

crypto.timingSafeEqual operates directly on memory buffers using bitwise operations (such as XOR accumulation) to verify equality across all bytes before returning a final boolean value. In browser environments or contexts where Node.js APIs are unavailable, libraries like Web Crypto or vetted constant-time string comparison packages should be used in place of native operators like === for all security-critical validations.
