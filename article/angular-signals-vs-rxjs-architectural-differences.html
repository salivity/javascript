Angular Signals vs RxJS: Architectural Differences

Angular Signals and RxJS Observables represent two distinct reactive paradigms within the JavaScript ecosystem. While RxJS is an asynchronous, event-driven stream processing library based on the Gang of Four Observer pattern, Angular Signals are synchronous, fine-grained state management primitives based on an internally tracked push-pull dependency graph. Understanding their architectural differences reveals how they complement each other rather than serve as direct drop-in replacements.

Reactivity Model: Push Streams vs. Push-Pull Graphs

The primary architectural distinction lies in how data propagates from producer to consumer.

  • RxJS (Push-Based Streams): Observables operate on a purely push-based contract. The producer emits a value, and the consumer reacts via an observer callback. The stream controls when the consumer receives data. Observables do not inherently retain state; they represent pipelines through which values pass.
  • Angular Signals (Push-Pull / Glitch-Free): Signals use a two-phase push-pull evaluation algorithm. When a signal’s value changes, a "push" phase synchronously marks dependent computed values and effects as dirty. The actual re-computation occurs lazily during the "pull" phase, when the consumer reads the value. This ensures "glitch-free" execution, eliminating unnecessary computations and diamond dependency issues common in pure push models.

State Representation vs. Event Streams

The nature of the data handled by each abstraction dictates its structure and usage:

  • Signals Model State: A signal represents a value that exists continuously over time. It is always synchronous and always possesses a current value that can be accessed without creating a subscription (mySignal()). Signals cannot error out or complete; they only change state.
  • Observables Model Events: An Observable models discrete events over time. A stream might emit zero, one, or infinite values, and can either complete successfully or terminate with an error. Values can be delivered synchronously or asynchronously. Importantly, a standard Observable does not have an intrinsic "current value" unless converted into a stateful construct like a BehaviorSubject.

Angular Change Detection Integration

Architecturally, Signals were designed to evolve Angular's rendering engine away from global dirty-checking.

  • Observables and Zone.js: Angular traditionally relies on Zone.js to monkey-patch browser APIs and intercept asynchronous operations, triggering top-down change detection cycles across component trees. Observables do not inform Angular which DOM node changed unless bridged through the async pipe, which internally calls ChangeDetectorRef.markForCheck().
  • Signals and Fine-Grained Reactivity: Signals directly integrate with Angular's reactive graph. The framework knows precisely which template nodes depend on which signals. This enables signal-based change detection (zoneless architecture), allowing targeted updates to specific components or template expressions without traversing the entire component hierarchy.

Lifecycle and Memory Management

  • RxJS Subscription Overhead: Observables require active subscription lifecycle management. If a developer subscribes imperatively to an Observable without tearing it down via takeUntil, takeUntilDestroyed, or explicit unsubscribe() calls, it risks creating memory leaks.
  • Signals Dynamic Tracking: Signals manage dependencies automatically. When a signal is read inside a computed() or effect(), it dynamically registers itself as a dependency. When a branch of conditional logic no longer reads that signal, the dependency is automatically pruned from the graph. Cleanup is tied to the enclosing injection context or component lifecycle without manual unsubscription.

Composition and Asynchrony

  • RxJS for Asynchronous Orchestration: RxJS excels at complex asynchronous operations. Its rich operator pipeline (switchMap, debounceTime, mergeMap, retry) makes it the architectural standard for handling race conditions, HTTP requests, WebSockets, and cancellable event pipelines.
  • Signals for Synchronous Computations: Signals are strictly synchronous. Derived state is generated using pure computations (computed(() => a() + b())). Signals lack native mechanisms for debouncing, throttling, or orchestrating asynchronous workflows, relying instead on interop utilities (toSignal and toObservable) to bridge with RxJS when asynchronous manipulation is required.
