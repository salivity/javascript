Spies vs Stubs vs Mocks in JavaScript Testing

In JavaScript test-driven development, test doubles are essential tools used to isolate units of code by replacing dependencies. While the terms "spy," "stub," and "mock" are often used interchangeably, they serve distinct architectural roles and manipulate the execution flow of a test suite differently. This article outlines the structural differences between these three test doubles, analyzing how they handle implementation execution, state recording, and assertion logic.

The Taxonomy of Test Doubles

Test doubles act as stand-ins for production dependencies—such as APIs, databases, or third-party libraries—to keep unit tests deterministic and fast. The distinction between spies, stubs, and mocks lies in how much control they take over the underlying code and how they verify test outcomes.

1. Spies: Execution Observation

A spy is a wrapper around an existing function that records metadata about its execution without changing its underlying behavior.

  • Structural Role: Non-invasive monitoring.
  • Implementation: The original function runs as normal. The spy sits between the caller and the target function, tracking invocations, passed arguments, return values, and thrown exceptions.
  • Verification Style: Post-execution assertion. You run the code under test, then assert that the spy recorded the expected interactions.
// Example using Jest
const paymentService = {
  process: (amount) => amount > 0,
};

// Structural wrap: original code still executes
const spy = jest.spyOn(paymentService, 'process');

paymentService.process(100);

// Assertion happens after execution
expect(spy).toHaveBeenCalledWith(100);
expect(spy).toHaveReturnedWith(true);

spy.mockRestore();

2. Stubs: Canned Behavior Replacement

A stub completely replaces a function’s implementation to provide predetermined (canned) responses, effectively preventing the execution of real side effects like network requests or database writes.

  • Structural Role: State substitution and flow control.
  • Implementation: The original code is bypassed entirely. The stub returns fixed values, resolves specific promises, or deliberately throws errors based on test setup.
  • Verification Style: Indirect state verification. Stubs are generally used to drive the system under test through specific conditional branches rather than to verify that the stub itself was called.
// Example using Sinon.js
const database = {
  getUser: (id) => { /* real DB query */ },
};

// Structural replacement: original implementation is severed
sinon.stub(database, 'getUser').resolves({ id: 1, name: 'Alice' });

const user = await database.getUser(1);
// Verifying the outcome based on the stub's canned state
assert.strictEqual(user.name, 'Alice');

3. Mocks: Contract and Expectation Enforcement

A mock is a pre-programmed double that combines implementation replacement with built-in behavioral verification. Unlike stubs, which passively respond, mocks are defined with strict expectations regarding how they must be called.

  • Structural Role: Interaction contract verification.
  • Implementation: The mock replaces the real object and specifies both the canned response and the expected interaction criteria (call counts, argument matches, order of execution) before the code runs.
  • Verification Style: Pre-execution specification with lifecycle verification. The test runner verifies the mock’s expectations automatically, failing if the interaction contract was violated during execution.
// Conceptual representation (Sinon.js mock style)
const mailer = {
  sendWelcomeEmail: (email) => { /* real mail server */ },
};

const mockMailer = sinon.mock(mailer);

// Define structural expectation before running the test
mockMailer
  .expects('sendWelcomeEmail')
  .once()
  .withExactArgs('user@example.com');

// Code under test runs
mailer.sendWelcomeEmail('user@example.com');

// Verification checks that the contract was strictly fulfilled
mockMailer.verify();

Structural Comparison Summary

Attribute Spy Stub Mock
Original Code Executes Yes (by default) No No
Primary Purpose Observe and record calls Provide canned answers Enforce interaction contracts
Assertion Location After the action executes Tested on the consumer's state Configured before execution
Failure Mode Assertion fails at test end Logic error in consumer Expectation fails during verification
Primary Test Target Behavior / Usage tracking State / Conditional branches Structural protocol between objects

Understanding these structural boundaries prevents brittle tests. Use spies when you need to confirm that a real subsystem was triggered, stubs when you need to bypass slow or non-deterministic code, and mocks when the precise communication protocol between objects is the primary requirement of the test.
