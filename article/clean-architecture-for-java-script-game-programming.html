Clean Architecture for JavaScript Game Programming

Applying clean architecture to JavaScript game development creates a strict boundary between low-level technical infrastructure—such as WebGL rendering, Web Audio, and DOM events—and pure gameplay mechanics. By enforcing an inward-pointing dependency rule, developers ensure that domain logic remains independent of third-party frameworks and platform-specific APIs. This overview explores how structuring game logic, boundary interfaces, and engine infrastructure leads to modular codebases that support headless server simulation, automated unit testing, and framework-agnostic rendering.

The Core Problem: Tight Coupling in Web Games

In standard JavaScript game development, game mechanics are frequently entangled with browser APIs or specific libraries such as PixiJS, Phaser, or Three.js. When a player entity directly references a canvas context to draw a sprite, or checks browser keyboard events directly within a combat calculation, the game logic becomes impossible to run without a browser environment. This coupling prevents unit testing in pure Node.js environments and complicates running authoritative multiplayer servers, where graphics and user input hardware are nonexistent.

The Dependency Rule in Game Systems

Clean architecture resolves this by enforcing the Dependency Rule: inner layers know nothing about outer layers. In game development, the layers are arranged concentrically:

  1. Domain Entities: Pure JavaScript objects and state machines containing the fundamental game data (e.g., player health, inventory state, coordinate math, spatial grids).
  2. Game Rules / Use Cases: Orchestration logic determining actions and outcomes (e.g., calculating damage, leveling up, pathfinding, validating movement).
  3. Interface Adapters: Translators that convert raw engine data into domain-friendly formats and vice versa (e.g., mapping keyboard state to abstract game intents, mapping spatial vectors to renderable scene graphs).
  4. Infrastructure / Engine Core: Platform-dependent code including Canvas 2D/WebGL rendering loops, WebSockets, LocalStorage, Web Audio API, and DOM listeners.

Under this model, the inner layers (Entities and Game Rules) never import or reference modules from the outer layers (Infrastructure).

Defining Boundaries with Interfaces and Inversion of Control

Because JavaScript lacks native interface types, developers rely on TypeScript interfaces, abstract classes, or structural typing (duck typing) to establish contracts between layers.

Instead of game logic pushing visual data directly to a screen, the core logic interacts with an abstract boundary:

// Game Core Boundary (Port)
class RenderPort {
  drawEntity(id, x, y, rotation) {
    throw new Error("Method not implemented.");
  }
}

// Infrastructure Implementation (Adapter)
class PixiRenderAdapter extends RenderPort {
  constructor(stage, spriteLibrary) {
    super();
    this.stage = stage;
    this.sprites = spriteLibrary;
  }

  drawEntity(id, x, y, rotation) {
    const sprite = this.sprites.get(id);
    sprite.x = x;
    sprite.y = y;
    sprite.rotation = rotation;
  }
}

By injecting this adapter into the game loop using Inversion of Control (IoC), the game logic updates spatial positions and notifies the port without requiring knowledge of textures, shaders, or rendering libraries.

Separating Input from Intent

Clean architecture dictates that player input should be normalized before it reaches game rules. The browser's keydown or pointerdown events belong to the outermost infrastructure layer.

An input adapter translates these raw events into abstract domain commands, such as MOVE_LEFT, JUMP, or USE_SKILL. The core game rules process these commands purely as state transformations. Consequently, input can originate from a keyboard, a virtual mobile joystick, an automated AI agent, or a network packet from a remote client without altering a single line of gameplay code.

Decoupling the Game Loop and State Updates

A standard game loop consists of processing input, updating world state, and rendering frames. Clean architecture splits this tick into deterministic state updates and non-deterministic visual interpolations:

  • Domain Update Loop: Executes on a fixed time step (e.g., 60 updates per second) using pure functions or strict mutation patterns to update domain entities. It relies exclusively on numerical logic and data structures.
  • Engine Render Loop: Operates on requestAnimationFrame. It queries the current domain state, interpolates between the previous and current state frames, and draws the result.

This separation ensures that game physics and rules are completely detached from frame rate variations and GPU constraints.

Practical Benefits of the Architecture

  • Headless Execution: The entire game simulation can execute in a Node.js worker thread or on an authoritative backend server without mocking browser APIs like window, document, or WebGL contexts.
  • Rapid Automated Testing: Unit tests can verify complex mechanics—such as combat calculations or inventory limits—in milliseconds using standard runners like Vitest or Jest, without instantiating mock canvases.
  • Engine Portability: Migrating a game from a 2D Canvas renderer to a 3D WebGL framework requires replacing only the outer infrastructure adapters, leaving all core rules, progression systems, and entity behaviors intact.
