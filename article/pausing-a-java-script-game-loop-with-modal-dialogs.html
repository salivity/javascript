Pausing a JavaScript Game Loop with Modal Dialogs

Freezing a game loop when opening a modal pause dialog requires managing application state, isolating input, and properly handling elapsed time so that gameplay does not violently jump forward upon resuming. This article explores how JavaScript developers correctly implement pause functionality using state flags, decoupled delta timing, and modern requestAnimationFrame patterns without breaking UI animations or game physics.

The Dual Architecture of Pausing

In JavaScript game development, pausing is rarely as simple as stopping the loop entirely. A game must stop updating dynamic entities (player positions, physics, AI) while often continuing to render the screen, listen for user interface events, or even run animated background shaders behind the modal.

There are two primary methods to implement a pause:

  1. Hard Freeze (cancelAnimationFrame): Canceling the loop completely stops execution. While resource-efficient, it prevents any in-game UI animations or animated pause menus from rendering via the canvas.
  2. Soft Pause (State Flagging): The requestAnimationFrame loop continues to execute, but updates to game entities are skipped based on an internal boolean state. This is the industry-standard approach.

Handling the Delta Time Jump

The most critical bug encountered when pausing via a modal dialog is the delta time accumulator bug.

Most modern game engines calculate physics and movements using delta time (\(\Delta t\)), which is the difference between the current frame's timestamp and the previous frame's timestamp:

let delta = (currentTime - lastTime) / 1000;

If a player opens a modal for ten seconds, currentTime - lastTime will equal 10,000 milliseconds when the loop resumes. If passed directly into the update loop, physics calculations will attempt to simulate ten seconds in a single step, resulting in collision clipping, disappearing objects, or instant game-overs.

To freeze the loop correctly, lastTime must be updated immediately upon unpausing before running the logic step, or \(\Delta t\) must be clamped.

Proper Delta Reset Implementation

let isPaused = false;
let lastTime = performance.now();

function togglePause(paused) {
  isPaused = paused;
  if (!isPaused) {
    // Reset lastTime to prevent a massive delta spike upon unpausing
    lastTime = performance.now();
  }
}

Structuring the Paused Loop

A resilient game loop separates the Update logic from the Render logic. When a modal opens, update logic is gated behind the pause flag, while rendering either persists the previous state or draws the modal overlay.

function gameLoop(currentTime) {
  const delta = (currentTime - lastTime) / 1000;
  lastTime = currentTime;

  if (!isPaused) {
    // Run game physics, inputs, AI, and world updates
    updateGame(delta);
  } else {
    // Optionally update pause menu animations or UI transitions
    updateModal(delta);
  }

  // Render the scene
  renderGame();
  
  if (isPaused) {
    renderPauseOverlay();
  }

  requestAnimationFrame(gameLoop);
}

Input Isolation and Focus Management

When a modal dialog is active, gameplay inputs must be suppressed so that pressing directional keys or action buttons inside the dialog does not trigger in-game events.

  • DOM Modals: If using HTML <dialog> or overlay elements, call event.stopPropagation() on UI interactions or remove the game canvas event listeners while the modal is open.
  • Canvas-based Modals: Switch the input controller's internal state machine from GAMEPLAY_STATE to UI_STATE, ensuring that keystrokes route only to the menu navigation handlers.

By keeping the animation frame loop running, resetting timestamps on unpause, and decoupling the update step from the render step, modal pause dialogs halt game execution predictably and reliably.
