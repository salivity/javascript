How React Hook Rules Prevent State Corruption

React hooks rely on a predictable execution order rather than unique identifiers to track component state across re-renders. Under the hood, React stores each hook's state in an ordered, index-based linked list attached to the component's Fiber node. Adhering to the Rules of Hooks—specifically calling them only at the top level and strictly within React functional components—guarantees that hooks execute in the exact same sequence on every render, preventing mismatched data, corrupted state, and unpredictable runtime crashes.

The Internal Mechanism: Ordered Linked Lists

Unlike traditional object-oriented state containers, hooks like useState and useEffect do not receive unique keys or names to identify which slice of state belongs to them. Instead, React maintains an internal singly linked list on the component's Fiber node, tracked via the memoizedState property.

When a component renders for the first time, React creates a node in this list for every hook encountered in the execution flow. During subsequent renders, React initializes an internal cursor at the head of the list. Each time a hook runs, React reads the current node's value, performs any necessary updates, and advances the cursor to the next node (workInProgressHook.next).

Why the Top-Level Rule Matters

The primary rule of hooks dictates that they must never be invoked inside loops, conditions, or nested functions. Because React relies solely on the invocation order to match each hook call to its corresponding node in the memoizedState list, any alteration in that order breaks the cursor tracking.

Consider a component with three hooks:

  1. useState(false) (Authentication state)
  2. useState('dark') (Theme state, wrapped incorrectly inside an if statement)
  3. useEffect(...) (Data fetching logic)

If the condition for the second hook evaluates to true on the initial render, the linked list creates three consecutive nodes. If the condition becomes false on a subsequent render, the second hook is skipped. When React encounters the third hook (useEffect), the internal pointer has only advanced to the second position in the list. React incorrectly assigns the data and handlers of the third hook to the second node's slot.

This index mismatch causes immediate state corruption:

  • State setters update the wrong variables.
  • Effect cleanups receive mismatched dependencies, leading to memory leaks or infinite fetch loops.
  • Type mismatches trigger fatal runtime exceptions when a hook expects an object or function but receives a primitive from a misaligned state slot.

Confining Hooks to React Functions

The secondary rule restricts hook calls exclusively to React functional components and custom hooks. Hooks rely on an active execution context set up by the React reconciler immediately before a component renders.

Invoking a hook inside a standard JavaScript function or outside the render lifecycle means the global dispatcher pointer (ReactCurrentDispatcher.current) is unset or points to an invalid context. This immediately throws an error ("Hooks can only be called inside the body of a function component") rather than silently corrupting memory.

Compile-Time Enforcement

To safeguard runtime integrity, React enforces these structural rules through the eslint-plugin-react-hooks package. The linter statically analyzes the Abstract Syntax Tree (AST) of the code to detect conditional hook invocations, early returns that precede hook declarations, or calls from non-component functions. By catching order-dependent anomalies prior to bundling, the rules preserve the deterministic execution model that makes React's functional state management predictable and safe.
