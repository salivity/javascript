JS Private Static vs Instance Fields and Methods

Modern JavaScript classes use the # hash prefix to enforce true encapsulation, but private static members and private instance members serve distinct architectural purposes. While both prevent access from outside the class declaration, they differ fundamentally in their ownership, memory allocation, and access contexts. Private static fields and methods belong exclusively to the class constructor itself, whereas private instance fields and methods are tied to individual object instances created with the new keyword.

Scope and Ownership

The primary distinction between private static and private instance members is who owns them:

  • Private Instance Fields and Methods: Belong to individual class instances. Each new instance created via new ClassName() gets its own separate copy of private instance fields. They represent the internal, hidden state of an object.
  • Private Static Fields and Methods: Belong directly to the class constructor function. They are evaluated once when the class definition is executed, meaning there is only ever one shared copy regardless of how many instances are created.
class Tracker {
  // Private static field: shared across the class
  static #totalCount = 0;

  // Private instance field: unique to each instance
  #id;

  constructor(id) {
    this.#id = id;
    Tracker.#incrementTotal();
  }

  // Private static method
  static #incrementTotal() {
    Tracker.#totalCount++;
  }

  static getTotalCount() {
    return Tracker.#totalCount;
  }

  // Private instance method
  #formatId() {
    return `ID: ${this.#id}`;
  }

  display() {
    return this.#formatId();
  }
}

Memory and Lifecycle

Private instance members are allocated every time an instance is initialized. If you instantiate one thousand objects, one thousand separate sets of private instance fields are allocated in memory. Their lifecycle is bound to their respective instance and they are garbage-collected when that instance goes out of scope.

Private static members are allocated once when the class is evaluated and persist as long as the class constructor itself remains in memory. This makes private static fields ideal for tracking shared caches, maintaining global instance counters, or storing fixed internal constants that instances should not duplicate.

Access Context and this Resolution

Access rules inside the class body depend on the execution context:

  • Accessing Instance Private Members: These must be invoked on an instance reference, typically this (e.g., this.#privateField or this.#privateMethod()). Calling them without an instance or from a static method without passing an instance will throw a TypeError.
  • Accessing Static Private Members: These are typically accessed using the class name itself within the class body (e.g., ClassName.#staticMethod()) or through this inside static methods where this refers to the class constructor. An instance cannot access a static private field using this.#staticField.
class Example {
  static #sharedData = "Class-level secret";
  #instanceData = "Instance-level secret";

  static testAccess(instance) {
    // Valid: static accessing static
    console.log(Example.#sharedData);

    // Valid: static accessing instance private member via an explicit instance reference
    console.log(instance.#instanceData);
  }

  run() {
    // Valid: instance accessing static via class name
    console.log(Example.#sharedData);

    // TypeError: static private members cannot be called via 'this' in instance context
    // console.log(this.#sharedData);
  }
}

Practical Use Cases

  • Use Private Instance Members for validating internal object state, hiding sensitive operational details (such as database connection handles for a specific client), and writing helper methods that directly mutate or read an instance's properties.
  • Use Private Static Members for class-wide utility functions, internal factory methods, configuration parameters, and shared caches that do not rely on individual instance states.
