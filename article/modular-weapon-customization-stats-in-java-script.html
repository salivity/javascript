Modular Weapon Customization Stats in JavaScript

Modular weapon customization systems dynamically alter gameplay by recalculating weapon attributes and player capabilities whenever components like scopes, barrels, or magazines are modified. In JavaScript game programming, this is achieved through data-driven object composition, where base weapon templates combine with attachment modifiers to produce composite values that feed directly into the player's core stat calculation pipeline. By utilizing aggregate modifier chains, observer patterns, or reactive stat systems, developers can ensure that any equipment change immediately and accurately updates player performance without sacrificing execution speed.

Data Modeling: Base Stats and Modifiers

To build a modular system, weapons and attachments should be represented as decoupled data structures. A weapon holds base stats and a collection of available slots, while attachments provide specific additive or multiplicative modifiers.

const baseRifle = {
  id: "assault_rifle_01",
  name: "Standard Rifle",
  baseStats: {
    damage: 30,
    fireRate: 600, // rounds per minute
    handling: 50,
    weight: 3.5 // in kg
  },
  slots: {
    barrel: null,
    optic: null,
    magazine: null
  }
};

const heavyBarrel = {
  id: "barrel_heavy",
  name: "Heavy Barrel",
  modifiers: {
    damage: { type: "flat", value: 5 },
    handling: { type: "percent", value: -0.10 },
    weight: { type: "flat", value: 0.8 }
  }
};

The Calculation Pipeline

Stats should not be permanently mutated on the base object. Instead, calculate effective weapon stats dynamically by running the base values through all active attachment modifiers.

The evaluation typically processes flat modifiers first, followed by percentage modifiers, or aggregates them using a standard reducer pattern:

function calculateWeaponStats(weapon) {
  const finalStats = { ...weapon.baseStats };
  const attachments = Object.values(weapon.slots).filter(Boolean);

  // Group modifiers
  attachments.forEach(attachment => {
    for (const [stat, mod] of Object.entries(attachment.modifiers)) {
      if (finalStats[stat] !== undefined) {
        if (mod.type === "flat") {
          finalStats[stat] += mod.value;
        } else if (mod.type === "percent") {
          finalStats[stat] *= (1 + mod.value);
        }
      }
    }
  });

  return finalStats;
}

Propagating Weapon Stats to the Player

The player entity maintains aggregate stats influenced by their baseline attributes, equipped armor, inventory weight, and the currently active weapon. When an attachment is equipped or removed, the player’s overall stats must reflect the changes—such as higher weapon weight lowering movement speed, or improved handling increasing aim-down-sights (ADS) transition rate.

This connection is best managed via an event-driven approach or explicit recalculation call:

class Player {
  constructor(name) {
    this.name = name;
    this.baseSpeed = 5.0; // meters per second
    this.equippedWeapon = null;
    
    // Derived stats
    this.currentStats = {
      movementSpeed: this.baseSpeed,
      attackPower: 0,
      handlingSpeed: 1.0
    };
  }

  equipAttachment(slot, attachment) {
    if (!this.equippedWeapon || !this.equippedWeapon.slots.hasOwnProperty(slot)) {
      return;
    }

    this.equippedWeapon.slots[slot] = attachment;
    this.updateStats();
  }

  updateStats() {
    if (!this.equippedWeapon) return;

    const weaponStats = calculateWeaponStats(this.equippedWeapon);

    // Apply weapon weight penalties to player movement
    const weightPenalty = weaponStats.weight * 0.1;
    this.currentStats.movementSpeed = Math.max(1.0, this.baseSpeed - weightPenalty);

    // Map weapon outputs to player capabilities
    this.currentStats.attackPower = weaponStats.damage;
    this.currentStats.handlingSpeed = weaponStats.handling / 50; // normalized multiplier
  }
}

Performance Optimization with Dirty Flags

In JavaScript game engines, recalculating nested objects during high-frequency loop cycles (such as inside a requestAnimationFrame render or tick loop) causes unnecessary garbage collection and CPU overhead.

To optimize:

  1. Mark as Dirty: Set an isDirty flag to true whenever an attachment is equipped, unequipped, or swapped.
  2. Batch Updates: Defer stat recalculations until the start of the next physics or logic frame, checking if (player.isDirty) { player.updateStats(); player.isDirty = false; }.
  3. Cache Outputs: Keep the calculated composite object in memory and read from the cache for combat logic, physics calculations, and HUD rendering until another modification occurs.
