How IndexedDB autoIncrement Works with Key Paths

In JavaScript IndexedDB, combining autoIncrement: true with a specified keyPath creates an in-line key generator that automatically assigns sequential numeric identifiers directly to stored objects. This mechanism ensures that records maintain a unique primary key within their own object structure without requiring manual ID generation. When an object lacks the designated key path property, the database generates a value and injects it into the object; when a key is manually provided, the system respects the manual key and adjusts its internal counter accordingly.

In-Line Key Generation and Property Injection

When an object store is initialized with both a keyPath (such as 'id') and autoIncrement: true, the primary key is stored "in-line." When you execute an add() or put() operation with an object that does not contain the specified key path property (or where the property is set to undefined), the IndexedDB engine evaluates the key generator sequence.

The engine takes the next available integer from its internal counter, injects this value directly into the object under the specified property name, and persists the modified object into the store. As a result, the object retrieved in subsequent queries will contain the newly generated property and value.

Handling Manually Supplied Keys

If an object explicitly contains a valid key at the keyPath location upon insertion, the auto-increment mechanism behaves differently:

  1. Key Retention: The engine accepts the user-defined key and inserts the record without generating a replacement.
  2. Generator Adjustment: If the manually provided key is a number greater than the current value of the internal auto-increment counter, the generator updates its counter to match this higher value. The next auto-generated key will be Math.floor(highestKey) + 1.
  3. Ignored Non-Numeric Values: If the manual key is a non-numeric valid key (such as a string or Date), the record is stored using that key, but the numeric auto-increment counter remains unchanged.

Generator State and Lifecycle

Each object store maintains its own dedicated key generator counter that begins at 1. The counter tracks the highest positive integer used as a key in that store. The sequence strictly produces positive integers and does not reuse numbers if a record is deleted. Furthermore, the counter persists across browser restarts and database connections.

Constraints and Edge Cases

  • Compound Keys: IndexedDB does not allow autoIncrement: true to be paired with an array-based compound keyPath (such as keyPath: ['userId', 'orderId']). Attempting to create an object store with this configuration throws an InvalidAccessError.
  • Nested Key Paths: Dotted key paths (such as keyPath: 'meta.id') are supported. If the parent object (meta) exists, IndexedDB injects the generated integer into meta.id. If the parent path does not exist, the engine creates the intermediate object structure to assign the generated key.
  • Frozen or Sealed Objects: If an object passed to add() is frozen via Object.freeze() and lacks the key path property, the engine will fail to inject the generated key, resulting in a transaction failure.
