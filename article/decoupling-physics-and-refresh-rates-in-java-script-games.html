Decoupling Physics and Refresh Rates in JavaScript Games

Decoupling the physics update frequency from the display refresh rate is an essential architectural practice in modern JavaScript game development. Relying on the browser’s render cycle to advance game mechanics leads to erratic simulations, game-breaking bugs, and inconsistent difficulty across different hardware. By separating the simulation into a deterministic, fixed-interval timestep while allowing rendering to occur as fast as the monitor allows, developers ensure stable physics, fair gameplay, and smooth visual performance across diverse devices ranging from 60Hz mobile screens to 240Hz gaming monitors.

The Flaw of Coupling Physics to Display Rates

In JavaScript, visual updates are traditionally driven by requestAnimationFrame, a native API designed to synchronize draw calls with the user's monitor refresh rate. When developers advance physics calculations inside this loop using the elapsed time (delta time) between frames, problems immediately emerge:

  • Hardware Dependency: A monitor running at 144Hz executes the update loop 2.4 times more frequently than a standard 60Hz monitor. Without a decoupled architecture, calculations behave differently on each display.
  • Physics Tunneling: When frame rates drop drastically—often caused by background garbage collection or heavy tab processing—the delta time spikes. A fast-moving projectile or falling character may jump past collision boundaries entirely in a single frame.
  • Non-Deterministic Calculations: Numeric integrators (such as Euler or Verlet) commonly used in 2D and 3D physics engines produce varying results depending on the step size. Inconsistent step sizes make jumping heights, acceleration, and friction behave unpredictably.

The Fixed Timestep and Accumulator Solution

The standard solution to this problem is implementing a fixed timestep loop alongside an accumulator inside the render loop.

Instead of passing the raw elapsed time directly to the physics engine, the engine tracks the accumulated time that has passed since the last render frame. The physics simulation then consumes this time in strict, identical chunks (such as 1/60th of a second, or approximately 16.6 milliseconds):

  1. Calculate Delta Time: Measure the time elapsed since the previous requestAnimationFrame call.
  2. Accumulate Time: Add this elapsed time to an accumulator variable.
  3. Run Fixed Steps: While the accumulator is greater than or equal to the designated fixed step, advance the physics state by that exact fixed increment and subtract the step time from the accumulator.
  4. Render: Draw the game world once the simulation catches up.

To prevent the "spiral of death"—where physics updates take longer to compute than the fixed step itself, causing the game to freeze—developers cap the maximum number of simulation steps that can run per render frame.

Preserving Visual Fluidity with Interpolation

A common side effect of running physics at a fixed rate (e.g., 60Hz) on a high-refresh monitor (e.g., 120Hz or 144Hz) is visual jitter or micro-stuttering. Because render frames occur between physics ticks, the rendered object positions can appear slightly behind the display's expected smooth path.

Decoupling solves this through state interpolation. By storing the previous and current transforms of every dynamic object, the renderer can calculate an alpha value representing the remaining time in the accumulator divided by the fixed timestep:

alpha = accumulator / fixedTimeStep

The render engine then linearly interpolates between the previous position and the current position using this fraction, achieving high-frame-rate rendering without sacrificing the integrity of the underlying fixed-rate simulation.

Determinism and Multiplayer Synchronization

Decoupled physics is indispensable for multiplayer games, replay systems, and platformers requiring pixel-perfect mechanics. When the simulation always updates at a steady rate:

  • Client-side prediction and server reconciliation function reliably because both the client and server simulate game rules using matching fixed increments.
  • Ghost runs in time-attack games and recorded inputs replay identically on any machine regardless of performance drops.
  • Game rules remain identical regardless of whether the player is running the game on a high-end desktop or an underpowered mobile browser.
