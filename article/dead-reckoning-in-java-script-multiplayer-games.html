Dead Reckoning in JavaScript Multiplayer Games

Dead reckoning is an algorithmic technique used in multiplayer network programming to predict the movement and position of remote entities between network updates or during network latency and packet loss. Instead of waiting for the authoritative server to send the position of an entity on every single frame, the local client extrapolates the entity's current position using its last known state, including coordinates, velocity, and sometimes acceleration. This article explains how dead reckoning functions, how it compensates for missing data during packet loss, and how to implement it effectively within a JavaScript game engine.

The Mechanics of Dead Reckoning

In multiplayer games, sending continuous position updates over WebSockets or WebRTC for every entity at 60 frames per second consumes unsustainable bandwidth. Instead, servers send updates at a lower tick rate, such as 10 to 20 times per second.

Under ideal network conditions, a client can smoothly interpolate between two previously received states. However, interpolation introduces artificial latency because the client is always rendering past states. Dead reckoning, by contrast, is an extrapolation technique. It uses physics calculations to guess where the entity is right now in real time:

\[\text{Position}_{\text{current}} = \text{Position}_{\text{last}} + (\text{Velocity}_{\text{last}} \times \Delta t)\]

If the remote entity is also accelerating or turning, the formula incorporates acceleration (\(\frac{1}{2} a \Delta t^2\)) and angular velocity.

Mitigating Packet Loss

Packet loss occurs when UDP packets (via WebRTC data channels) or WebSocket frames are dropped or delayed by network congestion. Without dead reckoning, missing a position packet causes the remote entity to either freeze abruptly or teleport across the screen when the next packet eventually arrives.

When a packet drops, dead reckoning treats the missing update as a continuation of the entity's previous trajectory. The client measures the elapsed time (\(\Delta t\)) since the last confirmed packet and advances the entity's coordinates along its last known velocity vector. Even if multiple consecutive packets fail to arrive, the entity continues moving realistically along its projected path, preserving visual fluidity for the player.

Reconciling Prediction Errors

Because player input is unpredictable, an entity might turn or stop during a period of packet loss. When the next authoritative packet finally arrives from the server, the client's extrapolated position will often diverge from the true position.

Snapping the entity immediately to the true position causes visual stuttering. To resolve this, developers use client-side reconciliation via Linear Interpolation (Lerp). Instead of instantly adopting the new coordinates, the client smoothly blends the dead-reckoned position toward the authoritative position over a brief correction window (typically 50 to 100 milliseconds).

// Linear interpolation helper
function lerp(start, end, alpha) {
    return start + (end - start) * alpha;
}

Implementing Dead Reckoning in JavaScript

In a JavaScript game environment using requestAnimationFrame, dead reckoning relies on high-resolution timestamps via performance.now() to calculate accurate time deltas.

Here is a typical implementation pattern for a remote entity in JavaScript:

class RemoteEntity {
    constructor() {
        // Last authoritative state from the server
        this.serverPosition = { x: 0, y: 0 };
        this.serverVelocity = { x: 0, y: 0 };
        this.lastUpdateTime = performance.now();

        // Rendered position on screen
        this.renderPosition = { x: 0, y: 0 };
    }

    // Called whenever a network packet arrives
    onServerUpdate(data) {
        this.serverPosition.x = data.x;
        this.serverPosition.y = data.y;
        this.serverVelocity.x = data.vx;
        this.serverVelocity.y = data.vy;
        this.lastUpdateTime = performance.now();
    }

    // Called on every local frame update
    update(currentTime) {
        // Calculate time elapsed since last server packet (in seconds)
        const dt = (currentTime - this.lastUpdateTime) / 1000;

        // Extrapolate expected position based on velocity (Dead Reckoning)
        const deadReckonedX = this.serverPosition.x + (this.serverVelocity.x * dt);
        const deadReckonedY = this.serverPosition.y + (this.serverVelocity.y * dt);

        // Smoothly blend the current rendered position toward the predicted position
        const smoothingFactor = 0.15;
        this.renderPosition.x = lerp(this.renderPosition.x, deadReckonedX, smoothingFactor);
        this.renderPosition.y = lerp(this.renderPosition.y, deadReckonedY, smoothingFactor);
    }
}

Limitations and Best Practices

While dead reckoning hides minor network hiccups, extrapolation degrades over extended durations of packet loss. If no packets arrive for a second or more, entities will continue flying through walls or off cliffs.

To mitigate this, implement a decay threshold: if the time since the last packet exceeds a defined limit (e.g., 500 milliseconds), gradually reduce the velocity to zero. This halts the entity naturally until reliable network communication is re-established.
