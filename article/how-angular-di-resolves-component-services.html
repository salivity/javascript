How Angular DI Resolves Component Services

Angular's Dependency Injection (DI) system is a hierarchical framework responsible for creating and delivering dependent objects to classes across an application. In JavaScript, the DI container resolves a component's services by inspecting compiled metadata, traversing a dual-tree injector hierarchy (ElementInjector and EnvironmentInjector), and instantiating or reusing service instances based on where and how they are provided.

Compilation and Dependency Metadata

During compilation under Angular's Ivy engine, TypeScript source code is transformed into plain JavaScript that includes static definitions. For a component, the compiler generates a factory function (ɵfac) and a component definition (ɵcmp).

The constructor's parameter types are converted into injection tokens. When Angular instantiates a component, its factory function invokes internal DI lookup methods (such as ɵɵdirectiveInject), passing the token associated with each requested service.

The Dual Injector Hierarchy

When resolving a service token, Angular searches through two distinct injector hierarchies:

  1. ElementInjector Hierarchy: Created implicitly at each DOM element where a component or directive is applied. If a component defines a service in its providers or viewProviders array, that instance belongs to its local ElementInjector.
  2. EnvironmentInjector Hierarchy: Configured at the module or application level. This includes providedIn: 'root', platform injectors, and legacy NgModule providers.

The Resolution Algorithm

When a component requests a service via its constructor, the DI container performs the following step-by-step resolution process:

  1. Current ElementInjector: The container first checks the ElementInjector attached to the requesting component's DOM element. If the service is listed in the component's providers or viewProviders, the container returns the existing instance or instantiates a new one if it has not yet been created.
  2. Parent ElementInjectors: If the token is not provided at the local level, the search bubbles up through the parent component nodes in the DOM tree, checking each parent's ElementInjector.
  3. EnvironmentInjector (Root Level): If the resolution reaches the top of the element tree without finding the provider, the search shifts to the EnvironmentInjector hierarchy. It checks the application root (AppModule or provideHttpClient/providedIn: 'root') and platform-level injectors.
  4. NullInjector: If the token is not found in either hierarchy, the search ends at the NullInjector. Unless marked otherwise, Angular throws a NullInjectorError.

Resolution Modifiers

Angular provides resolution modifiers that alter how the DI container walks the hierarchy:

  • @Optional(): Prevents throwing an error if the service is not found, returning null instead.
  • @Self(): Restricts the lookup exclusively to the local component’s ElementInjector.
  • @SkipSelf(): Skips the local ElementInjector and starts the search directly at the parent element.
  • @Host(): Limits the search up to the host component that renders the current template or directive.

Through this combination of compiled static properties, hierarchical injector trees, and resolution modifiers, Angular resolves component services efficiently while maintaining flexible scoping across the application lifecycle.
