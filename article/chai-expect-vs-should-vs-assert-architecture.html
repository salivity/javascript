Chai Expect vs Should vs Assert Architecture

The Chai assertion library for JavaScript provides three distinct interfaces—assert, expect, and should—each built on different architectural patterns. While assert adheres to the traditional, functional Test-Driven Development (TDD) model, expect and should implement Behavior-Driven Development (BDD) paradigms using chainable Domain-Specific Languages (DSLs). The core technical distinctions among them lie in how they interact with JavaScript's object model: assert relies on static functional calls, expect wraps values inside custom instances, and should mutates the global prototype chain.

The Core Engine: Chai's Assertion Prototype and Flags

To understand the differences, it helps to understand how Chai works internally. Chai provides an underlying Assertion constructor that manages assertions.

When BDD styles (expect and should) chain words together (such as .to.be.a), they use property getters registered on Chai's prototype via Object.defineProperty. Instead of executing immediate logic, intermediary words set internal key-value pairs called "flags" on the assertion instance (for example, setting the negate flag to true when encountering .not). When a terminating assertion method or property is invoked (like .equal()), the engine inspects these accumulated flags to evaluate the condition and generate appropriate error messages.

1. The assert Style: Classical and Unobtrusive

The assert interface mirrors the standard Node.js assert module while offering an expanded set of comparison utilities.

Architectural Characteristics:

  • No Prototype Pollution: assert does not modify Object.prototype or wrap target values in intermediary objects.
  • Direct Function Invocation: Assertions are made through explicit method calls passing the target and expected values as arguments: assert.equal(actual, expected).
  • Explicit Handling: Because it does not rely on calling properties on the target, evaluating null, undefined, or undeclared properties causes no immediate runtime syntax errors.
  • Separation of Concerns: The tested value remains completely decoupled from the assertion framework.

2. The expect Style: Instance Wrapping

The expect interface is a BDD-style interface that provides natural language chaining without altering native JavaScript prototypes.

Architectural Characteristics:

  • Wrapper Factory: Invoking expect(target) acts as a constructor/factory call that instantiates a new Chai Assertion object. The target value is stored as an internal reference within that instance.
  • Safe Null/Undefined Testing: Because expect passes the subject as an argument rather than resolving a property on the subject, statements like expect(null).to.be.null or expect(undefined).to.not.exist execute safely.
  • Browser and Environment Isolation: It leaves native global prototypes untouched, making it ideal for environments where prototype modification is strictly prohibited or could conflict with third-party code.
  • Memory Footprint: Each call constructs a distinct Assertion instance, discarding it after execution.
// expect architecture: creates a wrapper around the value
expect(foo).to.be.a('string');

3. The should Style: Prototype Extension

The should interface provides a fluent BDD syntax that allows assertions to be read directly from the object being tested.

Architectural Characteristics:

  • Object.prototype Mutation: Executing chai.should() extends Object.prototype by defining a dynamic getter named should.
  • Self-Referential Wrapping: When .should is accessed on an expression (foo.should), the getter retrieves this and automatically instantiates and returns a Chai Assertion instance wrapping this.
  • The Null/Undefined Limitation: Because null and undefined do not inherit from Object.prototype, attempting null.should results in a native JavaScript TypeError: Cannot read properties of null (reading 'should').
  • Fallback Mechanisms: To compensate for this structural limitation, Chai exposes static helpers on the initialized function: should.exist(val), should.not.exist(val), or should.Throw().
// should architecture: resolves .should through prototype inheritance
chai.should();
foo.should.be.a('string');

// Required workaround for null values
should.not.exist(bar);

Summary

Architecturally, assert is a pure utility library that operates on arguments without side effects. expect balances fluent BDD chaining with clean scope isolation by encapsulating target values within newly allocated assertion instances. should prioritizes fluent, readable syntax by extending JavaScript's root prototype, trading isolation and seamless null handling for continuous left-to-right readability.
