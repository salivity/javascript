Component Composition vs Classical Inheritance in JS Games

In modular JavaScript game programming, choosing the right architecture for game entities determines how easily a codebase can scale, adapt, and maintain performance. This article examines the core differences between classical inheritance—a hierarchical "is-a" modeling approach—and component composition—a modular "has-a" pattern. By contrasting how both paradigms handle code reuse, state mutation, and structural changes, you will understand why modern game development heavily favors composition over traditional class hierarchies.

Classical Inheritance: The Hierarchical Model

Classical inheritance organizes game objects into a top-down, strict taxonomy using ES6 class and extends keywords (or prototypes underneath). Entities inherit behaviors and properties from parent classes, forming an "is-a" relationship.

For example, a game might structure entities like this:

  • Entity
    • Actor extends Entity
      • Player extends Actor
      • Enemy extends Actor
        • FlyingEnemy extends Enemy

The Pitfalls in Game Development

  1. The Fragile Base Class Problem: Changes made to a top-level class like Entity or Actor inevitably ripple down the hierarchy, risking unintended side effects in subclasses.
  2. The "Gorilla/Banana" Problem: Subclasses inherit everything the parent has, even if they only need a fraction of that functionality.
  3. Rigid Taxonomy: If design requirements change—for instance, requiring a FlyingPlayer or a non-living object that can fly and take damage (like a drone)—inheritance forces developers to either duplicate code, reorganize the entire tree, or create an overly complex multiple-inheritance workaround.

Component Composition: The Modular Model

Component composition builds game entities by assembling small, independent, and reusable modules of functionality. Instead of defining what an object is, composition defines what an object can do or possesses—a "has-a" relationship.

In JavaScript, this is typically implemented by instantiating a generic entity (often just a unique ID or a lightweight container) and attaching behavior modules or data components to it:

// Components
const canFly = (state) => ({
  fly: () => { state.y += state.speed; }
});

const canShoot = (state) => ({
  shoot: () => { /* spawn projectile */ }
});

// Entity Assembler
function createFlyingShooter(x, y) {
  const state = { x, y, speed: 5 };
  return Object.assign(state, canFly(state), canShoot(state));
}

This pattern also serves as the foundation for the Entity-Component-System (ECS) architecture, where:

  • Entities are simple identifiers.
  • Components are pure data bags (no methods).
  • Systems contain the logic that operates across all entities possessing specific components.

Key Differences

Feature Classical Inheritance Component Composition
Relationship "Is-a" (e.g., Orc is an Enemy) "Has-a" (e.g., Orc has Health, Renderable, AI)
Coupling High; tight coupling across hierarchy levels Low; components are decoupled and self-contained
Flexibility Low; changing mechanics requires refactoring base classes High; mechanics can be added or removed at runtime
Reusability Vertical; shared down specific branches Horizontal; shared across entirely unrelated entities
Complexity Increases rapidly as the entity count grows Remains flat and predictable as new mechanics are introduced

Performance and Runtime Behavior in JavaScript

JavaScript engines optimize based on object shape (hidden classes). Deep classical inheritance chains can sometimes lead to polymorphous access patterns if properties are dynamically added across multiple hierarchy levels.

Composition, especially when structured through an ECS approach, enables predictable data structures. While assembling objects with functional composition (Object.assign or object spread) can incur minor garbage collection overhead if done frequently in the game loop, doing so during initial object pooling completely eliminates this issue.

Conclusion: Which Pattern Fits Best?

Classical inheritance can be sufficient for simple, static domains with clear, unchanging taxonomies, such as basic UI components or engine-level abstractions.

However, for dynamic gameplay mechanics, component composition is the superior paradigm in modular JavaScript game programming. It accommodates rapid design iteration, prevents monolithic class bloat, and allows developers to assemble new game entities on the fly without breaking existing architectures.
