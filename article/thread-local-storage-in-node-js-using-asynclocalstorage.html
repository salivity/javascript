Thread-Local Storage in Node.js Using AsyncLocalStorage

This article explores how Node.js achieves thread-local storage capabilities in an asynchronous, single-threaded runtime using the built-in AsyncLocalStorage API. You will learn the mechanics behind Continuation-Local Storage (CLS), how Node.js tracks context across asynchronous boundaries, how to implement AsyncLocalStorage in your code, and the performance considerations to keep in mind.

In traditional multi-threaded runtimes like Java or C++, Thread-Local Storage (TLS) allows developers to attach state directly to a specific operating system thread. Any code executing on that thread can implicitly access that state without explicit parameter passing. Node.js, however, relies on a single-threaded event loop to handle concurrent operations. Because asynchronous tasks (such as database queries, file system I/O, and HTTP requests) interleave their execution on the same thread, standard thread-bound variables bleed across concurrent operations, rendering traditional TLS unusable.

To solve this, Node.js provides Continuation-Local Storage through the AsyncLocalStorage class, found within the node:async_hooks module. Rather than binding data to a physical thread, AsyncLocalStorage binds data to the execution context of an asynchronous control flow.

How AsyncLocalStorage Works Internally

Under the hood, AsyncLocalStorage is powered by the Node.js async_hooks engine. The runtime assigns an asynchronous ID (asyncId) to every asynchronous resource—such as Promises, timers, TCP connections, and file handles. When an asynchronous resource is initialized, the runtime captures the identifier of the execution context that created it (the triggerAsyncId).

Node.js maintains a graph of these parent-child relationships. When an execution context transitions through a callback, AsyncLocalStorage looks up the storage reference associated with the current context chain, allowing data to follow the logical path of execution rather than the physical thread.

Implementation and Core API

Using AsyncLocalStorage involves creating an instance, wrapping an execution flow with .run(), and querying the state anywhere down the call stack using .getStore().

import { AsyncLocalStorage } from 'node:async_hooks';

const asyncLocalStorage = new AsyncLocalStorage();

function logWithTraceId(message) {
  const store = asyncLocalStorage.getStore();
  const traceId = store ? store.get('traceId') : 'no-trace';
  console.log(`[Trace: ${traceId}] ${message}`);
}

function processRequest(reqId) {
  const context = new Map();
  context.set('traceId', reqId);

  // Run the callback inside a tracked asynchronous context
  asyncLocalStorage.run(context, () => {
    logWithTraceId('Operation started');

    setTimeout(() => {
      // The context persists across async boundaries
      logWithTraceId('Async database operation complete');
    }, 100);
  });
}

processRequest('req-101');
processRequest('req-102');

The core primitives are:

  1. run(store, callback, ...args): Sets the active store for the duration of the callback. Any code called synchronously or asynchronously inside this callback inherits access to store.
  2. getStore(): Returns the store associated with the current asynchronous execution context. If called outside of a .run() boundary, it returns undefined.
  3. enterWith(store): Transitions the current execution context to a new store for the remainder of the synchronous turn. While simpler, it is prone to memory leaks and unexpected context propagation, making .run() the preferred pattern.

Common Use Cases

  • Distributed Tracing: Automatically propagating correlation IDs, trace IDs, and request metadata through logging systems without manual function argument plumbing.
  • Authentication Context: Making the authenticated user's session available to deeply nested business logic, data access layers, or audit loggers.
  • Multi-tenancy: Keeping tenant identifiers attached to ongoing database transactions to prevent accidental cross-tenant data access.

Performance and Best Practices

While AsyncLocalStorage is heavily optimized in modern Node.js versions (v16+), it introduces a baseline overhead because the runtime must allocate and maintain asynchronous context tracking. To maximize efficiency:

  • Store a plain object or Map rather than instantiating complex class instances inside each context.
  • Avoid using enterWith(), as it modifies the context transition state globally for the current asynchronous turn and can prevent proper garbage collection.
  • Use AsyncLocalStorage primarily for cross-cutting concerns like tracing and logging, rather than relying on it for general application control flow.
