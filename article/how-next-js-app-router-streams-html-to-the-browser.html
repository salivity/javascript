How Next.js App Router Streams HTML to the Browser

The Next.js App Router uses React Server Components and modern web streaming APIs to send progressively rendered HTML chunks to the client over a single, persistent HTTP response. This architecture allows the browser to display static UI elements and loading skeletons immediately, without waiting for slow server-side data fetching to complete or client-side JavaScript bundles to download and execute.

The Foundation: HTTP Streaming and ReadableStreams

Traditional Server-Side Rendering (SSR) requires the server to render the entire page into a complete HTML string before sending anything to the client. If a single database query takes two seconds, the entire response is blocked, resulting in a high Time to First Byte (TTFB).

The App Router resolves this by using Node.js and Web Streams (ReadableStream). Built on top of HTTP/1.1 Transfer-Encoding: chunked or HTTP/2 multiplexing, the server keeps the HTTP connection open and emits distinct byte chunks as soon as specific subtrees of the component tree are ready.

React Suspense Boundaries

Streaming in the App Router is driven by React Suspense. When you wrap an asynchronous Server Component in a <Suspense fallback={<Skeleton />}> boundary, you instruct Next.js to decouple that component from the initial document payload:

  1. Initial Shell Delivery: The server renders all synchronous components and any Suspense fallbacks. It flushes this initial HTML shell to the browser immediately.
  2. Immediate Paint: The browser receives this first chunk, parses the HTML, applies CSS, and paints the page structure alongside loading placeholders.
  3. Background Data Resolution: Asynchronous operations—such as database queries or third-party API calls inside Server Components—continue executing concurrently on the server.

Out-of-Order Streaming and Inlined Replacement Scripts

Because different Suspense boundaries complete at different times, Next.js streams content out-of-order. When an asynchronous component finishes executing:

  1. The server renders the component into an HTML segment.
  2. The server appends this markup to the open HTTP stream inside a hidden <template> tag, accompanied by a unique identifier.
  3. Immediately following the template, the server injects a tiny, inline <script> tag.

When the browser receives this chunk, it immediately executes the inline script. The script performs a native DOM operation: it extracts the rendered markup from the hidden template and swaps it into the DOM node occupied by the initial Suspense fallback placeholder.

DOM Updates Prior to JavaScript Bundle Execution

This replacement mechanism operates independently of the main React application bundle. Even if the network is constrained and large JavaScript bundles (such as framework.js or page-specific client chunks) are still downloading or parsing, the user sees real, interactive-looking HTML.

Once the JavaScript bundles finish loading, React hydrates the DOM nodes, binds event handlers, and attaches client-side interactivity without re-rendering the already visible markup.
