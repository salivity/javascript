AVA Concurrent Test Architecture Explained

AVA is a popular JavaScript test runner designed specifically to optimize test execution speed through high-level concurrency. This article breaks down AVA's dual-layer concurrent architecture, detailing how it leverages separate child processes to run test files in parallel across multiple CPU cores, while concurrently executing individual asynchronous tests within each process using Node.js event-loop primitives.

Process-Level Parallelism: Isolated Test Files

At the macro level, AVA isolates test files by running each file inside its own dedicated Node.js child process (or worker thread). This design choice achieves two critical goals:

  1. True Multi-Core Parallelization: JavaScript runs on a single thread by default. By spawning separate processes for each test file, AVA allows the operating system to distribute workloads across all available CPU cores, dramatically decreasing the total run time for large test suites.
  2. State Isolation: Because each test file resides in a separate process, global state is not shared between files. Global variables, module mocks, or environment mutations made in one test file cannot leak into or contaminate another.

The main AVA process acts as an orchestrator. It scans for test files, determines the system's available CPU capacity, spawns worker processes accordingly, and aggregates results via Inter-Process Communication (IPC).

In-Process Concurrency: Asynchronous Test Execution

Within an individual test file, AVA does not wait for a test to complete before starting the next one. Instead, it runs tests concurrently by default using JavaScript's native asynchronous architecture.

When multiple tests return Promises or use async/await, AVA initiates them simultaneously. While one test is awaiting an I/O operation (such as a database query, network call, or disk access), the Node.js event loop executes other pending tests. This maximizes throughput during I/O-heavy integration or end-to-end tests.

test('fetches user profile', async t => {
  const data = await fetchUserData();
  t.truthy(data);
});

test('fetches site settings', async t => {
  const settings = await fetchSettings();
  t.truthy(settings);
});

In the example above, both tests initiate their asynchronous requests concurrently within the same worker process.

Controlling Concurrency: Serial Execution

Because concurrent execution can cause race conditions when tests rely on a shared local state (such as an in-memory database or a specific file path), AVA provides an opt-in serial execution modifier:

test.serial('first step requiring shared database', async t => {
  await db.write({ id: 1 });
  t.pass();
});

test.serial('second step reading shared database', async t => {
  const record = await db.read(1);
  t.truthy(record);
});

Using test.serial instructs the runner to wait for the preceding test to finish completely before invoking the next one within that specific process, preventing race conditions without sacrificing the isolation benefits of the broader architecture.

Resource Throttling and Concurrency Limits

Running unrestricted parallel processes can quickly exhaust system memory and CPU resources. AVA mitigates this by profiling system resources and limiting the maximum number of worker processes running simultaneously, typically defaulting to the number of logical CPU cores. Developers can fine-tune this behavior through configuration flags, defining how many worker processes to spawn concurrently to balance execution speed with environment constraints.
