How Jotai Implements Atomic State in JavaScript

Jotai handles React state management through an atomic approach where state is divided into independent, minimal units called atoms. Unlike monolithic state libraries that manage an application-wide tree from the top down, Jotai builds complex application state from the bottom up by composing primitive and derived units. This article explores how Jotai defines primitive atoms, manages their runtime storage via JavaScript WeakMap collections, and uses dynamic dependency graphs to achieve efficient, granular UI updates.

Primitive Atoms as Configuration Objects

In Jotai, calling the atom() function does not create a state container holding a mutable value. Instead, a primitive atom is a lightweight, immutable configuration object (an atom definition).

import { atom } from 'jotai';

const countAtom = atom(0);

When atom(0) executes, it returns a plain JavaScript object containing metadata: the initial value, a read function, and a write function. Because the atom is merely a definition and does not store the current runtime value, it can be declared anywhere—even globally outside of React's component lifecycle—without causing memory leaks or unintended side effects.

Store Architecture and WeakMaps

To associate values with atom definitions, Jotai delegates state storage to a runtime store, typically mounted via a React Context (or using a default global store).

Jotai keeps the atom definitions decoupled from their values by using JavaScript's native WeakMap. Internally, the store maintains a mapping where the atom definition itself acts as the key, and an internal state object (containing the current value, epoch, and subscribers) acts as the value:

// Conceptual representation of Jotai's internal store
const atomStateMap = new WeakMap();

function getAtomState(atom) {
  let state = atomStateMap.get(atom);
  if (!state) {
    state = { value: atom.init, listeners: new Set(), dependents: new Set() };
    atomStateMap.set(atom, state);
  }
  return state;
}

Because WeakMap holds weak references to its keys, if an atom definition falls out of scope, the garbage collector automatically reclaims the memory used by that atom and its associated state, preventing memory leaks in dynamic applications.

Bottom-Up Composition with Derived Atoms

Bottom-up composition allows developers to build complex logic by combining simpler primitives. Jotai facilitates this by allowing atoms to accept a read function that consumes other atoms using a get function passed as an argument.

const priceAtom = atom(10);
const quantityAtom = atom(2);

// Derived atom composed from primitive atoms
const totalAtom = atom((get) => get(priceAtom) * get(quantityAtom));

In this pattern:

  1. Primitive Atoms hold raw, uncomputed values (e.g., numbers, strings, objects).
  2. Derived Atoms consume one or more primitive atoms (or other derived atoms) to compute new values on demand.
  3. Writable Derived Atoms can implement a custom write function that updates multiple underlying primitive atoms in a single transaction.

Instead of slicing pieces out of a massive central store, you declare granular primitives and stitch them together upwards as your requirements evolve.

Dependency Tracking and Granular Updates

When a derived atom or a component reads an atom value, Jotai dynamically tracks dependencies. When get(priceAtom) is invoked within totalAtom, Jotai records priceAtom as a dependency of totalAtom.

This creates a directed acyclic graph (DAG) of state dependencies:

  • Change Propagation: When a primitive atom changes (e.g., priceAtom updates), the store notifies only the atoms and React components directly subscribed to priceAtom or its dependents (totalAtom).
  • Targeted Re-renders: Unrelated components that consume different atoms are never evaluated. React hooks like useAtomValue subscribe directly to the specific atom node in the dependency graph, bypassing unnecessary tree-wide reconciliation.

By combining WeakMap-backed storage with dynamic dependency tracking, Jotai achieves a scalable bottom-up architecture that keeps state definitions declarative and UI updates minimal.
