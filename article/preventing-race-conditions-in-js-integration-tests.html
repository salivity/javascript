Preventing Race Conditions in JS Integration Tests

Asynchronous race conditions in JavaScript integration tests lead to flaky test suites, hard-to-reproduce bugs, and untrustworthy continuous integration pipelines. These issues typically arise when test execution outpaces state updates, database transactions, or background microtasks. Systematically preventing race conditions requires moving away from non-deterministic behaviors, such as arbitrary timeouts, and adopting structural patterns like polling-based assertions, rigorous test isolation, and explicit lifecycle hooks.

Eliminate Arbitrary Delays

Using arbitrary delays like setTimeout or sleep(1000) is the primary cause of integration test flakiness. Under heavy CI load, fixed delays are often too short; under local execution, they unnecessarily slow down the suite.

Replace fixed sleep timers with condition-based polling. Libraries like Testing Library (waitFor) or custom pollers continually check for a specific DOM change, database row, or network response until a condition is satisfied or an explicit timeout is reached:

// Anti-pattern
await triggerAsyncProcess();
await sleep(1500);
expect(await checkDatabase()).toBe(true);

// Systematic approach
await triggerAsyncProcess();
await waitFor(async () => {
  const result = await checkDatabase();
  expect(result).toBe(true);
});

Isolate State Per Test

Race conditions frequently occur when concurrent tests share a single global state, such as an in-memory datastore, mock server, or shared database schema.

  1. Unique Identifiers: Generate unique tenant, user, or entity IDs (such as UUIDs) for every test run to ensure simultaneous writes do not collide.
  2. Transaction Rollbacks: Wrap each integration test in an isolated database transaction that rolls back automatically during the afterEach lifecycle.
  3. Dedicated Schemas or Workers: In parallel test runners like Vitest or Jest, assign each test worker a distinct database schema or containerized instance.

Synchronize Asynchronous Pipelines

When code triggers background tasks (fire-and-forget promises, event emitters, or queue jobs), tests often complete before the underlying processing finishes.

  • Await Background Work: Modify internal APIs to allow awaiting execution pipelines during testing. Expose hooks, batch flush mechanisms, or returned promises that tests can explicitly await.
  • Drain Message Queues: If integration tests publish messages to a broker (such as RabbitMQ or Redis), wait for the consumer to acknowledge the message rather than assuming instantaneous delivery.
  • Flush the Event Loop: If operations rely on multiple nested microtasks, explicitly drain the microtask queue before asserting:
const flushMicrotasks = () => new Promise(resolve => setImmediate(resolve));

await performAction();
await flushMicrotasks();
expect(listener).toHaveBeenCalled();

Deterministic Network Handling

If tests interact with external HTTP services, real network latency introduces non-deterministic timing into assertions.

  • Use network-level interceptors like Mock Service Worker (MSW) or Nock to simulate real network responses deterministically without relying on real endpoints.
  • Ensure all intercepted calls are explicitly awaited and unregistered in cleanup hooks (afterEach) to prevent delayed responses from bleeding into subsequent tests.

Enforce Strict Linting and Promise Handling

Uncaught or unhandled promises often resolve out of band, triggering race conditions in unrelated subsequent tests.

  • Enable the @typescript-eslint/no-floating-promises lint rule to mandate that every asynchronous call is explicitly awaited, returned, or caught.
  • Configure the test runner to fail tests immediately on unhandled rejections using flags such as Node.js's --unhandled-rejections=strict.
