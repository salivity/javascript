How TC39 Evolves JavaScript Without Breaking the Web

The Ecma International Technical Committee 39 (TC39) governs the evolution of ECMAScript—the standard behind JavaScript—under the foundational rule: "don't break the web." This principle mandates that code written decades ago must continue to execute identically in modern browsers. To achieve this while continually modernizing the language, TC39 utilizes a multi-stage consensus process, comprehensive automated testing suites, engine telemetry, and deliberate lexical and semantic compromises to ensure backward compatibility remains intact.

The Staged Proposal Pipeline

TC39 manages language additions through a five-stage process (Stage 0 through Stage 4). A proposal cannot advance to completion simply on theoretical merit; it must prove it does not harm existing web infrastructure.

  • Stage 0 (Strawman) & Stage 1 (Proposal): Outlines the problem and potential solutions.
  • Stage 2 (Draft) & Stage 2.7 (Tests): Defines the formal specification syntax and initial compliance tests.
  • Stage 3 (Candidate): Browser vendors implement the feature behind flags or in preview builds. This stage is critical for web compatibility, as it exposes the implementation to real-world code before formal standardization.
  • Stage 4 (Finished): The feature passes the official test suite, ships enabled by default across multiple major browser engines without breaking user traffic, and is scheduled for the next ECMAScript release.

Real-World Telemetry and Counter-Testing

Browser vendors on the committee (such as Google, Mozilla, Apple, and Microsoft) use automated scrapers, web crawlers, and telemetry in canary and developer channels to test new features. By running candidate features against snapshots of top-ranking web pages (such as data sets from HTTP Archive), vendors identify unintended collisions with legacy frameworks.

If shipping a new feature alters an existing prototype or causes an error on even a fraction of a percent of sites, the feature is rolled back and re-evaluated. A famous example occurred during the introduction of array flattening: the originally proposed name Array.prototype.flatten conflicted with the legacy library MooTools, which injected a non-standard flatten method into the global prototype. To avoid breaking millions of older sites, TC39 renamed the standard method to Array.prototype.flat.

Additive Design and Name Alterations

JavaScript strictly avoids mutating the behavior or syntax of existing features. Instead, TC39 relies on additive evolution:

  • Identifier Selection: When standardizing methods that might conflict with historic, custom implementations on native prototypes, TC39 chooses alternate names (e.g., using String.prototype.includes instead of contains).
  • New Primitives and Keywords: Introducing new keywords risks breaking code that used those words as variable identifiers. TC39 works around this by introducing contextual keywords or utilizing non-colliding syntax, such as using symbols (Symbol.iterator) to extend objects without overwriting existing string keys.

Strict Mode and Granular Scoping

When certain legacy behaviors were deemed fundamentally problematic for engine optimization and code safety, TC39 did not unilaterally overwrite them. Instead, ECMAScript 5 introduced "use strict". Strict mode created an opt-in context that fixed early design errors (such as preventing silent failures on read-only assignments and eliminating implicit global variables) without modifying the execution context of legacy, un-migrated scripts.

Similarly, rather than altering the function-scoped behavior of var, TC39 introduced block-scoped bindings (let and const) alongside it, preserving the execution semantics of older codebases while giving developers modern alternatives.

The Test262 Conformance Suite

Engine parity is essential to stability. TC39 maintains Test262, the comprehensive ECMAScript conformance test suite. Before any specification change reaches Stage 4, comprehensive Test262 test cases must be written to cover valid usages, edge cases, and failure modes. All major engines (V8, JavaScriptCore, SpiderMonkey) must pass these tests, ensuring that browser behavior remains strictly identical across platforms and eliminating cross-browser incompatibilities that could destabilize the web.
