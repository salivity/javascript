Split-Screen Multiplayer Cameras in HTML5 Canvas

Split-screen multiplayer in JavaScript games allows two or more players to share a single display by partitioning an HTML5 <canvas> element into distinct viewports. This article explains how game developers achieve this effect through mathematical screen division, state transformation and clipping using the 2D rendering context, multi-pass rendering loops, and performance optimizations like camera-specific frustum culling.

Defining Viewport Boundaries

To divide a canvas, you must calculate the bounding box for each player's view based on the canvas dimensions (canvas.width and canvas.height).

  • Two Players (Vertical Split): Each viewport receives the full height and half the width (width / 2, height).
  • Two Players (Horizontal Split): Each viewport receives the full width and half the height (width, height / 2).
  • Four Players (Grid Split): The canvas is split into quadrants, where each viewport is width / 2 by height / 2.

Each viewport is represented by an object storing its screen coordinates: an origin (x, y), a width, and a height.

The Core Rendering Pipeline: Save, Clip, Translate, Restore

The standard approach to rendering multiple camera views onto a single canvas utilizes the 2D context (CanvasRenderingContext2D) transformation and clipping methods. For each player, the rendering pipeline executes the following sequence:

  1. Save Context State (ctx.save()): Preserves the default transformation matrix, clipping path, and styling settings.
  2. Define the Clipping Region (ctx.beginPath(), ctx.rect(), ctx.clip()): Constrains all subsequent drawing operations strictly within the designated player's viewport bounds. Any graphics rendered outside this boundary are discarded.
  3. Clear the Viewport (ctx.clearRect()): Clears only the active viewport area, preventing artifacts from the previous frame.
  4. Apply Camera Translation (ctx.translate()): Offsets the canvas grid so the player's world position aligns with their camera center. The translation formula maps the world coordinates to the center of the viewport: \[\text{offsetX} = \text{viewport.x} + (\text{viewport.width} / 2) - \text{player.x}\] \[\text{offsetY} = \text{viewport.y} + (\text{viewport.height} / 2) - \text{player.y}\]
  5. Render World Entities: Draws the background, terrain, and game entities using world coordinates.
  6. Restore Context State (ctx.restore()): Resets the canvas context to remove the clipping boundary and translation offsets before processing the next player.

Rendering HUD and Viewport Dividers

User interfaces (health bars, ammo counts, minimaps) require a separate pass. You can render player-specific HUD elements while the context is still clipped to that player's viewport, but without the camera translation applied. Once all viewports and HUD elements are rendered, a final pass can draw dividing borders (solid lines) along the shared boundaries to visually distinguish each player's screen space.

Alternative Approach: Offscreen Canvases

Instead of clipping directly onto the main canvas, developers can render each camera view to an individual, invisible offscreen canvas (document.createElement('canvas') or OffscreenCanvas). During the final composite step, the main canvas draws each offscreen canvas onto its surface using ctx.drawImage().

This method simplifies complex post-processing effects (such as individual camera shaders or screen-shake) at the cost of higher memory allocation and additional pixel-copying overhead.

Performance and Frustum Culling

Split-screen rendering multiplies the number of draw calls per frame by the number of active cameras. To maintain 60 frames per second:

  • Frustum Culling: Calculate an Axis-Aligned Bounding Box (AABB) for each camera's visible world area. Before issuing a draw command, check if an entity's coordinates intersect that specific camera's bounding box. Skip rendering for entities outside the view.
  • Shared Asset Calculations: Update game physics, input, and AI states once per tick, independent of the render loop. Avoid running duplicate game logic inside the multi-pass camera routines.
