Input Buffering for Responsive JavaScript Game Combos

Input buffering is a game programming technique that temporarily stores player inputs within a short time window, allowing actions to register even if entered slightly before the game state is ready to execute them. In JavaScript game development, where frame rates can fluctuate and browser event handling operates independently of the main render loop, input buffering is essential for eliminating dropped commands and creating fluid combat mechanics. This article explores the concept of input buffering, examines how it solves timing issues in JavaScript games, and outlines how to implement a responsive combo system using modern web standards.

The Problem: Dropped Inputs and Strict Frame Timing

In fast-paced action games and fighting games, character actions have defined durations, such as startup frames, active hit frames, and recovery frames. Without input buffering, a game engine only accepts a new command on the exact frame the character transitions from a recovery state back to an idle state.

If a player presses an attack button even one frame (roughly 16.6 milliseconds at 60 FPS) before the recovery state ends, the game drops the input entirely. This creates an experience known as "eating inputs," making controls feel unresponsive, stiff, and overly punishing. For complex combos requiring sequential button presses, this forces players to master rigid frame-perfect execution rather than focusing on strategy and rhythm.

What is an Input Buffer?

An input buffer acts as a rolling queue or list that records player actions alongside the exact timestamp or frame number they occurred. Instead of checking whether an input happened on the current frame, the game engine checks whether a valid input occurred within an acceptable recent window (typically between 50 to 150 milliseconds).

When a character enters a state where they can perform an action, the engine inspects the buffer. If an eligible action exists in the buffer and has not yet expired, the engine consumes that input and executes the corresponding move immediately.

Why Input Buffering is Crucial in JavaScript

Implementing input detection in browser-based games introduces unique timing challenges:

  1. Decoupled Input and Render Loops: Browsers process DOM keyboard and gamepad events asynchronously through the JavaScript event loop, while game rendering and physics typically run inside a requestAnimationFrame loop. A key press might occur halfway between two render ticks.
  2. Garbage Collection and Frame Jitter: JavaScript is a garbage-collected language. Brief spikes in execution time can cause occasional dropped frames or inconsistent tick rates (delta time).
  3. Hardware Latency: Display latency and browser input latency already introduce a delay between a physical button press and the visual result.

Input buffering bridges the gap between asynchronous DOM events and fixed-step or delta-time game loops, ensuring that player intent is preserved regardless of minor browser hiccups.

Implementing an Input Buffer in JavaScript

A standard JavaScript input buffer consists of an array of input objects, a mechanism to register new inputs, an expiration check, and a move-matching parser.

1. Recording Inputs with Timestamps

Listen to browser inputs and push them to an array with a high-resolution timestamp using performance.now():

class InputBuffer {
  constructor(bufferWindowMs = 120) {
    this.bufferWindowMs = bufferWindowMs;
    this.buffer = [];
  }

  addInput(action) {
    this.buffer.push({
      action: action,
      time: performance.now(),
      consumed: false
    });
  }

  cleanExpired(currentTime) {
    this.buffer = this.buffer.filter(
      input => !input.consumed && (currentTime - input.time <= this.bufferWindowMs)
    );
  }
}

2. Processing and Consuming Inputs in the Game Loop

During the update cycle, prune expired inputs and inspect the queue for actions relevant to the player's current state:

function updatePlayer(player, inputBuffer, currentTime) {
  inputBuffer.cleanExpired(currentTime);

  if (player.state === 'RECOVERY') {
    // Player cannot act yet, but inputs are being safely stored in the buffer
    return;
  }

  if (player.state === 'IDLE') {
    // Find the oldest unconsumed input within the buffer window
    const nextAction = inputBuffer.buffer.find(input => !input.consumed);

    if (nextAction) {
      player.executeAction(nextAction.action);
      nextAction.consumed = true; // Mark as consumed so it doesn't trigger twice
    }
  }
}

Handling Sequential Combos

For sequential combo strings (such as pressing Light Punch followed by Heavy Punch, or directional motions like Down, Forward, Punch), input buffering extends beyond single-button checks to sequence matching.

To implement combo recognition:

  1. Maintain a Longer History Buffer: While single-action buffering needs a tight window (e.g., 100ms) to prevent unintended actions, directional sequences require a longer trailing window (e.g., 300–500ms).
  2. Pattern Matching: On each update, evaluate the buffered sequence against defined combo patterns starting from the most complex moves down to basic attacks.
  3. Buffer Flushing: Once a combo pattern is recognized and executed, clear or consume the inputs involved in that sequence to prevent overlapping move triggers.

Key Best Practices

  • Keep the Buffer Window Tight: A buffer window that is too long (over 200ms) results in "sticky" controls where an old, panicked button press executes long after the player changes their mind.
  • Prioritize High-Value Actions: When multiple valid inputs exist in the buffer simultaneously, prioritize defensive options (like blocking or dodging) or special moves over standard attacks.
  • Differentiate Hold vs. Tap: Ensure your input collector distinguishes between a sustained key press and a single actuation frame to prevent a single held key from continuously filling the buffer.

By implementing an input buffer, JavaScript games achieve the same crisp, reliable control feel found in native desktop engines, providing players with responsive and forgiving execution windows.
