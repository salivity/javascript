Chain of Responsibility and JavaScript Middleware

This article explores the Chain of Responsibility design pattern and demonstrates how modern JavaScript frameworks use it to implement middleware chaining. You will learn the core mechanics of the pattern, see how it facilitates modular request processing in environments like Express.js, and examine a practical code implementation that illustrates passing control sequentially between independent handlers.

What is the Chain of Responsibility Pattern?

The Chain of Responsibility is a behavioral design pattern that allows a request to be passed along a pipeline of handlers. Upon receiving a request, each handler decides either to process the request, modify it, or pass it along to the next handler in the sequence. Alternatively, a handler can choose to halt the execution chain entirely—a behavior known as short-circuiting.

The primary advantage of this pattern is decoupling: the sender of a request does not need to know which specific object will handle it, and individual processing units remain isolated, reusable, and single-purposed.

Middleware Chaining in JavaScript

In JavaScript, particularly within server-side environments like Express, Koa, or Redux, the Chain of Responsibility pattern is universally known as middleware chaining.

In web servers, an incoming HTTP request must typically undergo several sequential steps:

  1. Logging the request details.
  2. Parsing incoming JSON payloads or URL parameters.
  3. Authenticating and authorizing the user.
  4. Validating request data.
  5. Executing final route logic and returning a response.

Rather than bundling all these concerns into a single, bloated route handler, middleware chaining splits these responsibilities across discrete functions.

Each middleware typically receives three arguments: the request object (req), the response object (res), and a callback usually named next. The next() function acts as the trigger that advances execution to the subsequent handler in the chain.

Short-Circuiting the Pipeline

A key aspect of this pattern is conditional termination. If an authentication middleware verifies a token and finds it invalid, it does not invoke next(). Instead, it sends an HTTP 401 response directly to the client. This immediately terminates the chain, ensuring downstream handlers (such as database queries) are never executed unnecessarily.

Practical Implementation in JavaScript

The following example demonstrates a simplified implementation of a middleware pipeline using the Chain of Responsibility pattern in native JavaScript:

class Pipeline {
  constructor() {
    this.middlewares = [];
  }

  use(fn) {
    this.middlewares.push(fn);
  }

  execute(context) {
    let index = 0;

    const next = () => {
      if (index < this.middlewares.length) {
        const currentMiddleware = this.middlewares[index++];
        currentMiddleware(context, next);
      }
    };

    next();
  }
}

// Instantiate pipeline
const app = new Pipeline();

// Middleware 1: Logger
app.use((ctx, next) => {
  console.log(`[LOG] Request to: ${ctx.url}`);
  ctx.startTime = Date.now();
  next();
});

// Middleware 2: Authentication Check
app.use((ctx, next) => {
  if (!ctx.authenticated) {
    console.log('[AUTH] Access denied. Halting chain.');
    return; // Chain stops here
  }
  console.log('[AUTH] Access granted.');
  next();
});

// Middleware 3: Final Handler
app.use((ctx) => {
  const duration = Date.now() - ctx.startTime;
  console.log(`[HANDLER] Processing request. Completed in ${duration}ms.`);
});

// Execute chain with unauthorized request
console.log('--- Test Run 1: Unauthorized ---');
app.execute({ url: '/api/data', authenticated: false });

// Execute chain with authorized request
console.log('\n--- Test Run 2: Authorized ---');
app.execute({ url: '/api/data', authenticated: true });

Benefits of the Pattern in JavaScript Applications

  • Single Responsibility Principle: Each middleware function focuses on one isolated concern, making code easier to test and maintain.
  • Dynamic Composition: Middlewares can be reordered, inserted conditionally, or combined in varying arrangements depending on environment configurations or routes.
  • Maintainability: Shared operations, such as error handling, rate limiting, and CORS handling, can be written once and attached globally across an entire application.
