What Is Server-Side Rendering and How Does It Work?

Server-Side Rendering (SSR) is a web development technique where a server dynamically executes JavaScript components to produce full HTML pages on every incoming request, rather than leaving the rendering work to the user's browser. This article explains the fundamentals of Server-Side Rendering, walks step-by-step through the process of converting JavaScript components into static HTML strings on demand, and covers the subsequent hydration phase that restores interactivity on the client side.

Understanding Server-Side Rendering

In a traditional Single-Page Application (SPA) using Client-Side Rendering (CSR), the server responds to a user's request by delivering an empty HTML shell accompanied by a large JavaScript bundle. The user's browser must download, parse, and execute this JavaScript before any meaningful content appears on the screen.

Server-Side Rendering inverts this responsibility. When a visitor requests a URL, a server-side JavaScript runtime (such as Node.js, Deno, or Bun) intercepts the request, runs the application’s component logic, fetches any necessary data, and compiles the final user interface into a complete HTML document. The browser receives fully formed markup that it can display immediately.

How JavaScript Components Are Converted to HTML on Request

Modern frameworks like React, Vue, and Svelte utilize specific server-side APIs to compile components into standard HTML. The conversion process follows a structured lifecycle:

1. Request Handling and Routing

When a user navigates to a specific route, the web server matches the URL against the application's routing definitions. The server determines which root components, layouts, and page templates correspond to that specific endpoint.

2. Server-Side Data Fetching

Before generating markup, the server identifies all asynchronous data dependencies required by the components for that route. Methods like Next.js's getServerSideProps or standard async server components trigger API calls, database queries, or cache lookups directly on the server network. The returned data is injected into the component state.

3. Component Tree Execution

The server executes the component code using the fetched data as props or state. In this environment, the framework constructs an in-memory representation of the UI (such as a Virtual DOM tree). Browser-specific APIs like window, document, or localStorage do not exist in this phase; the code relies strictly on pure JavaScript logic.

4. HTML Serialization

Once the component tree is constructed, the framework passes it through a serialization utility:

  • React: Uses functions such as renderToString() or the streaming alternative renderToPipeableStream().
  • Vue: Uses renderToString() from @vue/server-renderer.

These methods traverse the virtual component tree and serialize each node—translating custom component tags, state, and conditional blocks into standard semantic HTML tags (<div>, <p>, <h1>, etc.) accompanied by inline styles and class names.

5. Document Assembly and Delivery

The generated HTML string is inserted into the main document template alongside essential <head> metadata, CSS links, and script tags referencing client-side JavaScript bundles. The complete document is then sent over HTTP to the client with a 200 OK status.

The Hydration Phase

Although the browser immediately displays the server-generated HTML—yielding a rapid First Contentful Paint (FCP)—the page is initially inert. Event listeners like onClick or form submit handlers are not yet attached.

To make the application interactive, the browser downloads the client-side JavaScript bundle referenced in the HTML:

  1. The client-side framework initializes in the browser.
  2. It builds its own internal component tree and reconciles it with the existing, visible DOM nodes delivered by the server.
  3. It binds event listeners and initializes local state without re-creating the DOM elements from scratch.

This reconciliation and activation process is known as hydration. Once complete, the application behaves as a fully reactive Single-Page Application.

Why Use Server-Side Rendering?

  • Improved Search Engine Optimization (SEO): Search engine web crawlers receive complete, semantic markup immediately upon making a request, eliminating indexing delays or errors caused by unexecuted JavaScript.
  • Faster Perceived Performance: Users see actual page content much faster on mobile devices and slower network connections, improving Core Web Vitals such as Largest Contentful Paint (LCP).
  • Consistent Social Media Previews: Open Graph and Twitter Card crawlers can scrape dynamic page titles, descriptions, and thumbnail images generated per request.
