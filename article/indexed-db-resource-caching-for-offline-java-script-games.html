IndexedDB Resource Caching for Offline JavaScript Games

This article outlines how to implement an IndexedDB-based resource caching strategy to enable robust offline persistence in JavaScript game development. By leveraging IndexedDB to store heavy binary assets like textures, audio sprites, and 3D meshes as Blobs or ArrayBuffers, developers can circumvent standard browser storage limits and network latency. The following sections detail why IndexedDB is the optimal storage layer for game assets, the step-by-step caching architecture, asset retrieval workflows, and cache invalidation strategies.

Why Use IndexedDB for Game Assets

Browser-based games require significant amounts of data, often exceeding hundreds of megabytes. While localStorage is synchronous and restricted to roughly 5MB of string data, and the Cache API is primarily designed for HTTP request/response pairs, IndexedDB offers distinct advantages:

  • Large Storage Quotas: IndexedDB typically allows usage of up to a significant percentage of the user's available disk space.
  • Structured Binary Storage: It natively stores structured clones, including Blob, ArrayBuffer, and TypedArray objects, avoiding serialization overhead.
  • Asynchronous Execution: Operations run asynchronously on a separate thread, preventing frame drops and main-thread stutter during asset read/write cycles.

The Caching Architecture

An effective caching layer sits between the game engine's asset loader and the network. The workflow follows a "Cache-First" retrieval pattern:

  1. Request: The game engine requests an asset using an identifier or URL.
  2. Lookup: The caching layer queries an IndexedDB object store for the key.
  3. Hit: If the record exists, the binary data is converted to an in-memory object (such as an Object URL via URL.createObjectURL(blob)) and handed to the engine.
  4. Miss: If the record is absent, the asset is fetched over the network, saved into IndexedDB as a Blob or ArrayBuffer, and then delivered to the engine.

Implementation Workflow

1. Database Initialization

Create an initialization routine using indexedDB.open(). Set up an object store specifically for game assets during the onupgradeneeded lifecycle event.

function openAssetDatabase() {
  return new Promise((resolve, reject) => {
    const request = indexedDB.open("GameAssetCache", 1);

    request.onupgradeneeded = (event) => {
      const db = event.target.result;
      if (!db.objectStoreNames.contains("assets")) {
        db.createObjectStore("assets", { keyPath: "url" });
      }
    };

    request.onsuccess = () => resolve(request.result);
    request.onerror = () => reject(request.error);
  });
}

2. Writing Assets to the Store

When downloading an asset, fetch it as a blob or arrayBuffer. Write the payload along with metadata—such as a version hash and timestamp—into the database using a readwrite transaction.

async function cacheAsset(db, url, version) {
  const response = await fetch(url);
  const blob = await response.blob();

  return new Promise((resolve, reject) => {
    const tx = db.transaction("assets", "readwrite");
    const store = tx.objectStore("assets");
    store.put({ url, data: blob, version, timestamp: Date.now() });

    tx.oncomplete = () => resolve(blob);
    tx.onerror = () => reject(tx.error);
  });
}

3. Reading and Instantiation

Query the database with a readonly transaction. When reading back a stored Blob, instantiate it directly into your game's runtime:

async function loadAsset(db, url, currentVersion) {
  const cachedRecord = await new Promise((resolve) => {
    const tx = db.transaction("assets", "readonly");
    const request = tx.objectStore("assets").get(url);
    request.onsuccess = () => resolve(request.result);
    request.onerror = () => resolve(null);
  });

  if (cachedRecord && cachedRecord.version === currentVersion) {
    return URL.createObjectURL(cachedRecord.data);
  }

  const freshBlob = await cacheAsset(db, url, currentVersion);
  return URL.createObjectURL(freshBlob);
}

Cache Invalidation and Versioning

Offline functionality requires a mechanism to update assets when game patches are deployed.

  • Manifest-Driven Versioning: Maintain a JSON manifest containing asset paths paired with content hashes (e.g., {"textures/hero.png": "a8f3b1c"}). Compare the manifest hash against the version field stored in the IndexedDB record.
  • Pruning Stale Assets: During startup, scan the IndexedDB keys against the active manifest. Delete entries no longer referenced in the latest game build to prevent storage bloat.

Memory and Resource Management

  • Revoking Object URLs: When using URL.createObjectURL() to map stored Blobs to Image or Audio elements, invoke URL.revokeObjectURL() once the asset is parsed into WebGL textures or Web Audio buffers to release main-thread memory.
  • Quota Handling: Wrap storage operations in error handlers that detect QuotaExceededError. Implement a fallback to purge low-priority cached files (like background music) when disk space is constrained.
