Virtual Keyboards and Viewports in Mobile JS Games

In mobile JavaScript game development, on-screen virtual keyboards frequently disrupt rendering loops, user interface positioning, and touch event registration by dynamically altering browser viewports. When a player taps an input field—such as a chat bar, player name prompt, or account login—the software keyboard slides into the display area. This article examines the distinction between layout and visual viewports during keyboard activation, the specific technical issues this causes for HTML5 and WebGL games, and practical strategies to prevent interface breaking.

Layout Viewport vs. Visual Viewport

To understand how virtual keyboards impact games, developers must distinguish between the two mobile viewports:

  1. The Layout Viewport: The canvas upon which the browser draws CSS layouts. Historically, this corresponds to window.innerWidth and window.innerHeight.
  2. The Visual Viewport: The portion of the screen currently visible to the user. This is represented by the window.visualViewport API.

When a virtual keyboard appears, mobile browsers handle the screen occlusion using two distinct models:

  • Viewport Resizing: Some browsers resize the layout viewport to occupy only the space above the keyboard. This triggers standard CSS media queries, reflows, and window.resize events.
  • Overlay/Panned Mode: Other browsers keep the layout viewport intact and treat the keyboard as an overlay that shrinks only the visual viewport. In this mode, the browser often pans or scrolls the layout viewport upward so the active text field remains visible.

Key Issues Caused by Virtual Keyboards in Games

1. Canvas Re-dimensioning and Context Resets

Most mobile JavaScript games scale their <canvas> dynamically to fill window.innerWidth and window.innerHeight. If the browser resizes the layout viewport upon opening the keyboard, the canvas dimensions change immediately. This can cause severe aspect ratio distortion, letterboxing, or expensive WebGL context buffer allocations that result in noticeable frame drops.

2. Touch Coordinate Desynchronization

Games typically map screen touches to in-game coordinates using clientX/clientY or pageX/pageY relative to canvas.getBoundingClientRect(). When a browser automatically pans the layout viewport upward to reveal a focused input, the canvas’s bounding rectangle shifts off-screen or out of alignment. If the coordinate transformation logic does not account for viewport scroll offsets (visualViewport.offsetTop and visualViewport.offsetLeft), touch inputs will miss their intended in-game targets.

3. Unwanted Page Scrolling

HTML5 games usually prevent default scrolling via CSS (overflow: hidden, touch-action: none). However, when a native <input> or <textarea> receives focus, the browser’s native focus management bypasses these CSS rules to center the input on the screen. This shifts the fixed-position canvas out of view, exposing white space below or above the game area.

Technical Solutions and Best Practices

Utilize the Viewport Meta interactive-widget Property

Modern browsers support the interactive-widget key within the viewport <meta> tag. This attribute explicitly instructs the browser on how to treat the virtual keyboard:

<meta name="viewport" content="width=device-width, initial-scale=1.0, interactive-widget=overlays-content">
  • resizes-visual: Only the visual viewport shrinks; the layout viewport remains unchanged.
  • resizes-content: The layout viewport shrinks, triggering a full CSS layout resize.
  • overlays-content: The keyboard overlays the content entirely without altering any viewport dimensions.

Using overlays-content or resizes-visual prevents the main layout viewport from shrinking, stopping unwanted canvas resizing.

Decouple Game Scaling from the Layout Viewport

Do not rely exclusively on the global window.onresize event to resize the canvas. Monitor the window.visualViewport API separately:

if (window.visualViewport) {
  window.visualViewport.addEventListener('resize', () => {
    // Determine if the keyboard opened by checking the height difference
    const isKeyboardOpen = window.visualViewport.height < window.innerHeight;
    
    // Adjust UI overlays instead of rebuilding the primary game canvas
    adjustChatUI(window.visualViewport.height);
  });
}

By decoupling the game render target from the input UI, the game can keep the 3D scene or 2D world running at native device resolution while only translating UI elements upward to sit atop the keyboard.

Use the VirtualKeyboard API

Chromium-based browsers provide the navigator.virtualKeyboard interface, granting programmatic control over the keyboard overlay behavior:

if ('virtualKeyboard' in navigator) {
  navigator.virtualKeyboard.overlaysContent = true;

  navigator.virtualKeyboard.addEventListener('geometrychange', (event) => {
    const { x, y, width, height } = event.target.boundingRect;
    // Reposition HTML/Canvas input fields using the exact keyboard dimensions
  });
}

Setting overlaysContent = true prevents the browser from docking the layout viewport or scrolling the page, giving the game complete authority over what elements shift to stay visible.

Manage Hidden Inputs Safely

When using an offscreen <input> element to capture user text for in-engine rendering, never position it using large negative coordinate values (e.g., top: -9999px). Doing so causes the browser to pan the screen thousands of pixels away when focused. Instead, position the input element directly under the user's touch location with zero opacity:

.hidden-game-input {
  position: absolute;
  opacity: 0;
  pointer-events: auto;
  z-index: 10;
  width: 1px;
  height: 1px;
}

Fixing the input coordinates directly where the user expects to type eliminates browser-induced scrolling anomalies while seamlessly triggering the software keyboard.
