Absolute vs Relative Mouse Coordinates in HTML5 Canvas

In canvas-based JavaScript game programming, handling user input accurately requires translating physical mouse clicks into in-game positions. This article covers the fundamental differences between absolute mouse coordinates (the raw cursor position relative to the browser window or page) and relative mouse coordinates (the adjusted position relative to the canvas element and game world). Understanding this distinction is critical for preventing input misalignment caused by page scrolling, CSS scaling, and moving in-game cameras.

Understanding Absolute Coordinates

Absolute coordinates refer to the position of the cursor relative to a fixed browser reference point, completely unaware of where the <canvas> element sits on the page. In standard JavaScript DOM events, these are provided through properties on the MouseEvent object:

  • clientX / clientY: The position relative to the visible browser viewport, ignoring any page scrolling.
  • pageX / pageY: The position relative to the entire HTML document, accounting for scroll offsets.
  • screenX / screenY: The position relative to the user's physical monitor.

If a canvas is centered, padded, or located inside a scrolled page, using absolute coordinates directly causes inputs to register away from the intended target. A click at clientX: 100 means nothing to a game engine unless it knows where the canvas begins.

Canvas-Relative Coordinates

Canvas-relative coordinates map the mouse position directly to the canvas's local pixel grid, making (0, 0) correspond to the top-left corner of the canvas rather than the top-left of the monitor or viewport.

To convert viewport-absolute coordinates (clientX, clientY) into canvas-relative coordinates, subtract the canvas's position on the screen using getBoundingClientRect():

function getCanvasMousePosition(canvas, event) {
    const rect = canvas.getBoundingClientRect();
    return {
        x: event.clientX - rect.left,
        y: event.clientY - rect.top
    };
}

This ensures that clicking the top-left pixel of the canvas always yields (0, 0), regardless of page margins, CSS positioning, or page scrolling.

Handling CSS Scaling and Resolution Differences

A common trap in 2D game development is a mismatch between the canvas's internal drawing buffer resolution (width and height attributes) and its displayed CSS size (styled via CSS width and height).

If an internal canvas of 800×600 is scaled via CSS to fit a 1600×1200 layout, raw bounding rectangle subtraction will be off by a factor of 2. You must account for scaling factors along both axes:

function getScaledCanvasCoordinates(canvas, event) {
    const rect = canvas.getBoundingClientRect();
    
    // Calculate the ratio between the internal resolution and displayed size
    const scaleX = canvas.width / rect.width;
    const scaleY = canvas.height / rect.height;

    return {
        x: (event.clientX - rect.left) * scaleX,
        y: (event.clientY - rect.top) * scaleY
    };
}

World-Relative Coordinates (Cameras and Viewports)

Once coordinates are relative to the canvas bitmap, larger games often require a third layer: world-relative coordinates.

If your game features a scrolling world, an in-game camera, or a zoom mechanism, the canvas-relative coordinates represent screen space, not world space. To interact with an in-game entity, you must transform canvas coordinates by the camera's offset and scale:

function screenToWorld(canvasCoords, camera) {
    return {
        x: (canvasCoords.x / camera.zoom) + camera.x,
        y: (canvasCoords.y / camera.zoom) + camera.y
    };
}

Summary of the Pipeline

Accurate input mapping follows a sequential transformation pipeline:

  1. Absolute Viewport Space: (event.clientX, event.clientY)
  2. Element-Relative Space: Subtract rect.left and rect.top.
  3. Canvas-Bitmap Space: Multiply by (canvas.width / rect.width) to handle CSS scaling.
  4. Game-World Space: Apply camera offsets and camera zoom to obtain the final in-game target coordinate.
