Contract Testing Microservices With Pact in JavaScript

This article provides a comprehensive overview of contract testing and demonstrates how the Pact framework verifies microservices in a JavaScript environment. You will learn the core concepts of consumer-driven contract testing, why it is superior to traditional integration testing for distributed architectures, and the step-by-step workflow required to implement and verify contracts between JavaScript-based services.

What is Contract Testing?

Contract testing is an integration testing methodology that ensures two separate systems—a consumer (the client requesting data) and a provider (the server providing data)—can communicate with each other effectively. Instead of testing the entire system end-to-end in a live environment, contract testing captures the interactions between services in a shared agreement known as a "contract."

In a microservices architecture, traditional end-to-end (E2E) testing is slow, brittle, and difficult to maintain. Unit tests verify code in isolation but miss integration issues, while E2E tests require all dependent microservices to be running concurrently. Contract testing bridges this gap by testing API boundaries in isolation. It verifies that:

  • The consumer sends expected HTTP requests and can parse the provider's responses.
  • The provider can handle those exact requests and return responses matching the agreed-upon schema and status codes.

The Pact Framework

Pact is the industry standard for consumer-driven contract testing. In a consumer-driven approach, the consumer defines the expectations of the API (endpoints, request headers, bodies, and expected responses). Pact records these expectations during consumer tests and generates a standardized JSON file called a "pact." This pact file is then delivered to the provider to verify its implementation against the consumer's expectations.

Verifying JavaScript Microservices with Pact

Pact provides official support for JavaScript and TypeScript through the @pact-foundation/pact npm package. The verification process consists of two primary phases: consumer test execution and provider verification.

Phase 1: Consumer Test and Contract Generation

The consumer team defines the contract through automated tests using test runners like Jest or Mocha.

  1. Set Up the Mock Service: The consumer test initializes a Pact mock provider.
  2. Define Interactions: The developer specifies the expected HTTP method, path, headers, request body, and expected response (including dynamic matching rules for types, regex patterns, or minimum array lengths).
  3. Execute the Consumer Code: The real consumer API client code is executed against the Pact mock service instead of the real provider.
  4. Generate the Contract: If the consumer code succeeds and handles the mock response correctly, Pact writes the interactions to a JSON pact file.
import { PactV3, MatchersV3 } from '@pact-foundation/pact';
import { fetchUserProfile } from './apiClient';

const provider = new PactV3({
  consumer: 'FrontendApp',
  provider: 'UserService',
});

describe('User Service API', () => {
  it('returns a user profile when given a valid ID', async () => {
    provider
      .given('a user with ID 10 exists')
      .uponReceiving('a request for user 10')
      .withRequest({
        method: 'GET',
        path: '/users/10',
      })
      .willRespondWith({
        status: 200,
        headers: { 'Content-Type': 'application/json' },
        body: {
          id: MatchersV3.integer(10),
          name: MatchersV3.string('John Doe'),
        },
      });

    await provider.executeTest(async (mockserver) => {
      const user = await fetchUserProfile(mockserver.url, 10);
      expect(user.name).toEqual('John Doe');
    });
  });
});

Phase 2: Provider Verification

Once the pact file is generated—often hosted in a shared repository called a Pact Broker—the provider service validates that it meets the consumer's requirements.

  1. Start the Provider Service: The provider starts in a test configuration (e.g., an Express or Fastify server).
  2. Replay Interactions: The Pact verifier reads the JSON contract, issues the exact HTTP requests defined by the consumer to the running provider instance, and checks the real responses against the contract definitions.
  3. Manage Provider States: If an interaction requires specific backend data (such as "a user with ID 10 exists"), Pact triggers setup handlers on the provider to seed or mock the database prior to executing that specific request.
import { Verifier } from '@pact-foundation/pact';
import { server } from './server';

describe('Pact Verification', () => {
  beforeAll((done) => server.listen(8080, done));
  afterAll((done) => server.close(done));

  it('validates the expectations of FrontendApp', async () => {
    const verifier = new Verifier({
      provider: 'UserService',
      providerBaseUrl: 'http://localhost:8080',
      pactUrls: ['./pacts/FrontendApp-UserService.json'],
      stateHandlers: {
        'a user with ID 10 exists': async () => {
          // Database seeding or mock setup logic
        },
      },
    });

    await verifier.verifyProvider();
  });
});

Benefits of Using Pact in CI/CD

Integrating Pact into continuous integration and continuous deployment pipelines ensures safety without shared test environments. If a provider makes a breaking change (such as renaming a field or changing a data type), the provider verification step fails immediately before deployment. Coupled with the Pact Broker's can-i-deploy tool, teams can independently deploy microservices knowing their APIs remain fully compatible.
