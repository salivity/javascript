React Server Components Wire Format Explained

This article explores the React Server Components (RSC) wire format, detailing its structure as a streaming serialization protocol and demonstrating how client-side JavaScript parses and reconciles this data stream into a functional UI without destroying client-side state.

What is the RSC Wire Format?

The RSC wire format (internally referred to as the Flight protocol) is not raw HTML, nor is it standard JSON. It is a compact, newline-delimited streaming data protocol designed to represent a rendered React component tree across the network.

Because standard JSON cannot natively serialize promises, symbols, or circular references, and HTML strips away client-side React metadata, React uses this custom format. Each line in the response represents a discrete chunk of data prefixed by a line identifier, a tag, and a payload:

  • M (Module): Defines a reference to a Client Component. It provides the bundle ID and export name so the client runtime knows which client-side JavaScript chunk to download and execute.
  • J (JSON / Element Tree): Represents the rendered element tree. It serializes standard HTML elements, props, and references to Client Components via their module IDs.
  • S (Suspense): Marks Suspense boundaries and lazy initialization markers.
  • E (Error): Serializes errors thrown during server rendering.
  • T (Text): Streams raw text chunks, often used for large text blocks.

A simplified example of an RSC stream looks like this:

M1:{"id":"./src/Counter.client.js","name":"default"}
J0:["$","div",null,{"children":[["$","h1",null,{"children":"Hello World"}],["$","$L1",null,{"initialCount":0}]]}]

In this example, line M1 declares a Client Component located at ./src/Counter.client.js. Line J0 describes a div element holding an h1 and a reference ($L1) pointing to the Client Component defined in line 1, passing {initialCount: 0} as a prop.

How Client JavaScript Consumes the Wire Format

The client-side consumption process is handled by a specialized package—such as react-server-dom-webpack/client—and proceeds through the following phases:

1. Streaming and Parsing

When the client requests an RSC update, it initiates a standard fetch request. Instead of waiting for the entire response to complete, the client immediately reads the response using the ReadableStream API. As chunks arrive, the client parser splits the incoming data by newline characters and matches the tag prefixes (M, J, etc.).

2. Deserializing Nodes and Loading Modules

The parser deserializes the payload back into React elements:

  • When the parser encounters standard DOM elements (like div or span), it converts them directly into standard React Virtual DOM objects ($$typeof: Symbol(react.element)).
  • When it encounters a reference to a Client Component ($L1), it looks up the associated module reference declared by an M line. If the corresponding JavaScript chunk is not already loaded in the browser, the runtime uses the module bundler’s dynamic import API (e.g., import()) to fetch and execute the client code in parallel.
  • If the server encountered unresolved promises wrapped in <Suspense>, the payload contains placeholders. As the server resolves these promises, it streams subsequent chunks that instruct the client to resolve the placeholders.

3. Fiber Tree Reconciliation

Once the serialized nodes and referenced client code are resolved, the resulting React elements are passed to the client-side React reconciler.

React applies its standard diffing algorithm against the current Fiber tree. Because the wire format preserves element identities and explicitly separates Server Components (pure data) from Client Components (interactive elements), React updates only the changed parts of the DOM. Unchanged Client Components maintain their local state, such as active input focus, scroll positions, and form values, avoiding the full-page reset associated with traditional server-rendered HTML.
