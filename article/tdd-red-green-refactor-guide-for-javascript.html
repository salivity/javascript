TDD Red-Green-Refactor Guide for JavaScript

Test-Driven Development (TDD) is a software development methodology where automated tests are written before the functional code itself. Central to this approach is the Red-Green-Refactor cycle, a disciplined loop that directs how developers design, write, and polish features. In JavaScript, where dynamic typing and asynchronous logic frequently introduce subtle bugs, this workflow provides guardrails that ensure features are robust, minimal, and easily maintainable from the very first line of code.

Phase 1: Red (Write a Failing Test)

The process begins by defining what the feature should do before writing any application logic. Developers select a testing framework—such as Jest, Vitest, or Mocha—and write a unit test describing a small, specific piece of desired functionality.

For instance, if you need a utility function to calculate shopping cart discounts:

// cart.test.js
import { applyDiscount } from './cart.js';

test('applies a 10% discount to total amount', () => {
  const result = applyDiscount(100, 0.10);
  expect(result).toBe(90);
});

Running this test immediately results in a failure because the applyDiscount function either does not exist or does not return the expected output. In TDD, this failure is mandatory. It proves that the test is capable of catching missing functionality and prevents false positives where tests pass erroneously.

Phase 2: Green (Make the Test Pass)

Once the test fails for the right reason, the objective shifts to writing the minimal amount of JavaScript required to make the test pass. The focus here is strictly on functionality, not elegant architecture or optimization.

// cart.js
export function applyDiscount(price, discount) {
  return price - (price * discount);
}

Re-running the test suite executes the function, verifies the output, and turns the test status from red to green. Keeping this implementation minimal avoids over-engineering and prevents developers from writing unrequested code that lacks test coverage.

Phase 3: Refactor (Clean and Optimize)

With a green test confirming that the code meets specifications, the developer can now safely clean up the implementation. In this phase, the goal is to improve readability, eliminate duplication, and adhere to modern JavaScript best practices without changing the external behavior of the code.

During refactoring, you might handle edge cases, simplify logic, or improve variable naming:

// cart.js
export function applyDiscount(price, discountRate) {
  if (price < 0 || discountRate < 0 || discountRate > 1) {
    throw new Error('Invalid price or discount rate');
  }
  return Number((price * (1 - discountRate)).toFixed(2));
}

Because the test suite runs continuously, any accidental regressions introduced during refactoring are caught instantly. Once the code is clean and the tests remain green, the developer writes the next failing test for a new requirement—such as handling invalid inputs—and repeats the loop.

How the Workflow Guides Feature Implementation

The Red-Green-Refactor workflow transforms feature development from a speculative task into an iterative, verifiable process.

  1. Prevents Feature Creep: Writing tests first forces developers to think through acceptance criteria and implement only what is required to satisfy the specification.
  2. Clarifies API Design: Writing the test acts as a trial run for consuming the function or module, exposing clunky interfaces or poorly structured parameters before implementation begins.
  3. Supports Asynchronous Patterns: In JavaScript, handling Promises and async/await flows is prone to unhandled rejections. Structuring tests first forces the developer to explicitly handle both resolved values and error states.
  4. Enables Confident Modernization: With comprehensive test coverage established during the Red and Green phases, developers can freely upgrade packages, swap libraries, or adopt newer ECMAScript features during the Refactor phase without fear of breaking production code.
