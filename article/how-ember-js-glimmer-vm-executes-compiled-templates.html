How Ember.js Glimmer VM Executes Compiled Templates

This article explains how the Ember.js Glimmer Virtual Machine (VM) executes compiled component templates in modern web browsers. It covers the transformation of Handlebars templates into lightweight bytecode during the build process, the separation of initial rendering and re-rendering via the Append and Update virtual machines, and the mechanism by which the VM applies surgical, performant updates to the DOM using tracked references.

Build-Time Compilation to Wire Format

Instead of sending raw Handlebars strings or heavy Abstract Syntax Trees (ASTs) to the browser, Ember.js compiles templates ahead of time during the build step. The Glimmer compiler processes template markup, dynamic bindings, and control structures, outputting an intermediate representation known as the "wire format."

This wire format consists of low-level JSON arrays representing bytecode instructions (opcodes). By shifting the parsing and optimization overhead to build time, the browser receives a compact, serializable instruction set that requires no runtime template parsing.

The Virtual Machine Architecture

The Glimmer engine executes these compiled opcodes inside a register-based virtual machine written in JavaScript. To optimize both initial page loads and ongoing updates, Glimmer separates execution into two distinct runtime subsystems:

  1. The Append VM: Responsible for the initial creation and insertion of DOM nodes.
  2. The Update VM: Responsible for evaluating dynamic changes and executing targeted DOM updates when application state shifts.

Executing Initial Render with the Append VM

When a component renders for the first time, the Append VM iterates through the compiled bytecode sequentially. It uses internal registers to maintain context, such as the current DOM insertion point, active components, and dynamic variable scopes.

As the Append VM encounters structural opcodes (such as instructions to create an element or set a static attribute), it manipulates the browser's DOM directly using standard browser APIs.

When the Append VM encounters dynamic content—such as {{this.title}} or a conditional block—it does two things:

  1. It resolves the current value through a "Reference" object and renders it to the screen.
  2. It emits a specialized "update opcode" into a separate, linear list of instructions stored in memory.

Reactivity and Dirty Checking via References

Glimmer tracks dynamic data through an abstraction layer called References. A Reference represents a dynamic path in the application state and is bound to a revision tag (associated with Ember's @tracked reactivity system).

During the initial pass, each dynamic location in the template retains a reference to its source tag. When tracked properties are mutated in JavaScript, their associated tags are incremented. The Glimmer VM does not track DOM nodes directly; it tracks the validity of these computational tags.

Surgical DOM Patching with the Update VM

When Ember schedules a re-render, the Append VM is completely bypassed. The Glimmer VM instead invokes the Update VM, which loops strictly through the list of update opcodes generated during the initial render.

For each update opcode:

  1. The Update VM checks whether the revision tag on the dynamic reference has changed since the last execution.
  2. If the tag is unchanged, the VM immediately skips the instruction without touching the DOM or re-evaluating the JavaScript property.
  3. If the tag is dirty, the reference re-evaluates the dynamic value, compares it to the previous value, and issues a targeted DOM mutation (such as updating a text node's nodeValue or modifying an element attribute).

By executing a flat array of primitive bytecode instructions and skipping stable parts of the template tree at the opcode level, the Glimmer VM achieves fast re-renders without maintaining a costly, memory-heavy Virtual DOM tree.
