How to Track Asset Preloading in JavaScript Games

Asset preloading tracks percentage progress by calculating the ratio between completed load operations and the total volume of game resources scheduled for retrieval. This article explains the two primary methods used in JavaScript game development—count-based tracking and byte-based streaming—and demonstrates how to aggregate these metrics into a smooth, accurate loading bar for game engines and web applications.

The Basic Progress Formula

At its core, all progress tracking relies on a straightforward calculation:

\[\text{Percentage} = \left( \frac{\text{Current Progress}}{\text{Total Expected}} \right) \times 100\]

The difference between preloading implementations lies in how "Current Progress" and "Total Expected" are measured.

Count-Based Tracking

Count-based tracking is the simplest and most common approach. It treats every asset (image, sound, or JSON file) as a single unit. A manager initializes a counter with the total number of assets, increments a completed counter whenever an asset triggers an onload or canplaythrough event, and recalculates the percentage.

class AssetLoader {
  constructor() {
    this.totalAssets = 0;
    this.loadedAssets = 0;
  }

  loadImage(url) {
    this.totalAssets++;
    return new Promise((resolve, reject) => {
      const img = new Image();
      img.onload = () => {
        this.loadedAssets++;
        this.updateProgress();
        resolve(img);
      };
      img.onerror = reject;
      img.src = url;
    });
  }

  updateProgress() {
    const percent = Math.floor((this.loadedAssets / this.totalAssets) * 100);
    console.log(`Loading: ${percent}%`);
  }
}

The drawback of this method is uneven pacing: loading a 50MB sound file counts the same as loading a 2KB JSON configuration, causing the loading bar to stall on large files and jump quickly on small ones.

Byte-Based Tracking

Byte-based tracking monitors the exact number of bytes transferred over the network, providing smooth and accurate progress regardless of file size disparities.

Using XMLHttpRequest

The legacy XMLHttpRequest API provides native progress tracking via the onprogress event:

function loadAssetWithProgress(url, onProgress) {
  return new Promise((resolve, reject) => {
    const xhr = new XMLHttpRequest();
    xhr.open('GET', url, true);
    xhr.responseType = 'blob';

    xhr.onprogress = (event) => {
      if (event.lengthComputable) {
        onProgress(event.loaded, event.total);
      }
    };

    xhr.onload = () => resolve(xhr.response);
    xhr.onerror = reject;
    xhr.send();
  });
}

Using Fetch and ReadableStream

Modern web games prefer the fetch API. Tracking byte progress with fetch requires reading the Content-Length header and consuming the response body as a stream via ReadableStreamDefaultReader:

async function fetchWithProgress(url, onProgress) {
  const response = await fetch(url);
  const contentLength = +response.headers.get('Content-Length');
  const reader = response.body.getReader();
  
  let receivedLength = 0;
  const chunks = [];

  while (true) {
    const { done, value } = await reader.read();
    if (done) break;

    chunks.push(value);
    receivedLength += value.length;
    
    if (contentLength) {
      onProgress(receivedLength, contentLength);
    }
  }

  return new Blob(chunks);
}

Weighted Asset Tracking

When mixing raw network requests with proprietary engine loaders (such as Three.js texture loaders or Web Audio decoders), developers use a weighted system. Each asset or loading phase is assigned an estimated weight based on its expected payload:

const assetManifest = [
  { url: 'audio/bgm.mp3', weight: 40 },
  { url: 'textures/atlas.png', weight: 50 },
  { url: 'data/levels.json', weight: 10 }
];

const totalWeight = assetManifest.reduce((acc, a) => acc + a.weight, 0);
let currentWeight = 0;

function completeAsset(weight) {
  currentWeight += weight;
  const percentage = (currentWeight / totalWeight) * 100;
  renderProgressBar(percentage);
}

Decoupling Progress from Rendering

Directly tying UI updates to load events can make the loading bar feel jerky. Game engines usually decouple asset callbacks from the screen render loop. The loader records the targetPercentage, while the render loop uses linear interpolation (lerp) to advance the visible loading bar smoothly toward that target:

let displayedPercent = 0;
let targetPercent = 0;

function gameLoop() {
  // Move displayed progress toward target by 5% of the distance each frame
  displayedPercent += (targetPercent - displayedPercent) * 0.05;

  renderBar(displayedPercent);

  if (displayedPercent < 99.9) {
    requestAnimationFrame(gameLoop);
  }
}

This separation hides micro-stutters during network spikes and parsing operations, producing a consistent user experience during the loading phase.
