How tRPC Works: Type Safety Without Code Generation

This article explains how tRPC achieves seamless, end-to-end type safety between client and server applications without relying on code generation, schema compilation, or intermediate build steps. By utilizing TypeScript's advanced type inference, static type exports, and JavaScript runtime Proxies, tRPC bridges the gap between backend logic and frontend consumption directly at compile time.

TypeScript Type Inference at the Core

Traditional type-safe APIs (like GraphQL, gRPC, or OpenAPI-based tools) require an intermediate schema file and a build-step code generator to produce client-side SDKs and types. tRPC eliminates this step by treating your backend code itself as the single source of truth.

When you define a procedure on a tRPC router, TypeScript automatically infers the input requirements and return types based on your validation schemas and resolver functions.

// Server procedure definition
export const appRouter = router({
  getUser: publicProcedure
    .input(z.object({ id: z.string() }))
    .query(async ({ input }) => {
      return { id: input.id, name: "Alice", role: "admin" };
    }),
});

Because TypeScript analyzes the implementation directly, it understands that getUser requires an object with a string id and returns an object containing an id, name, and role.

Exporting Types, Not Runtime Code

To expose these types to the frontend without leaking backend logic, secrets, or database connections, tRPC leverages TypeScript's export type syntax:

// Export only the type definition of the router
export type AppRouter = typeof appRouter;

Because this statement exports only a type definition rather than an actual JavaScript object, the bundler completely strips it from the production JavaScript output. No server dependencies, environmental variables, or implementation details are packaged into the client bundle. The client receives a purely static contract of the server's capabilities.

The JavaScript Proxy Architecture

Without generated client files, how does the client know how to make calls? tRPC uses the runtime JavaScript Proxy object.

When you instantiate a tRPC client, you pass the AppRouter type generic to the client creation function:

// Client instantiation
const trpc = createTRPCProxyClient<AppRouter>({
  links: [httpBatchLink({ url: '/api/trpc' })],
});

At runtime, trpc is a recursive Proxy. When you write trpc.getUser.query({ id: "1" }), the Proxy dynamically detects the property access paths (getUser) and the execution method (query). It intercepts this call and constructs a standard HTTP request to the corresponding endpoint (e.g., GET /api/trpc/getUser?input=...).

Simultaneously, TypeScript overlays the AppRouter type definitions directly on top of the Proxy. The IDE provides autocompletion and type checking for the procedure path, the input arguments, and the awaited return data, ensuring instant feedback if the backend schema changes.

Runtime Validation with Zod or Valibot

While TypeScript handles static compile-time safety, runtime network boundaries still require validation. tRPC integrates with validation libraries such as Zod, Valibot, or Superstruct.

These parsers serve a dual purpose:

  1. Compile Time: TypeScript infers the exact input shapes from the parser, giving the client compiler-level errors if arguments are missing or malformed.
  2. Runtime: The backend validates incoming network payloads before executing resolver logic, rejecting invalid HTTP requests immediately.

Summary

tRPC avoids code generation by exploiting the fact that full-stack TypeScript projects share a common type system. By extracting inferred types directly from backend resolvers, exporting purely static router types, and pairing them with a dynamic client-side Proxy, tRPC delivers compile-time verification and rich developer tooling with zero generation steps.
