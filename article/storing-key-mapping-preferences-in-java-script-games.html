Storing Key Mapping Preferences in JavaScript Games

In JavaScript game development, custom key mapping allows players to rebind controls to match their ergonomic or accessibility preferences. These custom configurations are managed by defining an in-memory control registry, capturing dynamic keyboard input through event listeners, and serializing the resulting mappings into client-side web storage APIs like localStorage or IndexedDB. By pairing persistent browser storage with fallback schemas, developers ensure that customized control schemes remain intact across play sessions and adapt gracefully to game updates.

Structuring the Control Registry

Before storing any user preferences, the game must define a default control schema. This schema maps abstract game actions (such as jump, moveLeft, or attack) to standard web keyboard identifiers, preferably using KeyboardEvent.code values (e.g., KeyW, Space, ArrowUp) rather than KeyboardEvent.key. Using event.code targets the physical location of the key on the keyboard, preventing layout-related issues across different language settings (such as QWERTY versus AZERTY).

const DEFAULT_KEY_BINDINGS = {
  moveUp: "KeyW",
  moveDown: "KeyS",
  moveLeft: "KeyA",
  moveRight: "KeyD",
  jump: "Space",
  attack: "KeyJ"
};

let currentKeyBindings = { ...DEFAULT_KEY_BINDINGS };

Capturing Dynamic Rebinds in the UI

When a player enters a settings menu and clicks an action to rebind it, the game enters a "listening" state. An event listener attached to the window waits for the next keydown event, captures the incoming event.code, assigns it to the chosen action in the in-memory object, and removes the listener to prevent unintended reassignments.

function rebindAction(actionName, onComplete) {
  function handleInput(event) {
    event.preventDefault();
    
    // Prevent reserved system keys like Escape from being bound
    if (event.code !== "Escape") {
      currentKeyBindings[actionName] = event.code;
      saveKeyBindings(currentKeyBindings);
    }
    
    window.removeEventListener("keydown", handleInput);
    if (onComplete) onComplete(currentKeyBindings[actionName]);
  }

  window.addEventListener("keydown", handleInput);
}

Persisting Data with Web Storage

Because game configurations are relatively small JSON structures, the Web Storage API's localStorage is the standard tool for persisting preferences. Storing requires serializing the configuration object with JSON.stringify(), while retrieving requires parsing it back into a JavaScript object via JSON.parse().

const STORAGE_KEY = "game_custom_controls";

function saveKeyBindings(bindings) {
  try {
    const serializedData = JSON.stringify(bindings);
    localStorage.setItem(STORAGE_KEY, serializedData);
  } catch (error) {
    console.error("Failed to save key bindings to localStorage:", error);
  }
}

Loading Configurations and Merging Fallbacks

When the game initializes, it attempts to read the stored configuration. It is critical to merge stored preferences with the default bindings rather than replacing them completely. If a game update introduces new action bindings that do not exist in the player's previously saved configuration, merging ensures the game does not crash due to missing bindings.

function loadKeyBindings() {
  try {
    const savedData = localStorage.getItem(STORAGE_KEY);
    if (savedData) {
      const parsedBindings = JSON.parse(savedData);
      
      // Merge saved bindings over defaults to preserve new actions
      currentKeyBindings = {
        ...DEFAULT_KEY_BINDINGS,
        ...parsedBindings
      };
      return currentKeyBindings;
    }
  } catch (error) {
    console.warn("Corrupt key mapping data. Falling back to defaults.", error);
  }
  
  currentKeyBindings = { ...DEFAULT_KEY_BINDINGS };
  return currentKeyBindings;
}

Handling Complex Use Cases

For more advanced games, configurations can be expanded beyond simple one-to-one string mappings. The same storage workflow can be used for structures that support secondary bindings (e.g., mapping both KeyW and ArrowUp to the same action) or multiple input types by saving an array of codes or categorizing by device (keyboard, mouse button, or gamepad button indices). If the configuration includes cloud synchronization across devices, the serialized configuration is simply sent to a backend server using the fetch API instead of, or in addition to, writing to localStorage.
