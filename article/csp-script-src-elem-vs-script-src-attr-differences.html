CSP script-src-elem vs script-src-attr Differences

Content Security Policy (CSP) Level 3 introduced distinct directives to control JavaScript execution with greater granularity: script-src-elem and script-src-attr. While both directives regulate script execution to prevent Cross-Site Scripting (XSS) attacks, they apply to different structural locations within an HTML document. This article breaks down the technical differences between these two directives, explains their fallback mechanisms, and outlines why splitting them improves web application security.

The Core Difference

The distinction between script-src-elem and script-src-attr lies in whether the JavaScript originates from an HTML element or an HTML attribute:

  • script-src-elem governs <script> elements and script-loading elements.
  • script-src-attr governs inline event handler attributes and inline execution contexts.

Prior to CSP Level 3, the generic script-src directive governed both vectors simultaneously. The separation allows security teams to allow scripts loaded via elements while strictly forbidding risky inline event handlers.

Understanding script-src-elem

The script-src-elem directive applies exclusively to elements that load or execute scripts. It controls:

  • External script files loaded using <script src="...">.
  • Inline JavaScript written directly within <script>...</script> tags.
  • Declarative script preloading, such as <link rel="preload" as="script" href="..."> or <link rel="modulepreload" href="...">.
  • XSLT stylesheets that execute scripts.

For example, to allow external scripts from your own domain and scripts using a cryptographic nonce, you configure:

Content-Security-Policy: script-src-elem 'self' 'nonce-rAnd0m123';

Any attempt to execute an inline <script> tag lacking the matching nonce will be blocked by the browser.

Understanding script-src-attr

The script-src-attr directive controls JavaScript embedded inside HTML attributes. It controls:

  • Inline event handlers such as onclick, onload, onerror, onmouseover, and similar HTML attributes.
  • javascript: URLs used in navigation contexts, such as <a href="javascript:alert(1)">.

Because inline event handlers are historically one of the most common injection points for reflected and stored XSS, securing or eliminating them is a primary goal of robust CSP policies. To completely disable inline event handlers while retaining modern scripting, you configure:

Content-Security-Policy: script-src-attr 'none';

Under this rule, clicking <button onclick="doSomething()"> will fail, and the browser will log a CSP violation.

Fallback Hierarchy

Both directives fall back to parent directives if they are not explicitly declared in your policy:

  1. If script-src-elem is omitted, the browser falls back to script-src.
  2. If script-src-attr is omitted, the browser falls back to script-src.
  3. If script-src is also omitted, both fall back to default-src.

If you specify script-src-elem but leave out script-src-attr, any event handlers on the page will follow the rules of script-src (or default-src), not script-src-elem.

Practical Security Application

Splitting element and attribute rules solves a common architectural challenge: modern frontend frameworks often require loading script bundles via <script> tags, but modern security best practices discourage inline event handlers.

By utilizing both directives, you can construct an optimal defense:

Content-Security-Policy: script-src-elem 'self' https://trustedscripts.example.com; script-src-attr 'none';

This configuration ensures that legitimate script files load as intended, while any script injected by an attacker into an HTML attribute—such as <img src="x" onerror="stealData()">—is immediately neutralized.
