Server Reconciliation in JavaScript Game Development

This article explores server reconciliation, an essential netcode technique used in real-time multiplayer JavaScript games to maintain synchronization between clients and an authoritative server. You will learn the mechanics of client-side prediction, why prediction errors occur due to network latency, and the step-by-step process of using input histories and state rewinds to smoothly correct mispredictions without sacrificing responsiveness.

The Need for Client-Side Prediction

In real-time multiplayer games, waiting for a remote server to acknowledge player input introduces noticeable input lag. If a player presses the right arrow key, waiting 100 milliseconds for a round-trip network response makes the controls feel sluggish.

To eliminate this latency, games implement client-side prediction. The client applies user input immediately to the local state, allowing the character to move instantly on screen. Concurrently, the client transmits the input to the authoritative server over WebSockets or WebRTC DataChannels for verification.

What Is Server Reconciliation?

Server reconciliation is the process where a client checks its locally predicted state against the authoritative state returned by the server, identifies any discrepancies, and silently corrects them.

Because the server is the single source of truth, it might reject a client's predicted movement. For example, another player may have blocked the path, or a physics calculation produced a slightly different floating-point result. When the server’s response arrives, its state represents the past. Simply teleporting the player to the server's coordinates creates jarring visual artifacts known as "rubber-banding." Server reconciliation resolves this by rewinding the client to the verified server state and replaying all subsequent local inputs that the server has not yet processed.

How the Reconciliation Process Works

To implement server reconciliation in JavaScript, the client and server must track inputs using sequential identifiers.

1. Input Buffering and Sequence Numbering

Every frame the user generates input, the client assigns it an incrementing sequence number (or tick count). The client stores these inputs in a local array (an input buffer) alongside their simulated outcomes:

let inputSequenceNumber = 0;
const pendingInputs = [];

function handleInput() {
    const input = {
        sequenceNumber: ++inputSequenceNumber,
        dx: getHorizontalInput(),
        dy: getVerticalInput(),
        dt: deltaTime
    };

    // Apply prediction locally
    applyMovement(localPlayer, input);

    // Save for potential future reconciliation
    pendingInputs.push(input);

    // Send to authoritative server
    network.send({ type: 'INPUT', payload: input });
}

2. Authoritative Server Processing

The server collects inputs from the network, validates them against the game rules, updates the world simulation, and broadcasts an authoritative state packet. This packet includes the sequence number of the last input processed for that specific client:

// Server snapshot payload sent to client
{
    lastProcessedInput: 42,
    position: { x: 120.5, y: 84.0 },
    velocity: { x: 5.0, y: 0.0 }
}

3. Error Detection

When the client receives the server snapshot, it discards all stored inputs with a sequence number less than or equal to lastProcessedInput, as they are now confirmed:

function onServerUpdate(snapshot) {
    // Discard acknowledged inputs
    while (pendingInputs.length > 0 && pendingInputs[0].sequenceNumber <= snapshot.lastProcessedInput) {
        pendingInputs.shift();
    }

    // Compare server position against historical or current predicted position
    const errorThreshold = 0.001;
    const dx = Math.abs(localPlayer.x - snapshot.position.x);
    const dy = Math.abs(localPlayer.y - snapshot.position.y);

    if (dx > errorThreshold || dy > errorThreshold) {
        reconcile(snapshot);
    }
}

4. Replaying Unprocessed Inputs

If a mismatch exceeds an acceptable threshold, reconciliation triggers. The client resets its state to the server's snapshot and immediately reapplies all remaining inputs in pendingInputs in order:

function reconcile(snapshot) {
    // Rewind state to server's authoritative state
    localPlayer.x = snapshot.position.x;
    localPlayer.y = snapshot.position.y;
    localPlayer.vx = snapshot.velocity.x;
    localPlayer.vy = snapshot.velocity.y;

    // Fast-forward: Re-apply inputs that the server hasn't seen yet
    for (const input of pendingInputs) {
        applyMovement(localPlayer, input);
    }
}

Visual Smoothing

While replaying inputs corrects the underlying simulation state within a single JavaScript execution tick, large discrepancies can still cause a visible jitter. To handle this, game engines decouple the visual mesh or sprite position from the underlying physics coordinates. When reconciliation shifts the physics coordinates, the rendering system smoothly interpolates the render target toward the newly corrected position over several frames, masking the mathematical adjustment from the player's view.
