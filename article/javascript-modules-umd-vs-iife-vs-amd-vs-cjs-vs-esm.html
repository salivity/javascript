JavaScript Modules: UMD vs IIFE vs AMD vs CJS vs ESM

JavaScript module formats have evolved significantly to solve the challenges of code organization, scope isolation, and dependency management across browsers and server environments. This guide breaks down the core differences between the five major module and bundle formats—IIFE, AMD, CommonJS (CJS), UMD, and ECMAScript Modules (ESM)—explaining how they work, where they run, and when to use each.

IIFE (Immediately Invoked Function Expression)

An IIFE is a traditional JavaScript design pattern rather than a formalized module standard. It wraps code inside an anonymous function that executes immediately upon definition:

(function () {
  const secret = 'private';
  window.myModule = {
    getSecret: () => secret
  };
})();
  • Environment: Primarily legacy web browsers.
  • Loading: Synchronous, loaded via direct <script> tags.
  • Characteristics:
    • Prevents variable leakage into the global scope using closure.
    • Lacks native dependency management; dependencies must be manually ordered via <script> tags.
    • Produces code that attaches its public API directly to the global object (e.g., window).

AMD (Asynchronous Module Definition)

AMD was designed to bring modularity to client-side JavaScript, executing dependencies asynchronously without blocking page rendering. It was popularized by loaders like RequireJS.

define(['dependency1', 'dependency2'], function (dep1, dep2) {
  return {
    run: () => dep1.action()
  };
});
  • Environment: Client-side browsers.
  • Loading: Asynchronous.
  • Characteristics:
    • Uses a define() function to declare dependencies and module definitions.
    • Prevents UI blocking during script execution.
    • More complex syntax and requires a dedicated client-side module loader library to function.

CJS (CommonJS)

CommonJS was built to bring JavaScript outside the browser, serving as the foundational module format for Node.js.

const dep1 = require('dependency1');

function doWork() {
  dep1.action();
}

module.exports = { doWork };
  • Environment: Server-side runtimes (Node.js).
  • Loading: Synchronous.
  • Characteristics:
    • Uses require() for imports and module.exports or exports for public interfaces.
    • Modules are loaded synchronously, assuming files are stored locally on the disk.
    • Evaluates dependencies at runtime, which makes static analysis and dead-code elimination (tree-shaking) difficult.

UMD (Universal Module Definition)

UMD was created as a bridge pattern to support both AMD and CommonJS environments with a single codebase, while also falling back to a global object when running in environments without module loaders.

(function (root, factory) {
  if (typeof define === 'function' && define.amd) {
    // AMD
    define(['dependency1'], factory);
  } else if (typeof module === 'object' && module.exports) {
    // CommonJS
    module.exports = factory(require('dependency1'));
  } else {
    // Browser Global
    root.myModule = factory(root.dependency1);
  }
}(typeof self !== 'undefined' ? self : this, function (dep1) {
  return { /* module definition */ };
}));
  • Environment: Universal (browsers, Node.js, AMD loaders).
  • Loading: Adapts dynamically to the environment (synchronous or asynchronous).
  • Characteristics:
    • Implemented as an IIFE wrapper checking for the existence of module interfaces.
    • Ideal for publishing third-party libraries across diverse developer toolchains prior to modern standardization.
    • Adds boilerplate overhead to the bundle.

ESM (ECMAScript Modules)

ESM is the official, standardized module system introduced in ECMAScript 2015 (ES6). It is natively supported in modern browsers and current versions of Node.js.

import { action } from 'dependency1';

export function doWork() {
  action();
}
  • Environment: Universal native standard (modern browsers, Node.js, Deno, Bun).
  • Loading: Asynchronous in browsers (<script type="module">), asynchronous or synchronous resolution depending on runtime.
  • Characteristics:
    • Uses explicit import and export statements.
    • Statically analyzable: import paths and exported symbols are determined at compile-time, enabling tree-shaking and aggressive bundler optimizations.
    • Supports dynamic imports via import() for lazy-loading.

Key Comparison

Standardized No (Pattern) No (Community) No (Community) No (Pattern) Yes (ECMA)
Primary Target Legacy Web Browsers Node.js Universal Universal
Resolution Synchronous Asynchronous Synchronous Hybrid Static / Async
Tree-Shaking No No Minimal Minimal Native
Syntax Wrapper function define() require / module.exports Boilerplate wrapper import / export

Which Format to Use Today

  • ESM is the modern default for new applications, tools, and libraries. It provides optimal bundle sizes through tree-shaking and runs natively in standard environments.
  • CJS remains relevant for legacy Node.js services or packages that have not yet migrated to ESM.
  • UMD and IIFE are largely reserved for output targets that require direct compatibility with legacy applications via standard <script> tags without using build pipelines.
