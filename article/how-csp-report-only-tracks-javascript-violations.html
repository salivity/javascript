How CSP Report-Only Tracks JavaScript Violations

The Content-Security-Policy-Report-Only (CSP-Report-Only) HTTP response header allows web developers to test security policies by monitoring JavaScript execution without enforcing blocking actions. When a script breaches the defined rules, the user's web browser intercepts the behavior, executes the script normally, and asynchronously transmits a detailed JSON-formatted violation report to a specified endpoint. This mechanism provides engineering teams with accurate, real-world telemetry on unauthorized inline scripts, insecure eval() calls, and third-party script injections without risking site breakage.

Setting Up the Header and Directives

To collect JavaScript metrics, the server delivers the Content-Security-Policy-Report-Only header within the HTTP response headers (it cannot be set via HTML <meta> tags). Within this header, developers define constraints specifically targeting script behavior using directives such as:

  • script-src: Restricts the authorized domains, hashes, or nonces allowed to execute JavaScript.
  • script-src-elem: Isolates controls explicitly to <script> tags.
  • script-src-attr: Targets inline event handlers like onclick.
  • unsafe-eval: Detects the usage of string-to-code execution methods like eval(), setTimeout(), and Function().

Alongside these constraints, the header specifies where the telemetry should be sent, using either the modern report-to directive or the legacy report-uri directive:

Content-Security-Policy-Report-Only: script-src 'self' https://trustedscripts.com; report-to csp-endpoint;

When using report-to, the site pairs this header with the standard Reporting-Endpoints header to declare the destination URL:

Reporting-Endpoints: csp-endpoint="https://analytics.example.com/csp-reports"

How the Browser Detects Violations

During DOM construction and runtime execution, the browser's JavaScript engine evaluates every script invocation against the defined policy. If an event occurs that would normally violate a strict CSP—such as an unapproved third-party tracker loading, an inline script lacking a cryptographic nonce, or an eval() statement—the browser's security layer flags the event.

Because the policy is set to "Report-Only", the browser does not halt script execution or throw a runtime error in the user interface. Instead, it logs the incident internally to the developer console and queues a telemetry payload.

The Violation Report Payload

Once flagged, the browser compiles a structured JSON report detailing the exact nature of the violation. For legacy implementations, this is sent with the application/csp-report content type containing a csp-report object:

{
  "csp-report": {
    "document-uri": "https://example.com/checkout",
    "referrer": "https://example.com/cart",
    "violated-directive": "script-src 'self' https://trustedscripts.com",
    "effective-directive": "script-src",
    "original-policy": "script-src 'self' https://trustedscripts.com; report-uri /csp-report-endpoint",
    "disposition": "report",
    "blocked-uri": "https://unauthorized-cdn.com/malicious.js",
    "line-number": 42,
    "column-number": 15,
    "source-file": "https://example.com/static/bundle.js",
    "status-code": 200
  }
}

Modern browsers using the Reporting API send this data via application/reports+json, wrapping the payload inside an array of report objects that include additional metadata, such as user agent context and relative timestamps.

Key metrics captured in the payload include:

  • effective-directive: Identifies whether the violation was an inline element, attribute, or source domain violation.
  • blocked-uri: Displays the full URL of the offending script, or identifiers like inline and eval.
  • source-file, line-number, and column-number: Pinpoints the exact file and position where the script execution originated, assisting in debugging legitimate application code.
  • disposition: Clarifies that the state was report rather than enforce.

Asynchronous Data Dispatch

The browser dispatches these violation reports in the background via HTTP POST requests. To ensure that metric collection does not degrade website performance or network availability for the end user, browsers batch reports and transmit them during idle CPU cycles or just before page unload using non-blocking transport mechanisms similar to the Beacon API.

The receiving server or telemetry collector parses these JSON payloads, aggregates the occurrence counts, and exposes trends across user sessions, script sources, and application routes.
