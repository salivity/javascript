How Babylon.js Integrates Havok and Cannon Physics

Babylon.js enables real-world simulation in web applications through a decoupled physics architecture that abstracts complex mathematical engines into unified, developer-friendly APIs. By utilizing a plugin-based system, the framework allows developers to seamlessly switch between different physics backends—such as the high-performance, WebAssembly-powered Havok engine or the pure-JavaScript Cannon.js—without needing to rewrite mesh interactions, event listeners, or rendering logic. This article explains how Babylon.js abstracts physics engines, manages communication between JavaScript and native code, and synchronizes physical simulations with the visual render loop.

The Plugin Abstraction Layer

At the core of Babylon.js's physics integration is an abstraction layer represented by the IPhysicsEnginePlugin interface. Instead of coupling its rendering pipeline directly to a specific physics library's data structures, Babylon.js delegates simulation responsibilities to a dedicated plugin class.

The framework currently supports two main architectural paradigms:

  • Physics V1 (PhysicsImpostor): Used primarily by legacy engines like Cannon.js and Oimo.js. It pairs a Babylon mesh directly to a single impostor object that wraps mass, friction, and restitution.
  • Physics V2 (PhysicsBody and PhysicsShape): Introduced in Babylon.js 6.0 and tailored for modern engines like Havok. It separates the physical representation into dynamic bodies, collision shapes, and material properties, allowing for compound bodies and shared geometry instances.

Integrating Havok via WebAssembly

Havok integration represents the modern standard for Babylon.js physics. Because the core Havok engine is written in C++, it is compiled into WebAssembly (WASM) along with a lightweight JavaScript wrapper package (@babylonjs/havok).

  1. Initialization: The browser loads the Havok WASM binary asynchronously. Once instantiated, the engine exposes a low-level C++ memory interface to JavaScript.
  2. The Havok Plugin: Babylon.js initializes the HavokPlugin, passing the WASM instance to it. The plugin translates Babylon.js scene commands into calls that write directly to the WASM heap.
  3. Execution: Havok handles rigid body dynamics, continuous collision detection (CCD), constraints, and raycasting entirely within compiled WebAssembly. This delivers near-native performance while minimizing JavaScript garbage collection overhead.

Integrating Cannon.js via Pure JavaScript

Cannon.js operates entirely within the JavaScript runtime without WASM binaries. It integrates into Babylon.js via the CannonJSPlugin using the Physics V1 architecture.

  1. Direct Object Mapping: When a developer assigns a PhysicsImpostor to a mesh, the CannonJSPlugin creates corresponding native Cannon.js constructs, such as CANNON.Body and CANNON.Shape (e.g., spheres, boxes, or convex polyhedrons).
  2. Data Translation: Vector and quaternion mathematics are translated between Babylon.js types (BABYLON.Vector3, BABYLON.Quaternion) and Cannon types (CANNON.Vec3, CANNON.Quaternion) on every simulation frame.
  3. Execution: Because Cannon.js runs on the main JavaScript thread, it is straightforward to debug and bundle, though it is computationally heavier for scenes with complex geometry or hundreds of simultaneous collisions.

The Simulation and Synchronization Loop

Regardless of whether Havok or Cannon is loaded, Babylon.js synchronizes the physical simulation with the rendering loop through a standardized execution flow:

  1. Pre-Physics Step: Babylon.js collects external inputs, user forces, velocities, or kinematic transform updates applied during the frame and forwards them to the active physics plugin.
  2. World Step: The scene calls plugin.executeStep(deltaTime). Havok steps forward inside WASM; Cannon steps forward in JavaScript. During this step, the physics solver handles contact points, resolves collisions, and updates internal linear and angular momentum.
  3. Transform Synchronization: After the simulation step finishes, the plugin reads the updated positions and rotations from the physics bodies and applies them back to the Babylon.js TransformNode or Mesh objects.
  4. Render: The scene renders the updated mesh transforms to the WebGL or WebGPU canvas.

By separating the visual graph from the underlying simulation and bridging them through versioned plugin interfaces, Babylon.js provides a unified JavaScript workflow capable of driving both lightweight, accessible physics and high-end, native-grade WebAssembly simulations.
