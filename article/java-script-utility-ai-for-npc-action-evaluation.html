JavaScript Utility AI for NPC Action Evaluation

This article explores how Utility Artificial Intelligence (Utility AI) systems calculate, weigh, and select Non-Player Character (NPC) actions dynamically in JavaScript game development. You will learn the mathematical principles behind utility scoring, how to transform raw game state metrics using response curves, methods for combining multiple weighted considerations, and how to implement a clean, performant evaluation loop in JavaScript.

Understanding the Core Concept of Utility AI

Unlike Finite State Machines (FSMs) or Behavior Trees that rely on rigid transitions, a Utility AI scores every potential action based on the NPC's current environment and internal state. Each possible behavior (such as "Attack," "Take Cover," "Heal," or "Flee") is treated as an independent candidate.

The system scores each candidate between 0.0 (completely useless) and 1.0 (critically important). The action with the highest aggregate score—or a choice picked via weighted random selection—is executed for that game tick.

Normalization and Consideration Curves

The first step in evaluating choices is converting arbitrary game values (e.g., player distance in pixels, remaining health percentage, available ammo) into a normalized float between 0.0 and 1.0.

Linear mappings are rarely natural in games. Instead, developers use mathematical response curves to model behavioral urgency:

  • Linear: Utility increases proportionally with input (\(y = x\)). Useful for simple meters like remaining stamina.
  • Quadratic/Exponential (\(y = x^k\)): Utility remains low until a critical threshold is reached, then spikes. Ideal for low-health panic states.
  • Logistic/Sigmoid: Produces an S-curve, providing smooth transitions at both extremes with rapid change in the middle. Useful for threat proximity.
// Example response curve functions
const ResponseCurves = {
  linear: (x) => Math.max(0, Math.min(1, x)),
  quadratic: (x) => Math.pow(Math.max(0, Math.min(1, x)), 2),
  logistic: (x) => 1 / (1 + Math.exp(-10 * (x - 0.5)))
};

Combining Multiple Considerations

A single action often requires analyzing several factors. For an NPC deciding whether to use a healing potion, considerations might include:

  1. Current health (lower health = higher utility).
  2. Potion inventory count (fewer potions = lower utility to preserve resources).
  3. Distance to the nearest enemy (closer enemy = lower utility due to interruption risk).

To combine these considerations into a single score, developers typically multiply them together. Multiplying ensures that if any single consideration drops to zero (e.g., having zero potions left), the overall utility for that action becomes zero instantly.

To prevent an increasing number of considerations from mathematically deflating the score toward zero, developers often apply a compensation factor or use a weighted geometric mean:

\[\text{Final Score} = \left( \prod_{i=1}^{n} s_i \right) \times \text{Action Weight}\]

Implementing the Evaluator in JavaScript

Here is a modular pattern for defining actions, evaluating their considerations, and selecting the optimal behavior in vanilla JavaScript:

class Action {
  constructor(name, weight = 1.0, considerations = []) {
    this.name = name;
    this.weight = weight;
    this.considerations = considerations;
  }

  evaluate(context) {
    if (this.considerations.length === 0) return 0;

    let finalScore = 1.0;

    for (const consideration of this.considerations) {
      const score = consideration(context);
      
      // If any consideration is invalid, the action cannot be performed
      if (score <= 0) return 0;

      finalScore *= score;
    }

    return finalScore * this.weight;
  }
}

// Sample considerations
const healthConsideration = (ctx) => {
  // Lower health returns higher utility
  const healthRatio = ctx.npc.health / ctx.npc.maxHealth;
  return ResponseCurves.quadratic(1 - healthRatio);
};

const enemyDistanceConsideration = (ctx) => {
  // Normalize distance to a range of 0 to 500 units
  const maxDistance = 500;
  const normalizedDistance = Math.min(ctx.distanceToEnemy / maxDistance, 1);
  return ResponseCurves.linear(normalizedDistance);
};

// Define an Action
const healAction = new Action('Heal', 1.2, [
  healthConsideration,
  enemyDistanceConsideration
]);

Selecting the Winning Action

Once all actions receive an evaluation score, the system decides which action to execute. There are two primary strategies for execution:

1. Absolute Highest Score (Winner-Takes-All)

The simplest approach is iterating over the evaluated actions and selecting the one with the highest numerical value.

function getBestAction(actions, context) {
  let bestScore = -1;
  let bestAction = null;

  for (const action of actions) {
    const score = action.evaluate(context);
    if (score > bestScore) {
      bestScore = score;
      bestAction = action;
    }
  }

  return bestAction;
}

2. Weighted Random (Softmax / Roulette Wheel)

To prevent NPCs from acting completely deterministically, developers use a weighted random algorithm. Scores are treated as probabilities, allowing lower-scoring but viable actions to occasionally be selected:

function getWeightedRandomAction(actions, context) {
  const scoredActions = actions.map(action => ({
    action,
    score: action.evaluate(context)
  })).filter(item => item.score > 0);

  const totalScore = scoredActions.reduce((sum, item) => sum + item.score, 0);
  if (totalScore === 0) return null;

  let randomPoint = Math.random() * totalScore;
  for (const item of scoredActions) {
    if (randomPoint < item.score) {
      return item.action;
    }
    randomPoint -= item.score;
  }

  return scoredActions[0].action;
}

Performance Considerations for JavaScript

  1. Avoid Object Allocation in the Loop: Recreating arrays, contexts, or closures inside the evaluate() cycle every frame leads to garbage collection spikes. Reuse flat context objects.
  2. Evaluation Frequency: Do not evaluate utility on every frame (\(60\text{Hz}\)). Instead, throttle the decision loop using timers (e.g., every \(100\text{ms}\)–\(250\text{ms}\)) or stagger evaluations across different frames for different NPC instances.
  3. Early Exits: Sort considerations so that computationally cheap conditions (like boolean inventory checks) run before costly checks (like pathfinding raycasts). If a cheap check returns 0, the evaluation halts immediately.
