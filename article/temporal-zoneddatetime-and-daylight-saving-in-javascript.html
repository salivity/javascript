Temporal.ZonedDateTime and Daylight Saving in JavaScript

This article provides an overview of the modern Temporal.ZonedDateTime object in JavaScript, focusing on how it manages timezone-aware timestamps and reliably resolves the challenges posed by Daylight Saving Time (DST). You will learn how Temporal.ZonedDateTime differs from the legacy Date object, how it manages clock jumps and overlaps during DST shifts, and how developers can utilize built-in disambiguation strategies to handle invalid or ambiguous local wall-clock times predictably.

What is Temporal.ZonedDateTime?

Temporal.ZonedDateTime is a timezone-aware date and time representation introduced in the ECMAScript Temporal API. Unlike the legacy JavaScript Date object—which internally stores only a Unix timestamp in UTC and relies on the execution environment's local runtime timezone for display—Temporal.ZonedDateTime combines an exact instant in time with a specific calendar system and an IANA time zone identifier (such as "America/New_York" or "Europe/London").

This design guarantees that conversions between absolute UTC instants and local wall-clock times are always explicit, deterministic, and independent of host environment settings.

The Problem with Daylight Saving Time

Daylight Saving Time creates two primary scheduling anomalies on local clocks:

  1. Gaps ("Spring Forward"): Clocks skip forward (typically from 02:00 to 03:00). As a result, local times between 02:00:00 and 02:59:59 do not exist.
  2. Overlaps ("Fall Back"): Clocks are set backward (typically from 02:00 back to 01:00). As a result, local times between 01:00:00 and 01:59:59 occur twice.

Historically, JavaScript's Date handled these transitions inconsistently across different browsers and runtimes, frequently causing silent data corruption and unexpected offsets.

How Temporal.ZonedDateTime Handles Transitions

When instantiating or modifying a Temporal.ZonedDateTime using local clock fields, the Temporal API automatically detects whether the requested time falls within a gap or an overlap. To resolve this, it provides a configurable disambiguation parameter with four strategies:

  • compatible (Default): Mirrors the behavior users naturally expect. During a gap, the wall-clock time is shifted forward by the length of the gap (e.g., 02:30 shifts to 03:30). During an overlap, it selects the earlier of the two possible instants.
  • earlier: During a gap, it adjusts backward to the instant immediately before the transition. During an overlap, it selects the first occurrence of that wall-clock time.
  • later: During a gap, it adjusts forward past the transition gap. During an overlap, it selects the second occurrence of that wall-clock time.
  • reject: Throws a RangeError whenever an ambiguous or non-existent local time is supplied, preventing silent adjustments.

Handling Gaps

When setting a non-existent wall-clock time during a spring transition:

// Clocks in New York skip from 02:00 to 03:00 on March 10, 2024
const zdt = Temporal.ZonedDateTime.from({
  year: 2024,
  month: 3,
  day: 10,
  hour: 2,
  minute: 30,
  timeZone: 'America/New_York'
}, { disambiguation: 'compatible' });

// Results in 2024-03-10T03:30:00-04:00[America/New_York]

Under the 'compatible' option, the time is pushed forward to 03:30. If 'reject' were specified instead, the engine would throw an exception.

Handling Overlaps

When creating a time that occurs twice during an autumn transition:

// Clocks repeat 01:00 to 02:00 on November 3, 2024
const earlier = Temporal.ZonedDateTime.from({
  year: 2024,
  month: 11,
  day: 3,
  hour: 1,
  minute: 30,
  timeZone: 'America/New_York'
}, { disambiguation: 'earlier' });

const later = Temporal.ZonedDateTime.from({
  year: 2024,
  month: 11,
  day: 3,
  hour: 1,
  minute: 30,
  timeZone: 'America/New_York'
}, { disambiguation: 'later' });

// earlier.offset is '-04:00' (EDT)
// later.offset is '-05:00' (EST)

By explicitly specifying 'earlier' or 'later', applications can unambiguously target the first or second iteration of a repeated hour.

DST-Aware Arithmetic

Temporal.ZonedDateTime also differentiates between calendar-based math and absolute duration math:

  • Adding Days: Adding one day (zdt.add({ days: 1 })) preserves the wall-clock time if possible, meaning the underlying elapsed duration may be 23, 24, or 25 real-world hours depending on whether a DST change occurred.
  • Adding Hours: Adding 24 hours (zdt.add({ hours: 24 })) advances the absolute timeline by exactly 24 hours, which may result in a different local wall-clock time if a DST transition occurred within that interval.
