Identify Detached Entities Using JS Heap Snapshots

Profiling memory heap snapshots is a diagnostic technique in JavaScript game development used to detect and eliminate memory leaks caused by detached entities. When dynamic game objects—such as enemies, projectiles, or particles—are removed from a scene graph, lingering references can prevent the JavaScript garbage collector from reclaiming their memory. By capturing baseline and post-cleanup heap snapshots through browser developer tools, developers can compare object counts, inspect the retaining paths from the garbage collection root, and isolate the exact references keeping obsolete entities in memory.

Understanding Detached Entities in Games

In JavaScript game programming, an entity is considered detached when it has been logically destroyed or removed from the active game loop, physics simulation, or display hierarchy, yet remains allocated in memory. This usually occurs with objects like sprites, Three.js meshes, or custom Entity-Component-System (ECS) instances. Even if an entity is removed from a parent container or scene array, the JavaScript runtime cannot free its memory if any other variable, closure, or data structure continues to hold a reference to it. Over time, these uncollected entities accumulate, inflating memory usage, degrading frame rates, and causing eventual browser tab crashes.

The Heap Profiling Workflow

To expose retained detached entities, developers use the Memory profiler found in modern browser developer tools (such as Chrome DevTools):

  1. Take a Baseline Snapshot: Load the game into a steady state (e.g., the main level before spawning dynamic objects) and record Snapshot 1.
  2. Execute the Gameplay Cycle: Trigger the creation and subsequent destruction of the entities in question, such as spawning a wave of enemies and destroying them.
  3. Trigger Manual Garbage Collection: Click the "Collect Garbage" (trash can) icon in DevTools to ensure the engine flushes any legitimately unreachable memory.
  4. Take a Follow-Up Snapshot: Record Snapshot 2 immediately after the garbage collection step.

Comparing Snapshots to Isolate Leaks

DevTools allows developers to switch the view mode of Snapshot 2 from "Summary" to "Comparison" against Snapshot 1. This filters the data to display the net delta of allocated objects between the two points in time.

By sorting by the # Alloc (number of allocations) or # Delta column, developers can immediately spot constructor types that should have returned to zero net change but instead show positive balances. For example, if 50 Enemy objects were spawned and defeated, the # Delta for the Enemy constructor should be 0. A positive number confirms that detached entities are persisting.

Reading Retainer Trees and Retained Size

Selecting a leaked entity within the heap snapshot reveals its Retainers panel. This view displays the chain of references (the retaining path) that connects the detached object back to a Garbage Collection (GC) root, such as the window object or an active execution context:

  • Shallow Size vs. Retained Size: The shallow size is the memory directly held by the entity itself, while the retained size is the total memory that would be freed if the entity and its isolated children were deleted. Detached entities often have small shallow sizes but massive retained sizes because they hold textures, geometry buffers, and nested component arrays.
  • Tracing the Culprit: Expanding the nodes in the Retainers panel reveals the exact variable, array, or closure pinning the entity. Common causes include unremoved event listeners, global tracking arrays, physics engine collision registries, or timer callbacks (setInterval/requestAnimationFrame) capturing the entity within their lexical scope.

Once the retaining reference is identified, developers can resolve the leak by explicitly nullifying references, clearing arrays, or unregistering event listeners as part of the entity's destruction lifecycle.
