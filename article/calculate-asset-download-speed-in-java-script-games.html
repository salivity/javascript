Calculate Asset Download Speed in JavaScript Games

This article explains how JavaScript game engines track and calculate download speeds for heavy assets using progress event monitoring. By measuring bytes transferred over high-resolution time deltas, developers can derive real-time transfer rates, smooth the data to prevent erratic UI updates, estimate remaining download times, and dynamically adapt game asset delivery based on the player's connection speed.

The Mechanism of Progress Events

In modern browser environments, tracking asset downloads typically relies on either the older XMLHttpRequest API with its ProgressEvent listener or the modern Fetch API coupled with a ReadableStream. Both mechanisms expose the fundamental data required for bandwidth calculation: the number of bytes transferred (loaded or chunk byte length) and, if supplied by the server via the Content-Length header, the total file size (total).

When downloading massive 3D models, audio banks, or texture atlases, the browser emits data chunks sequentially. Each time new data arrives, the runtime exposes an event or stream chunk indicating how much data has been received up to that exact moment.

The Math: Converting Byte Deltas to Speed

Raw speed is defined as distance over time, which translates in networking to data transferred over elapsed time. Calculating an accurate download rate requires tracking two continuous variables: the timestamp of the event and the cumulative bytes received.

Using performance.now() ensures sub-millisecond precision, avoiding the inaccuracies and system clock skew associated with Date.now(). The formula for instantaneous download speed is:

\[\text{Speed (Bytes/ms)} = \frac{\text{Current Loaded Bytes} - \text{Previous Loaded Bytes}}{\text{Current Timestamp} - \text{Previous Timestamp}}\]

To convert this value into a standard, human-readable format like Megabits per second (Mbps) or Megabytes per second (MB/s):

  • MB/s: Multiply the result (Bytes/ms) by \(1000\) to get Bytes per second, then divide by \(1{,}048{,}576\) (\(1024^2\)).
  • Mbps: Multiply Bytes per second by \(8\), then divide by \(1{,}000{,}000\) (or \(1{,}048{,}576\) depending on decimal vs. binary standard).

Implementation with Fetch and Streams

While XMLHttpRequest.onprogress is simple to bind, fetch() provides more granular control over heavy game assets through streaming:

async function downloadAssetWithSpeedTracking(url, onProgress) {
  const response = await fetch(url);
  const contentLength = +response.headers.get('Content-Length');
  const reader = response.body.getReader();

  let receivedLength = 0;
  let lastTime = performance.now();
  let lastLoaded = 0;

  while (true) {
    const { done, value } = await reader.read();
    if (done) break;

    receivedLength += value.length;
    const currentTime = performance.now();
    const timeDelta = currentTime - lastTime;

    // Throttle calculation to avoid divide-by-zero or micro-fluctuations
    if (timeDelta > 200) {
      const bytesDelta = receivedLength - lastLoaded;
      const bytesPerSecond = (bytesDelta / timeDelta) * 1000;
      const speedMBps = bytesPerSecond / (1024 * 1024);

      lastTime = currentTime;
      lastLoaded = receivedLength;

      onProgress({
        percent: contentLength ? (receivedLength / contentLength) * 100 : null,
        speedMBps: speedMBps,
        etaSeconds: contentLength ? (contentLength - receivedLength) / bytesPerSecond : null
      });
    }
  }
}

Smoothing Fluctuations: Moving Averages

Instantaneous network speed fluctuates wildly due to packet loss, TCP window scaling, and thread scheduling. Displaying raw instantaneous speed directly causes the loading interface to flicker and provides inaccurate time-to-completion (ETA) estimates.

To solve this, game engines apply an Exponential Moving Average (EMA) to smooth the readings:

\[\text{Smoothed Speed} = (\alpha \times \text{Current Speed}) + ((1 - \alpha) \times \text{Previous Smoothed Speed})\]

A smoothing factor (\(\alpha\)) between \(0.1\) and \(0.3\) dampens sudden spikes while keeping the calculation responsive to genuine network degradation or improvement.

Estimating Time to Completion (ETA)

With a smoothed speed metric, calculating the remaining download time becomes straightforward:

\[\text{Remaining Time (seconds)} = \frac{\text{Total Bytes} - \text{Loaded Bytes}}{\text{Smoothed Bytes Per Second}}\]

If the server does not send a Content-Length header (common with compressed streams like Gzip or Brotli when dynamic chunking is used), ETA and percentage completion cannot be determined mathematically from the stream alone. In these scenarios, games must supply pre-baked asset manifests that explicitly define file sizes ahead of time.

Practical Applications in Game Architecture

Beyond populating a loading bar, tracking download metrics in real time enables several advanced engine behaviors:

  1. Adaptive Asset Streaming: If download speeds fall below a critical threshold during initial load, the engine can fall back to lower-resolution texture sets or compressed audio bundles.
  2. Dynamic Thread Allocation: Web Workers handling background asset decompression can be throttled or prioritized depending on whether the bottleneck is network throughput or CPU decompression performance.
  3. Connection Quality Profiling: The initial splash screen download acts as an organic bandwidth benchmark, allowing the game to configure default texture quality settings before the player reaches the main menu.
