Compute Shaders for JavaScript GPU Particle Physics

This article explores how modern JavaScript game developers utilize WebGPU compute shaders to simulate millions of physics-driven particles directly on the GPU. By leveraging the WebGPU API and the WebGPU Shading Language (WGSL), developers can offload mathematical calculations—such as velocity integration, collision detection, and spatial partitioning—from the single-threaded JavaScript CPU environment to thousands of parallel GPU cores. You will learn the mechanics of storage buffers, compute workgroups, dispatch pipelines, and zero-copy rendering workflows that make high-performance browser simulations possible.

The Shift from CPU to GPU Simulation

Traditional JavaScript particle systems run on the CPU within the main browser thread or via Web Workers. The CPU calculates position, velocity, and lifespan for each particle sequentially before streaming updated coordinates to the GPU via vertex buffers every frame. When particle counts exceed tens of thousands, memory transfer overhead across the PCIe bus and JavaScript execution limits cause frame rate drops.

Compute shaders resolve this bottleneck by keeping simulation logic and particle data entirely on the GPU. Using the WebGPU API, JavaScript initializes compute pipelines that execute massively parallel programs written in WGSL. Because the data remains in VRAM, simulations scale from thousands to millions of interactive particles running at a stable 60 or 120 frames per second.

Memory Layout with GPU Storage Buffers

In a compute-driven architecture, particle attributes are stored in continuous blocks of GPU memory called storage buffers (GPUBuffer with usage flags GPUBufferUsage.STORAGE). JavaScript initializes these buffers once using typed arrays (typically Float32Array).

Common particle attributes include:

  • Position and Lifespan: vec3<f32> for coordinates, f32 for remaining life.
  • Velocity and Mass: vec3<f32> for directional speed, f32 for weight/inertia.
  • Color or Flags: vec4<f32> for visual tint or packed integer bitfields for state management.

To avoid memory alignment penalties and cache misses, data is arranged either as an Array of Structures (AoS) or a Structure of Arrays (SoA). A single struct combining position and velocity allows a compute thread to fetch all necessary simulation state for a particle in minimal memory transactions.

Parallel Execution: Workgroups and Invocations

When launching a compute shader, the GPU organizes execution into a hierarchy of threads:

  1. Invocations: Individual shader executions. In a particle system, one invocation typically updates one single particle.
  2. Workgroups: Collections of invocations that execute concurrently on a single compute unit and share fast on-chip memory (var<workgroup>). Common workgroup sizes are 64, 128, or 256 invocations.

In WGSL, the built-in variable @builtin(global_invocation_id) provides each thread with a unique 3D vector. The compute shader flattens this ID into a 1D index:

@compute @workgroup_size(64)
fn main(@builtin(global_invocation_id) global_id : vec3<u32>) {
    let index = global_id.x;
    if (index >= arrayLength(&particles)) {
        return;
    }
    
    // Physics update logic
}

In JavaScript, the execution is triggered using passEncoder.dispatchWorkgroups(Math.ceil(particleCount / 64)).

Simulating Physics: Integration and Forces

During each compute pass, the shader reads the current state of a particle, calculates applied forces, and applies numerical integration:

  • Force Accumulation: The shader aggregates external vectors such as gravity, drag, wind, and curl noise fields.
  • Euler or Verlet Integration: The particle's velocity is updated by acceleration multiplied by delta time (\(v = v + a \cdot \Delta t\)), and position is updated by velocity multiplied by delta time (\(p = p + v \cdot \Delta t\)).
  • Boundary and Static Collisions: Particles are tested against collision primitives (bounding boxes, analytical spheres, or Signed Distance Fields). When a penetration is detected, the position is projected back to the surface and the velocity vector is inverted along the collision normal with an energy restitution coefficient.

Particle-to-Particle Interactions

While independent forces (gravity, wind) execute in parallel without cross-thread communication, particle-to-particle physics (such as flocking, fluid dynamics, or granular collisions) requires spatial awareness. Because scanning every particle creates an \(O(N^2)\) workload, developers implement spatial partitioning directly on the GPU:

  1. Uniform Grids: The 3D world is subdivided into discrete cells. A compute pass assigns each particle a cell hash based on its position.
  2. GPU Sorting: Algorithms such as parallel Bitonic Merge Sort sort particle indices by their cell hash entirely within compute shaders.
  3. Neighbor Search: A separate compute shader reads sorted cell ranges to allow particles to query only adjacent grid cells for proximity checks, keeping performance near \(O(N)\).

Zero-Copy Rendering Direct to Screen

The primary architectural advantage of compute shaders in WebGPU is zero-copy rendering. In previous technologies like WebGL, reading compute results often required ping-pong framebuffers or reading data back to the CPU.

In WebGPU, a single GPUBuffer can be flagged with both GPUBufferUsage.STORAGE and GPUBufferUsage.VERTEX. Once the compute pass finishes writing the updated physics coordinates:

  1. The compute pass ends via computePass.end().
  2. A render pass begins on the same command encoder via commandEncoder.beginRenderPass().
  3. The render pass binds the exact same buffer as a vertex buffer or references it as a storage buffer inside the vertex shader.
  4. Instanced rendering draws billboarded quads, points, or meshes using the GPU-calculated positions without any CPU round-trips.

Through this pipeline, JavaScript acts purely as an orchestrator, setting uniforms such as delta time and dispatch counts, while the GPU autonomously handles the entire physics and visualization lifecycle.
