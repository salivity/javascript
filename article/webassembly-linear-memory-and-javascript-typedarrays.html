WebAssembly Linear Memory and JavaScript TypedArrays

WebAssembly linear memory allows WebAssembly modules and JavaScript to share data directly with high performance by mapping the same raw binary storage into both environments. Instead of copying or serializing data across the boundary, JavaScript can read from and write to WebAssembly memory using TypedArrays such as Uint8Array or Float32Array. This article explains how WebAssembly linear memory functions as an ArrayBuffer, how JavaScript constructs typed views on top of that buffer, and how to safely synchronize complex data structures between both runtimes.

The Underlying Mechanism: WebAssembly.Memory

WebAssembly represents its linear memory as an instance of WebAssembly.Memory. Under the hood, this memory is backed by a standard JavaScript ArrayBuffer (or SharedArrayBuffer if multi-threading is enabled). The memory can be allocated directly in JavaScript and passed into a WebAssembly module during instantiation, or it can be created within the WebAssembly module and exported to JavaScript.

Regardless of where it is created, JavaScript accesses this raw memory space through the .buffer property:

const wasmMemory = new WebAssembly.Memory({ initial: 1 }); // 1 page = 64KB
const rawBuffer = wasmMemory.buffer; // Underlying ArrayBuffer

Because this buffer exists inside the JavaScript engine's heap, both the WebAssembly instance and the JavaScript engine have direct access to the same contiguous byte space.

Mapping Data with TypedArrays

To read or modify this raw memory in JavaScript, you wrap slices of the ArrayBuffer inside a TypedArray (e.g., Int32Array, Float64Array) or a DataView. These views do not allocate new memory; they merely provide an interface that interprets the underlying bytes.

A typed view requires three key parameters:

  1. The target buffer: wasmMemory.buffer
  2. The byte offset: The starting address in WebAssembly memory where the data structure resides.
  3. The length: The number of elements to include in the view.

For example, if a WebAssembly module returns a pointer to an array of 32-bit floats:

// WebAssembly exports a pointer (offset) and a count
const ptr = wasmInstance.exports.get_data_pointer();
const count = wasmInstance.exports.get_data_count();

// Create a direct view on the WebAssembly memory
const floatArray = new Float32Array(wasmMemory.buffer, ptr, count);

// Direct read and write
console.log(floatArray[0]);
floatArray[0] = 42.5; // Immediately visible to WebAssembly

Mutations made by JavaScript to floatArray mutate the memory at address ptr immediately without data copying. Similarly, if the WebAssembly code updates the memory at that address, JavaScript reads the updated values on subsequent accesses.

Handling Structs and Complex Data

While arrays of primitive types map directly to single TypedArrays, compound structures like C structs require precise offset management:

  1. Memory Alignment: Compilers like Clang (via Emscripten) or rustc align fields according to target platform ABI rules (e.g., 4-byte alignment for 32-bit integers).
  2. Field Access: JavaScript can read individual struct fields by indexing specific byte offsets using a DataView or by creating multiple TypedArrays mapped to corresponding field offsets within the struct.

For example, a struct containing an integer ID (4 bytes) followed by a 32-bit floating-point value (4 bytes) can be inspected using DataView:

const structView = new DataView(wasmMemory.buffer, ptr, 8);
const id = structView.getInt32(0, true);      // Little-endian
const value = structView.getFloat32(4, true); // Little-endian

Memory Growth and Buffer Invalidation

WebAssembly linear memory can dynamically expand using the memory.grow instruction or the wasmMemory.grow() method. When WebAssembly memory grows, the runtime typically reallocates the underlying buffer to accommodate the new pages.

When this reallocation occurs, the previous ArrayBuffer becomes detached. Consequently, any existing TypedArray or DataView referencing the old ArrayBuffer becomes invalid and throws errors or reads zero-length arrays.

To handle memory growth safely:

  • Avoid keeping persistent long-lived references to TypedArray instances pointing to WebAssembly memory.
  • Re-instantiate views just before reading or writing data, or refresh cached views after any operation that might trigger memory.grow.
