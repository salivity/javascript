How Node.js async_hooks Traces Async Operations

The node:async_hooks module provides an internal API to monitor the creation, execution, and destruction of asynchronous resources in a Node.js application. By intercepting low-level C++ and JavaScript operations, it assigns unique identifiers to asynchronous events and registers lifecycle callbacks. This enables monitoring tools and context-tracking utilities, such as AsyncLocalStorage, to preserve state across concurrent, non-blocking operations without manually passing references through function signatures.

Core Concepts: Identifiers and Causality

At the heart of the tracing mechanism are two unique numeric identifiers assigned to every asynchronous resource:

  • asyncId: A unique number identifying the specific instance of an asynchronous resource for its entire lifetime.
  • triggerAsyncId: The asyncId of the resource or execution context that triggered the creation of the new asynchronous resource.

By pairing each resource's asyncId with its triggerAsyncId, Node.js constructs a causal dependency tree. When an incoming HTTP request initializes a timer or initiates a database query, the timer or query receives a distinct asyncId while recording the HTTP request’s asyncId as its triggerAsyncId. This parent-child mapping establishes context lineage across the asynchronous boundary.

The Lifecycle Hooks

A tracing instance created via async_hooks.createHook() tracks state transitions through five core callbacks:

  1. init(asyncId, type, triggerAsyncId, resource): Fired when an asynchronous object is instantiated. It exposes the resource type (such as TCPWRAP, PROMISE, or Timeout), the causality identifiers, and the underlying reference. Context stores allocate tracking data at this stage.
  2. before(asyncId): Fired immediately prior to the execution of the asynchronous resource’s user-land callback. Node.js updates its internal execution context so that any new async resources created within this callback inherit this asyncId as their triggerAsyncId.
  3. after(asyncId): Fired immediately after the callback execution completes. This signals that the active execution scope for the resource has concluded.
  4. destroy(asyncId): Fired when the resource is garbage-collected or explicitly closed at the C++ layer. Context trackers use this event to purge associated metadata from memory to prevent leaks.
  5. promiseResolve(asyncId): Specifically triggered when the resolve function of a Promise is invoked, which may occur prior to the execution of chained .then() callbacks.

Execution Context Tracking

The module maintains an internal execution stack that tracks what is actively executing on the main thread. When a callback begins, the runtime pushes the current asyncId to this stack, making it available via async_hooks.executionAsyncId().

When asynchronous operations are scheduled, the runtime captures the current executionAsyncId() and assigns it as the new operation's triggerAsyncId. When the event loop processes the completed task later, the before hook sets the active executionAsyncId back to that task's ID, restoring the logical continuity of the asynchronous chain.

Integration with the V8 Engine

Node.js bridges JavaScript operations with native C++ abstractions. For native handles such as file descriptors and network sockets, lifecycle events are dispatched directly from the C++ layer using internal hooks like AsyncWrap.

For standard JavaScript promises, Node.js hooks directly into the V8 engine's promise lifecycle via native V8 microtask hooks. This allows Node.js to register microtask queue transitions and retain execution context seamlessly across Promise.resolve(), await expressions, and chained callbacks.
