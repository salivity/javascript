Using Decision Tables for JavaScript Game Logic

Managing complex game states often leads to deeply nested conditionals and brittle code architectures that are difficult to debug. This article explores how decision tables resolve this issue in JavaScript game development by replacing tangled if/else ladders with declarative, tabular structures. By decoupling rule evaluation from action execution, decision tables clarify multi-variable states, streamline debugging, and make expanding game mechanics significantly faster.

The Problem with Deeply Nested Conditionals

In game loops, entities frequently react to a combination of dynamic conditions: player input, physical environment, resource meters, and status effects. Handling these with traditional control flow creates "arrow anti-patterns" or massive switch blocks:

if (player.isGrounded) {
  if (input.jump && player.stamina >= 10) {
    player.jump();
  } else if (input.attack && player.weaponDrawn) {
    player.attack();
  }
} else if (player.inWater) {
  if (input.jump) {
    player.swimUp();
  }
}

As new mechanics like status ailments or power-ups are introduced, every added condition increases cyclomatic complexity exponentially. Missing edge cases becomes common, and refactoring existing mechanics risks breaking unrelated states.

What is a Decision Table?

A decision table is a structured, matrix-based representation of conditions and their corresponding actions. It models inputs as columns or keys and determines the resulting system state without embedding logical branches directly into the execution flow.

In JavaScript, decision tables can be implemented effectively using arrays of rule objects, bitmasks, or compound key lookups via plain objects or Map instances.

Implementing a Decision Table in JavaScript

Consider a player character deciding between multiple states—running, jumping, wall-sliding, or falling—based on several environmental flags.

Instead of writing sequential branches, conditions and actions are structured declaratively:

const playerRules = [
  {
    name: 'Jump',
    when: (p, input) => p.isGrounded && input.jump && p.stamina >= 10,
    action: (p) => {
      p.velocityY = -12;
      p.stamina -= 10;
    }
  },
  {
    name: 'Wall Slide',
    when: (p, input) => !p.isGrounded && p.isTouchingWall && p.velocityY > 0,
    action: (p) => {
      p.velocityY = 2; // slow fall speed
    }
  },
  {
    name: 'Standard Fall',
    when: (p) => !p.isGrounded,
    action: (p) => {
      p.velocityY += 0.5; // normal gravity
    }
  }
];

function updatePlayerState(player, input) {
  const matchedRule = playerRules.find(rule => rule.when(player, input));
  if (matchedRule) {
    matchedRule.action(player);
  }
}

For discrete, binary conditions (e.g., isGrounded, hasWeapon, isStunned), you can achieve constant-time \(O(1)\) lookups using bitwise flags or string serialization:

const stateLookup = {
  // Key format: "isGrounded:hasStamina:inputAction"
  'true:true:attack': (player) => player.performGroundAttack(),
  'false:true:attack': (player) => player.performAirAttack(),
  'true:true:jump': (player) => player.jump(),
  'true:false:jump': (player) => player.pant(),
};

function resolveAction(player, actionType) {
  const stateKey = `${player.isGrounded}:${player.stamina > 0}:${actionType}`;
  const action = stateLookup[stateKey] || (() => {});
  action(player);
}

Key Advantages in Game Programming

1. Exhaustive Edge-Case Detection

By listing state variables as axes of a table, developers can visually or programmatically audit every possible permutation. This prevents unexpected states, such as a player initiating an attack while locked in hit-stun, from going unnoticed during development.

2. Separation of State Evaluation and Behavior

Conditional checks evaluate what the entity is, while actions dictate what it does. Separating these concerns makes mechanics modular. Modifying a jump requirement does not require altering physics handling, and updating an animation does not risk breaking collision logic.

3. Data-Driven Scalability

Because decision tables are plain JavaScript objects or arrays, they can be extracted into JSON files or external configuration sheets. Game designers can tune behaviors, adjust transition prerequisites, or disable mechanics directly without altering the underlying engine logic.

4. Simplified Unit Testing

Testing complex logic in a decision table does not require simulating multiple sequential game frames. Each rule is a pure condition function paired with an isolated mutation function, allowing individual transitions to be tested with simple, deterministic mock data.
