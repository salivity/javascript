Dangers of setInterval in JavaScript Game Loops

Using setInterval to drive a core game loop in JavaScript introduces significant performance and architectural risks. While it may appear to be a straightforward solution for triggering recurring logic and render passes, setInterval lacks synchronization with the display hardware, drifts over time due to JavaScript's single-threaded nature, and behaves unpredictably when browser tabs lose focus. This article examines the technical flaws of relying on setInterval for real-time game development and outlines why modern browser APIs are required for stable performance.

Inaccurate Timing and Drift

JavaScript operates on a single-threaded event loop. Functions scheduled via setInterval are not executed at precise hardware-level intervals; instead, they are queued as macro-tasks once the timer expires. If the call stack is occupied by heavy calculations, physics steps, or garbage collection, the callback is forced to wait.

This behavior causes significant timing drift. If an interval is set to trigger every 16.6 milliseconds (targeting 60 frames per second), the actual execution intervals will fluctuate wildly depending on CPU load. Over time, these delays accumulate, leading to stuttering, inconsistent game speeds, and broken physics simulations.

Screen Tearing and Lack of VSync Alignment

Displays refresh at fixed hardware frequencies—commonly 60Hz, 120Hz, or 144Hz. setInterval has no awareness of the monitor's vertical blanking interval (VSync).

When a game renders via setInterval, the draw call can occur in the middle of a screen refresh cycle. This mismatch causes screen tearing, where the top half of the screen displays one frame while the bottom displays the next. Even if the interval runs at an exact math-based rate, running out of phase with the hardware display creates visible micro-stutters and jittery motion.

Tab Inactivity and Browser Throttling

Modern web browsers optimize resource consumption by throttling inactive tabs. When a user switches to another tab or minimizes the browser, the browser aggressively reduces the frequency of setInterval timers, often clamping them to fire only once per second (1000ms) or stopping them entirely.

If a game relies on setInterval to calculate fixed-step physics, returning to the tab can cause severe errors. Depending on how delta time is handled, the game might attempt to process hundreds of queued frames in a single instant—a condition known as the "spiral of death"—freezing the browser tab or causing physics objects to pass straight through collision barriers.

Unnecessary Resource Consumption

Conversely, setInterval will attempt to continue running even when rendering is physically impossible or unnecessary, such as when the canvas is hidden behind another element or the window is minimized. This wastes CPU cycles, drains battery life on mobile devices, and generates unnecessary heat, degrading overall system performance.

The Modern Alternative: requestAnimationFrame

To build a reliable game loop in JavaScript, developers should avoid setInterval and use requestAnimationFrame combined with delta timing.

The requestAnimationFrame API is purpose-built for visual updates. It matches the refresh rate of the user's specific monitor, aligns execution with VSync to eliminate tearing, and automatically suspends execution when the tab is backgrounded. For deterministic physics, developers pair requestAnimationFrame with a fixed timestep accumulator, ensuring gameplay remains completely consistent regardless of fluctuating frame rates.
