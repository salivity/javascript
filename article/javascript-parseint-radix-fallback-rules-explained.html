JavaScript parseInt Radix Fallback Rules Explained

The parseInt() function in JavaScript converts a string into an integer according to a specified numeral system base, known as the radix. While specifying this radix is considered a best practice, omitting the argument causes JavaScript to infer the base automatically based on the input string's formatting. This article explains the exact fallback rules JavaScript uses when the radix parameter is omitted or set to undefined (or 0), highlights the historical differences between ECMAScript versions, and reviews common edge cases.

Modern Default Radix Behavior (ECMAScript 5+)

In modern JavaScript environments adhering to ECMAScript 5 and later, if no radix argument is supplied—or if the radix is set to 0 or undefined—the engine determines the base using the following sequence:

  1. Hexadecimal Base (16): If the input string begins with 0x or 0X (after leading whitespace is trimmed), the radix defaults to 16. The engine parses the remaining characters as a hexadecimal number.

    parseInt("0x10"); // Returns 16
parseInt("0XFF"); // Returns 255

  2. Decimal Base (10): If the string begins with any other character—including a leading zero (0) followed by digits—the radix defaults to 10.

    parseInt("42");   // Returns 42
parseInt("08");   // Returns 8

The Historical Octal Trap (ECMAScript 3)

In older JavaScript implementations governed by ECMAScript 3 (prior to 2009), strings starting with a leading 0 were interpreted as octal (base 8) rather than decimal.

Under ES3 rules:

parseInt("07"); // Returned 7
parseInt("08"); // Returned 0 (because 8 is not a valid digit in base 8)

This behavior caused widespread bugs in applications handling zero-padded inputs, such as dates and times. ECMAScript 5 formally removed this behavior, requiring modern engines to default leading zeros to base 10 instead of base 8.

Handling of Binary (0b) and Octal (0o) Prefixes

While modern JavaScript syntax supports binary (0b) and octal (0o) numeric literals, parseInt() does not automatically detect these prefixes when the radix is absent.

When encountering these prefixes without an explicit radix:

  • Parsing begins at 0.
  • The parser encounters b or o, which are invalid digits in decimal notation.
  • Parsing stops immediately, returning 0.
parseInt("0b101"); // Returns 0
parseInt("0o77");  // Returns 0

To parse binary or octal strings prefixed with these identifiers, you must pass the radix explicitly or use the Number() function:

parseInt("101", 2);  // Returns 5
Number("0b101");     // Returns 5
Number("0o77");      // Returns 63

Summary of the Radix Fallback Decision Tree

When evaluating parseInt(string) with no second argument:

  • Leading whitespace is ignored.
  • If the remaining string starts with 0x or 0X -> Radix is 16.
  • In all other cases -> Radix is 10.

To prevent unexpected behavior and maintain code clarity across all runtimes, always provide the radix argument explicitly (e.g., parseInt(value, 10)).
