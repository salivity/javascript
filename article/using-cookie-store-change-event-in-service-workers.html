Using Cookie Store Change Event in Service Workers

The Cookie Store API introduces an asynchronous, Promise-based mechanism for managing cookies, extending cookie access to contexts where the synchronous document.cookie interface is unavailable. In service workers, the Cookie Store change event enables background monitoring of cookie modifications—such as creations, updates, and deletions. By subscribing to specific cookie changes, a service worker can react to authentication updates, synchronize application state across tabs, and manage session lifecycles without requiring an active document window or relying on expensive polling strategies.

The Limitation of Traditional Cookie Handling

Historically, web workers and service workers could not access HTTP cookies directly because document.cookie is bound to the synchronous DOM environment. This limitation forced developers to pass cookie data manually between the main thread and service workers via postMessage, or rely on server-side synchronization. Because service workers run on background threads to handle network requests, push notifications, and caching, the absence of native cookie awareness created significant architectural hurdles for session-dependent logic.

How the Cookie Store API Enables Monitoring

The Cookie Store API resolves this limitation by exposing an asynchronous global cookieStore object in both window and service worker scopes. To listen for modifications, service workers utilize the CookieChangeEvent interface.

Unlike standard DOM environments where an event listener is directly added to cookieStore, service workers operate under an event-driven lifecycle where the worker may be terminated when idle. To ensure the service worker wakes up when a cookie changes, it must first register interest using the cookieStore.subscribeToChanges() method during lifecycle events, such as install or activate.

Subscribing to Changes

A service worker subscribes to specific cookies by defining the cookie names and URL paths it needs to monitor:

self.addEventListener('activate', (event) => {
  event.waitUntil(
    cookieStore.subscribeToChanges([
      {
        name: 'session_token',
        url: '/api'
      }
    ])
  );
});

Subscribing explicitly minimizes unnecessary wake-ups, conserving device resources and ensuring the service worker is only invoked when relevant data is altered.

Handling the Change Event

When a monitored cookie is created, updated, or removed—either via JavaScript using cookieStore.set() or through HTTP Set-Cookie response headers—the service worker's cookiechange event fires.

The event object passed to the handler is an instance of CookieChangeEvent, which categorizes modifications into two distinct arrays:

  • changed: An array of CookieListItem objects representing cookies that have been added or updated. Each item includes properties such as name, value, domain, path, and expires.
  • deleted: An array of CookieListItem objects representing cookies that were expired or explicitly removed.

Example Listener Implementation

self.addEventListener('cookiechange', (event) => {
  for (const cookie of event.changed) {
    if (cookie.name === 'session_token') {
      console.log(`New session token set: ${cookie.value}`);
      // Perform tasks such as updating cached headers or syncing state
    }
  }

  for (const cookie of event.deleted) {
    if (cookie.name === 'session_token') {
      console.log('Session token removed. Clearing cached user data.');
      // Invalidate credentials or purge sensitive caches
    }
  }
});

Core Advantages

  1. Non-Blocking Operation: Because the API is fully asynchronous, reading, writing, and monitoring cookies does not block the main thread or interrupt background network tasks.
  2. Lifecycle Independence: Service workers can wake up to process cookie changes even when no browser tabs for the origin are actively open.
  3. Cross-Tab Synchronization: A cookie update performed in one tab triggers the cookiechange event in the shared service worker, allowing the worker to broadcast updates or invalidate caches uniformly across all active clients.
