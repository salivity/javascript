How SSG Compiles JavaScript to Static HTML

Static Site Generation (SSG) transforms dynamic JavaScript component trees into pre-rendered, production-ready HTML files during a project's build phase. Instead of relying on a client's browser or a live web server to render pages on demand, SSG frameworks evaluate code inside an isolated Node.js environment. This process reads the component tree, executes build-time data-fetching operations, renders the resulting component hierarchy into an in-memory Virtual DOM, and serializes that structure into flat .html files alongside lightweight JavaScript bundles used for client-side interactivity.

1. Route Discovery and Dependency Resolution

The compilation process begins with the SSG engine scanning the project's file structure to identify entry points and define the site's routing tree. For dynamic routes, the compiler executes dedicated discovery functions (such as Next.js's getStaticPaths) to resolve parameter lists into a concrete set of URLs to generate.

Once the route map is established, a module bundler (such as Webpack, Rollup, or Vite) analyzes the JavaScript and TypeScript imports within each route. It resolves the full component dependency graph, tracing root layout components down to leaf components to ensure all dependencies are bundled for compilation.

2. Build-Time Data Fetching

Before rendering markup, the compiler resolves all asynchronous dependencies for each route. Components often require external data from APIs, databases, or local markdown files.

During the build:

  • The framework invokes build-specific data-loading functions (such as getStaticProps or Astro frontmatter scripts).
  • These functions run exclusively in a server-side Node.js environment and are stripped from the final client-side bundle.
  • The returned data is serialized into JSON payloads. These payloads serve two purposes: injecting data directly into components during the immediate build render, and saving static JSON files that the client will fetch during route transitions.

3. Virtual DOM Execution

Once data is injected, the framework instantiates the component hierarchy. In libraries like React, this step involves running the component functions or class constructors starting at the root page component and proceeding recursively through all nested children.

Because this step runs in Node.js rather than a browser, browser-specific APIs (such as window, document, or localStorage) are unavailable. The execution generates an in-memory representation of the UI—typically an abstract syntax tree or Virtual DOM object graph—containing HTML element tags, attributes, and resolved text content.

4. String Serialization

With the complete Virtual DOM resolved in memory, the engine serializes the object tree into raw HTML strings. In React-based SSG, this step relies on low-level server-rendering methods such as renderToString() or modern streaming equivalents like renderToPipeableStream.

The engine converts Virtual DOM nodes into their corresponding standard HTML tags. For example, JSX fragments such as <div className="card"><h1>{title}</h1></div> are converted into the literal text string <div class="card"><h1>Example Title</h1></div>. Custom component wrappers disappear, leaving only valid markup.

5. HTML Document Assembly and Output

The serialized component markup is injected into an outer HTML document shell that contains doctype declarations, <head> metadata, stylesheets, and <script> tags. The build engine writes this complete string to the output directory as an individual .html file matching the specific route (e.g., /about/index.html).

Along with the static HTML, the compiler outputs the client-side JavaScript bundles and inline state scripts. When a user requests the page, the server instantly delivers the raw HTML file for immediate visual display. Subsequently, the browser downloads the associated JavaScript to "hydrate" the page, attaching event listeners and restoring client-side reactivity to the already-rendered DOM elements.
