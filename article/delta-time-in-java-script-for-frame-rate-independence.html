Delta Time in JavaScript for Frame Rate Independence

Delta time is a fundamental concept in game development that decouples a game’s logic and physics updates from its rendering frame rate. In JavaScript, varying hardware capabilities and display refresh rates mean games run at different speeds on different machines unless explicitly controlled. This article explains the mechanics of delta time calculations using requestAnimationFrame, why it is essential for achieving frame rate independence, and how to implement it directly within your game loops to ensure consistent movement and gameplay across all devices.

The Problem with Fixed-Per-Frame Updates

In naive game loop implementations, entity updates are often tied directly to individual frames. For example, moving a character by a static value like position.x += 5 each time the render loop executes creates a dependency on hardware performance.

On a standard 60Hz monitor, that loop runs approximately 60 times per second, moving the character 300 pixels per second. However, on a 144Hz or 240Hz gaming display, the loop executes much faster, causing the character to move more than twice as fast. Conversely, if a device experiences performance drops and renders at 30 frames per second, the game will appear in slow motion. Tying movement directly to frame execution creates an unpredictable and unfair player experience.

What is Delta Time?

Delta time (commonly abbreviated as \(\Delta t\) or dt) represents the amount of elapsed time between the previous frame and the current frame. Instead of expressing movement and physical changes as "units per frame," delta time allows you to define changes as "units per second."

By multiplying an entity's velocity by this elapsed time fraction, the actual movement scales proportionally with the duration of the frame:

\[\text{New Position} = \text{Current Position} + (\text{Speed Per Second} \times \Delta t)\]

If a frame takes longer to render, \(\Delta t\) increases, and the object moves further in that single frame to compensate. If the frame renders quickly, \(\Delta t\) decreases, moving the object a smaller distance. In both scenarios, the total distance traveled over a real-world second remains identical.

Implementing Delta Time with requestAnimationFrame

In JavaScript, the standard method for running a game loop is requestAnimationFrame(). The browser automatically passes a high-resolution timestamp (a DOMHighResTimeStamp in milliseconds) to the callback function passed to requestAnimationFrame().

Here is a standard implementation:

let lastTime = 0;

function gameLoop(currentTime) {
  // Convert delta time to seconds
  const deltaTime = (currentTime - lastTime) / 1000;
  lastTime = currentTime;

  update(deltaTime);
  render();

  requestAnimationFrame(gameLoop);
}

// Start the loop
requestAnimationFrame((timestamp) => {
  lastTime = timestamp;
  requestAnimationFrame(gameLoop);
});

Applying Delta Time to Game Entities

Once calculated, pass deltaTime to the update routines of your game entities:

class Player {
  constructor() {
    this.x = 0;
    this.speed = 200; // Pixels per second
  }

  update(deltaTime) {
    // Moves consistently regardless of frame rate
    this.x += this.speed * deltaTime;
  }
}

Handling Edge Cases: The Delta Time Spike

While delta time creates consistent motion under normal variations, large pauses can disrupt the calculation. For example, if a user minimizes the browser tab or switches windows, requestAnimationFrame pauses. When the tab is refocused, the difference between currentTime and lastTime can be several seconds wide.

Unclamped, this massive delta time value can cause entities to teleport across the screen, pass through collision boundaries (known as tunneling), or crash physics engines. To prevent this, always clamp the maximum value of delta time:

const maxDelta = 0.1; // Maximum limit of 100 milliseconds
const deltaTime = Math.min((currentTime - lastTime) / 1000, maxDelta);

Clamping delta time ensures that if a severe frame drop occurs, the simulation slows down gracefully rather than calculating an excessively large jump in physical state.
