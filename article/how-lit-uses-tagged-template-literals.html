How Lit Uses Tagged Template Literals

The Lit library enables the creation of fast, lightweight Web Components by using native JavaScript tagged template literals to manage rendering. Instead of relying on a resource-intensive virtual DOM, Lit pairs the standard html tag function with browser-native HTML templates to identify dynamic content and surgically update only the DOM nodes that change. This article examines the mechanics behind tagged template literals in Lit, the separation of static structure from dynamic expressions, and the inner workings of Lit’s high-performance DOM update pipeline.

Understanding Tagged Template Literals

Tagged template literals are a native JavaScript feature introduced in ES2015. When a tag function is prepended to a template literal—such as html`

${name}
`—JavaScript invokes the function with distinct arguments: an array of static string chunks and the evaluated values of the interpolation expressions.

A critical performance characteristic of JavaScript engines is that the static strings array passed to a tag function maintains the exact same memory reference across multiple executions of the same code path. Lit relies on this referential identity to recognize whether a template's HTML structure has already been analyzed.

The TemplateResult Object

When a Lit component executes its render() method, returning an html`...` expression does not directly produce DOM nodes or parse raw HTML strings. Instead, it generates a lightweight TemplateResult object.

A TemplateResult stores two primary properties:

  1. A reference to the static strings array.
  2. An array containing the current evaluated values of the dynamic expressions.

Because creating this object involves no DOM manipulation and minimal memory allocation, re-running a component's render() method is extremely inexpensive.

First Render: Native <template> Preparation and Parts

During the initial render of a TemplateResult, Lit prepares the DOM structure using the native HTML <template> element:

  1. HTML Assembly and Markers: Lit takes the static strings array and joins them together, inserting special internal comments or attribute placeholders where dynamic expressions occur.
  2. Template Creation: This assembled string is parsed once by the browser into a native <template> element. The browser parses the HTML tree only once per unique template literal in your code.
  3. Part Mapping: Lit traverses the <template>'s DOM tree to locate the placeholders. For each placeholder, it records the exact node and creates a "Part" instance (such as a ChildPart, AttributePart, or BooleanAttributePart). These Parts act as direct pointers to dynamic locations in the DOM.
  4. Cloning and Value Assignment: Lit clones the template content using document.importNode(), binds the recorded Parts to the corresponding cloned nodes, and commits the initial dynamic values into those Parts.

Subsequent Renders: Targeted Dirty Checking

When component state changes and triggers a re-render, Lit skips DOM creation entirely:

  1. Lit checks the referential identity of the incoming TemplateResult strings array against the existing template. If they match, the structure is identical.
  2. Lit iterates through the array of dynamic values and performs a strict equality check (===) against the previous values stored in each Part.
  3. If an expression has not changed, Lit does nothing.
  4. If an expression has changed, the specific Part directly updates its target DOM node (e.g., modifying a text node's data property or calling setAttribute()).

Virtual DOM vs. Lit's Approach

Traditional virtual DOM libraries generate a full tree of JavaScript representations of the UI on every update and recursively diff that tree against the prior tree to calculate mutations. This process consumes memory and CPU cycles traversing both static and dynamic nodes.

Lit completely bypasses virtual DOM diffing. By leveraging tagged template literals, Lit distinguishes static boilerplate from dynamic expressions at the language level. Static DOM is never re-inspected, and dynamic DOM updates occur through direct, localized mutations, resulting in minimal overhead and superior runtime efficiency for Web Components.
