Sandboxing JavaScript with Null Origin Web Workers

Executing untrusted, user-provided JavaScript in the browser requires strict isolation to prevent cross-site scripting (XSS), data theft, and unauthorized access to application state. This article explains how to safely sandbox untrusted JavaScript by combining Web Workers with opaque (null) origins, outlining the browser security model, the implementation steps using sandboxed iframes, and essential controls for CPU limits and data exchange.

Why Standard Web Workers Are Not Enough

By default, Web Workers inherit the origin of the document that instantiates them. If a parent page at https://example.com spawns a dedicated worker using a standard script or a local Blob URL, that worker retains access to https://example.com.

Even though Web Workers lack direct access to the DOM (window, document), an inherited origin permits them to:

  • Access storage mechanisms such as IndexedDB and CacheStorage.
  • Issue authenticated network requests via fetch() or XMLHttpRequest containing ambient credentials (cookies and HTTP auth).
  • Read or overwrite sensitive persistent state shared across the same origin.

To neutralize these vectors, untrusted scripts must run inside an execution context assigned an opaque origin (null).

Enforcing a Null Origin

A Web Worker created inside an execution context that has an opaque origin will itself run with a null origin. An opaque origin disables access to IndexedDB, prevents reading standard storage, and causes all outgoing network requests to be treated as cross-origin without credentials.

The most reliable cross-browser pattern to achieve this consists of a two-tier sandbox:

  1. The Host Application: Spawns a hidden <iframe> configured with sandbox="allow-scripts". By omitting allow-same-origin, the browser forces the iframe into a unique, opaque (null) origin.
  2. The Sandboxed Iframe: Generates a Web Worker using a Blob URL. Because the iframe has an opaque origin, the worker inherits the null origin.

Step-by-Step Implementation

1. Create the Sandboxed Iframe Bridge

The host document embeds a lightweight iframe with restricted privileges.

<!-- In index.html -->
<iframe 
  id="sandboxBridge" 
  src="sandbox.html" 
  sandbox="allow-scripts" 
  style="display: none;">
</iframe>

2. Implement the Worker Dispatcher inside the Bridge

The sandbox.html document listens for incoming code from the parent, wraps it inside an isolated worker, and handles message relaying.

<!-- In sandbox.html -->
<!DOCTYPE html>
<html>
<head><meta charset="utf-8"></head>
<body>
<script>
  window.addEventListener('message', (event) => {
    // Only accept messages from the trusted parent origin
    if (event.origin !== 'https://example.com') return;

    const { code, inputData, id } = event.data;

    // Wrap untrusted code inside a Web Worker wrapper
    const workerScript = `
      self.onmessage = function(e) {
        try {
          // Execute untrusted code within a scoped context
          const userFunction = new Function('input', e.data);
          const result = userFunction(e.data.input);
          self.postMessage({ status: 'success', result: result });
        } catch (err) {
          self.postMessage({ status: 'error', error: err.message });
        }
      };
    `;

    const blob = new Blob([workerScript], { type: 'application/javascript' });
    const workerUrl = URL.createObjectURL(blob);
    const worker = new Worker(workerUrl);

    // Enforce execution timeout to mitigate infinite loops / DoS
    const timeoutId = setTimeout(() => {
      worker.terminate();
      URL.revokeObjectURL(workerUrl);
      window.parent.postMessage({ id, status: 'error', error: 'Execution timed out' }, 'https://example.com');
    }, 2000);

    worker.onmessage = (e) => {
      clearTimeout(timeoutId);
      worker.terminate();
      URL.revokeObjectURL(workerUrl);
      window.parent.postMessage({ id, ...e.data }, 'https://example.com');
    };

    worker.onerror = (e) => {
      clearTimeout(timeoutId);
      worker.terminate();
      URL.revokeObjectURL(workerUrl);
      window.parent.postMessage({ id, status: 'error', error: e.message }, 'https://example.com');
    };

    // Send payload to worker
    worker.postMessage({ code, input: inputData });
  });
</script>
</body>
</html>

3. Dispatch Jobs from the Host

The main application dispatches the untrusted code to the bridge via postMessage.

// In main.js
function runUntrustedCode(code, inputData) {
  return new Promise((resolve, reject) => {
    const bridge = document.getElementById('sandboxBridge').contentWindow;
    const messageId = crypto.randomUUID();

    function handleResponse(event) {
      // In null-origin iframes, event.origin can be the string "null"
      if (event.data && event.data.id === messageId) {
        window.removeEventListener('message', handleResponse);
        if (event.data.status === 'success') {
          resolve(event.data.result);
        } else {
          reject(new Error(event.data.error));
        }
      }
    }

    window.addEventListener('message', handleResponse);
    bridge.postMessage({ id: messageId, code, inputData }, '*');
  });
}

Critical Hardening Guidelines

  • Terminating Worker Instances: Untrusted code can trigger infinite loops (while (true) {}). Always set a strict timer in the supervising context to call worker.terminate(). Terminating the worker immediately frees the thread.
  • Network Isolation with CSP: While a null origin prevents cookie delivery on requests, the script could still make unauthorized outbound requests (e.g., pingback data exfiltration). Serve sandbox.html with a strict Content Security Policy header: Content-Security-Policy: default-src 'none'; script-src 'unsafe-inline' blob:;.
  • Data Serialization Limits: Avoid passing complex objects or functions through postMessage. Use structured cloning or JSON-serialized primitives to eliminate object-reference leaks.
  • Memory Management: Always revoke Blob URLs using URL.revokeObjectURL() once the worker has initialized to prevent client-side memory leaks over time.
