Frame Pacing in JavaScript Game Development

This article explores the concept of frame pacing in JavaScript game development, detailing why consistent frame delivery is far more important than raw frame rates for achieving smooth visuals. You will learn the mechanics behind frame pacing, how the browser’s execution model introduces visual stutter, and the specific programming techniques required to implement rock-solid frame delivery in web-based games.

What Is Frame Pacing?

Frame pacing refers to the consistency with which individual video frames are rendered and displayed on screen over time. While most developers focus on the overall Frames Per Second (FPS) metric, FPS only represents an average. A game can run at an average of 60 FPS while suffering from severe visual stutter if the time between individual frames (the frame time) fluctuates wildly.

On a standard 60Hz display, a new frame should ideally appear every 16.67 milliseconds. Frame pacing is the discipline of ensuring each frame arrives as close to that exact interval as possible, preventing uneven gaps that cause motion to appear jerky or jittery.

The Single-Threaded JavaScript Challenge

JavaScript operates on a single-threaded event loop shared by script execution, rendering, user inputs, and garbage collection. This environment creates distinct challenges for consistent frame pacing:

  • Garbage Collection (GC) Pauses: When the browser automatically reclaims memory, it can pause execution for several milliseconds. If this pause delays a frame render past the screen refresh deadline, the browser drops the frame, resulting in an immediate hitch.
  • Event Loop Congestion: Heavy calculations or unoptimized event handlers can monopolize the main thread, delaying the next frame cycle.
  • Variable Display Refresh Rates: Modern displays vary from 60Hz to 120Hz, 144Hz, or higher. Hardcoding assumptions about screen timing leads to frame pacing breakdowns on high-refresh-rate hardware.

Why Frame Pacing Is Critical for Smooth Motion

Human vision is exceptionally sensitive to irregular motion. A steady 30 FPS with perfect frame pacing often appears smoother to players than a game fluctuating wildly between 45 FPS and 60 FPS.

Without proper pacing, two main issues arise:

  1. Micro-Stuttering and Judder: If one frame takes 8ms to render and the next takes 24ms, the object in motion appears to jump unevenly across the screen, breaking visual immersion.
  2. Physics Instability: If physics calculations rely directly on unpredictable render timings, game objects can clip through geometry, move at variable speeds, or behave inconsistently depending on device load.

Techniques for Implementing Proper Frame Pacing

To achieve consistent frame delivery in JavaScript, developers must manage rendering and physics loops with precision.

1. Leverage High-Resolution Timestamps

Always use requestAnimationFrame() instead of setTimeout or setInterval. The browser passes a high-resolution timestamp (DOMHighResTimeStamp) directly to your callback. Use this value to measure the exact delta time elapsed since the previous frame rather than relying on Date.now().

2. Implement a Fixed Timestep with Interpolation

Decouple the game’s internal simulation from the display’s rendering schedule. Run game logic (physics, collisions, state updates) on a fixed timestep (e.g., exactly 60 updates per second) using an accumulator pattern.

When a render occurs between fixed updates, interpolate the visual positions of entities between their previous and current states. This ensures that physics remain deterministic while visual rendering adapts smoothly to any display refresh rate.

3. Eliminate Memory Allocations in the Game Loop

To avoid unpredictable garbage collection hitches:

  • Pre-allocate objects using object pools rather than creating new objects inside the render or update loops.
  • Avoid creating temporary arrays, closures, or short-lived data structures during frame processing.
  • Reuse existing vector and matrix instances.

4. Cap and Smooth Delta Time

External interruptions, such as tab switching or background processing, can cause sudden spikes in delta time. Always cap the maximum allowable delta time (e.g., to 100ms) to prevent the "spiral of death," where the engine tries to process too many fixed update steps in a single frame to catch up, completely destroying frame pacing.
