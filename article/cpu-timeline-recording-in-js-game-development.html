CPU Timeline Recording in JS Game Development

CPU timeline recording using browser developer tools is a performance profiling method that captures a detailed, chronological breakdown of CPU activity during gameplay. This article explains what CPU timeline recording is, how it captures script execution and frame rendering within the browser's performance panel, and how JavaScript game developers use this data to diagnose frame drops, eliminate garbage collection spikes, and maintain consistent frame rates.

Understanding CPU Timeline Recording

In web browsers such as Chrome, Firefox, and Safari, the developer tools feature a "Performance" or "Profiler" panel. When you start a CPU timeline recording, the browser logs every operation processed on the main thread alongside hardware events over a specified duration. The resulting output is visualized as a flame chart—a horizontal timeline showing function calls, execution times, rendering pipelines, and idle periods stacked vertically by call depth.

The Frame Budget in Game Programming

JavaScript games typically target 60 frames per second (FPS), providing a strict time budget of approximately 16.6 milliseconds per frame (or 8.3ms for 120 FPS). Within this window, the browser must execute the game loop logic, process input, run physics calculations, resolve collisions, issue draw calls (via Canvas 2D or WebGL), and paint the result to the screen.

A CPU timeline recording visually breaks down each frame into individual tasks. Any single frame exceeding the budget causes a noticeable stutter or hitch (jank) for the player. The recording clearly highlights these over-budget frames, often marking them in red or labeling them as "Long Tasks" (tasks taking longer than 50 milliseconds).

What the Timeline Measures

A typical CPU timeline recording captures several distinct phases of execution:

  • Scripting: The execution of your JavaScript code, including requestAnimationFrame callbacks, physics engines, AI routines, and state updates.
  • Rendering and Layout: Time spent calculating element styles, layout recalculations, and DOM interactions (primarily relevant for DOM-based games or UI overlays).
  • Painting and Compositing: Converting draw instructions into actual pixels on the screen, managing WebGL draw calls, and compositing layers on the GPU.
  • Garbage Collection (GC): Visualized as distinct pauses where the JavaScript engine halts or delays execution to reclaim memory. Excessive object allocations within the game loop create frequent GC pauses, easily identifiable as recurring spikes in the timeline.
  • Idle Time: The remaining time within a frame where the main thread is waiting for the next refresh cycle, indicating healthy performance headroom.

How Game Developers Use Timeline Recordings

To diagnose an issue, a developer starts a recording, triggers the problematic gameplay event (such as an explosion, a wave of enemies, or a scene transition), and stops the recording. By navigating the captured flame chart, developers can zoom into specific frames where the frame rate dipped.

Clicking on wide blocks in the flame chart reveals the exact functions consuming the most execution time, complete with links to the corresponding lines of source code. This allows developers to locate algorithmic bottlenecks—such as an unoptimized spatial partitioning system or costly matrix operations—and refactor them directly. Developers also inspect the memory graph below the CPU timeline to detect allocation churn and prevent garbage collection interruptions.
