MessagePort Structured Cloning in Node.js

This article provides an overview of how the Node.js worker_threads module leverages the structured clone algorithm through MessagePort to pass data across execution contexts. You will learn the mechanics behind the serialization and deserialization process, which JavaScript data types are supported, how circular references are preserved, and how transferring memory differs from standard deep copying.

The Structured Clone Mechanism

When communication occurs between threads in Node.js using MessagePort.prototype.postMessage(), the runtime does not share references to standard JavaScript objects. Instead, it relies on an implementation of the HTML structured clone algorithm, implemented internally through the V8 serialization API (v8.serialize and v8.deserialize).

When an object is passed to postMessage(), V8 traverses the object graph and serializes it into an internal binary format. This binary payload is then safely moved across thread boundaries and deserialized inside the receiving thread's heap, constructing entirely new object instances with identical state.

Supported and Unsupported Types

The structured clone algorithm supports a broader set of data types than JSON serialization:

  • Primitives: Strings, numbers, booleans, null, undefined, and BigInt.
  • Built-in Objects: Plain objects, arrays, Map, Set, Date, and RegExp.
  • Binary Data: ArrayBuffer, SharedArrayBuffer, and TypedArray views (such as Uint8Array).
  • Error Objects: Most native Error types retain their name, message, and stack trace.

However, certain entities cannot be cloned:

  • Functions and Closures: Attempting to pass a function throws a DataCloneError.
  • Prototypes: Prototype chains are not preserved. An instance of a custom class will deserialize as a plain Object containing the cloned instance properties.
  • Symbols and Native Handles: Most Symbol keys and system-level resources (such as active TCP sockets or database connections) cannot be cloned.

Preserving Object Graphs and Circular References

Unlike naive cloning mechanisms, the structured clone algorithm tracks references encountered during traversal. If an object references itself or if multiple properties point to the same object instance, that relationship is maintained:

const user = { name: "Alice" };
user.self = user; // Circular reference

const payload = {
  first: user,
  second: user
};

port.postMessage(payload);

On the receiving end, received.first and received.second will point to the same object reference, and received.first.self will reference received.first, avoiding infinite recursion and preserving identity integrity.

Cloning vs. Transferring

By default, structured cloning performs a deep copy of the data. For large datasets, such as multi-megabyte ArrayBuffer instances, this copy step introduces CPU overhead and increases memory consumption.

To avoid copying, MessagePort.prototype.postMessage(value, [transferList]) accepts a transfer list. Transferable objects include ArrayBuffer and MessagePort instances:

  • Cloning (Copy): The underlying memory is duplicated. Both sender and receiver maintain separate access to their own copies.
  • Transferring (Move): The memory backing the ArrayBuffer is detached from the sending thread and moved directly to the receiving thread with zero-copy overhead. After transfer, the buffer on the sending side has a byteLength of zero and becomes unusable.

Shared Memory Alternatives

For scenarios requiring concurrent reads and writes without cloning or transfer overhead, SharedArrayBuffer can be sent over a MessagePort. In this case, the structured clone algorithm does not copy the underlying memory; it clones only the wrapper reference. Both threads then access the exact same region of memory simultaneously, requiring synchronization primitives like Atomics to prevent race conditions.
