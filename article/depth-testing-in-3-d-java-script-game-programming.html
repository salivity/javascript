Depth Testing in 3D JavaScript Game Programming

Depth testing is a fundamental computer graphics technique that determines which 3D surfaces are visible to the camera and which should be hidden behind other objects. In 3D JavaScript game programming—typically powered by WebGL or libraries like Three.js—rendering objects solely based on draw order often causes distant objects to mistakenly appear in front of nearer ones. This article explains the mechanics of the depth buffer, breaks down the mathematical comparison process that eliminates visual overlap artifacts, and demonstrates how to implement depth testing properly within JavaScript-based rendering pipelines.

The Problem of Visual Overlap in 3D Rendering

When a GPU renders a 3D scene onto a 2D screen, it processes geometry as triangles and converts them into fragments (pixels). Without depth testing, the rendering engine typically relies on the order in which draw calls are executed. The last object drawn simply overwrites the pixels on the screen, a limitation known from the traditional Painter's Algorithm.

This approach fails in complex interactive environments. If a JavaScript game renders a distant mountain after drawing a nearby player character, the mountain will paint over the character, breaking spatial logic. Furthermore, intersecting meshes or complex concave geometries cannot be sorted accurately on an object-by-object basis.

What Is Depth Testing?

Depth testing solves visual overlap by evaluating depth values at the individual fragment level rather than the object level. It relies on a dedicated memory structure called the depth buffer (or Z-buffer), which mirrors the resolution of the screen.

Instead of storing color information, each entry in the depth buffer stores a floating-point value—usually normalized between 0.0 (near clipping plane) and 1.0 (far clipping plane)—representing the distance from the camera to the closest fragment rendered at that pixel coordinate.

How the Depth Test Works

During the rasterization phase of the rendering pipeline, the GPU executes the following sequence for every generated fragment:

  1. Depth Calculation: The GPU computes the fragment's distance from the camera along the Z-axis in screen space.
  2. Buffer Comparison: The GPU compares the fragment's calculated depth against the depth value currently stored in the depth buffer at that exact screen coordinate.
  3. Pass or Discard:
    • If the comparison condition passes (most commonly LESS or LEQUAL, meaning the new fragment is closer to the camera than the existing one), the fragment passes the test.
    • The new color is written to the color buffer, and the new depth value overwrites the old value in the depth buffer (known as depth write).
    • If the condition fails, the fragment is discarded entirely, preventing background geometry from obscuring foreground elements.

Implementing Depth Testing in JavaScript

Native WebGL

In raw WebGL, depth testing is disabled by default and must be explicitly configured in your setup routine:

// Enable the depth test capability
gl.enable(gl.DEPTH_TEST);

// Specify the comparison function (default is usually gl.LESS)
gl.depthFunc(gl.LEQUAL);

// In the render loop, clear both color and depth buffers every frame
gl.clear(gl.COLOR_BUFFER_BIT | gl.DEPTH_BUFFER_BIT);

Failing to clear the gl.DEPTH_BUFFER_BIT on each frame will cause the depth buffer to retain values from previous frames, resulting in new geometry failing depth checks and disappearing from view.

Three.js

High-level libraries like Three.js enable depth testing by default on the WebGLRenderer. However, developers frequently interact with depth testing via materials:

const material = new THREE.MeshStandardMaterial({
    color: 0x00ff00,
    depthTest: true,  // Determines whether to perform the depth test
    depthWrite: true  // Determines whether this object writes to the depth buffer
});

Handling Edge Cases: Z-Fighting and Transparency

  • Z-Fighting: When two surfaces exist at virtually the same depth coordinate, floating-point precision limitations in the depth buffer cause the surfaces to rapidly flicker over one another. This is mitigated by pulling the camera's near clipping plane as far forward as possible and pushing the far plane closer, concentrating depth precision where the action occurs.
  • Transparent Objects: Semi-transparent objects need to show geometry behind them while still testing against closer opaque surfaces. In JavaScript games, transparent meshes usually set depthWrite: false while keeping depthTest: true, and are rendered after all opaque objects from back to front.
