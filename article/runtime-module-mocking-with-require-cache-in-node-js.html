Runtime Module Mocking with require.cache in Node.js

Node.js uses the CommonJS module system to cache modules after their initial evaluation, storing them inside a globally accessible object known as require.cache. By directly inspecting, mutating, or deleting properties within require.cache, developers can manipulate module loading at runtime. This provides a mechanism for cache invalidation—enabling features like hot reloading without process restarts—as well as runtime module mocking, which allows test suites to inject mock dependencies without third-party mocking libraries.

Understanding the Structure of require.cache

When a file is imported using require(), Node.js resolves the absolute file path, executes the module's code, and stores the resulting module instance in require.cache.

The require.cache object uses absolute file system paths as its keys. Each entry maps to a Module object containing metadata such as the module's id, filename, loaded status, and its exported values under the exports property:

const filePath = require.resolve('./service');
console.log(require.cache[filePath]);

Because require.cache is a standard, mutable JavaScript object, any modification to it directly influences future calls to require().

Cache Invalidation

Cache invalidation is the process of forcing Node.js to discard a previously loaded module so that subsequent calls to require() re-read and re-execute the file from the disk. This is commonly used in development tools, configuration reloaders, and lightweight hot-reloading systems.

To invalidate a module, locate its absolute path using require.resolve() and delete the entry using the delete operator:

const targetPath = require.resolve('./config');

// Invalidate the cache
delete require.cache[targetPath];

// The file is re-read and re-executed from disk
const freshConfig = require('./config');

Caveats of Cache Invalidation

Deleting a module from require.cache only removes the reference held by the module loader. If other modules have already imported and retained a reference to the old exports, those modules will continue to use the stale reference. To achieve a complete reload across an application, every module in the dependency tree that depends on the invalidated module must also be purged from require.cache.

Runtime Module Mocking

In automated testing, isolating a unit under test often requires replacing external services, such as database drivers or network clients, with mock implementations. require.cache enables this by allowing you to inject custom exports before a module is consumed by the system under test.

To mock a module, preemptively populate require.cache with a dummy module definition:

const targetPath = require.resolve('./paymentGateway');

// Inject the mock implementation
require.cache[targetPath] = {
  id: targetPath,
  filename: targetPath,
  loaded: true,
  exports: {
    processPayment: async () => ({ success: true, transactionId: 'mock-123' })
  }
};

// Any module requiring './paymentGateway' receives the mock
const checkoutService = require('./checkoutService');

Once tests are complete, clean up the mock by either deleting the key from require.cache or restoring the original implementation to prevent mock leakage across test suites.

Limitations and ESM Compatibility

Direct manipulation of require.cache is specific to the CommonJS module system. ECMAScript Modules (ESM), loaded via import statements, use an asynchronous, static module graph managed internally by the V8 runtime. ESM does not expose an equivalent cache registry, meaning require.cache cannot be used to invalidate or mock native ES modules. In mixed environments, ensure that the target modules are exclusively CommonJS before relying on require.cache.
