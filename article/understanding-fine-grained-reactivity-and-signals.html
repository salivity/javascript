Understanding Fine-Grained Reactivity and Signals

Fine-grained reactivity is a modern web architecture pattern that updates only the specific parts of an application that rely on changed state, eliminating the need to re-execute entire component trees. At the core of this model are signals—reactive primitives that encapsulate values and automatically track where and how those values are read. This article breaks down the mechanics of fine-grained reactivity, detailing how signals dynamically record dependencies at runtime and how state changes propagate through an application with minimal overhead.

What Is Fine-Grained Reactivity?

In traditional component-based models (such as classic React), a change in state triggers a top-down re-render of the component and its children. The framework generates a new Virtual DOM tree, compares it against the previous tree (reconciliation), and updates the actual DOM accordingly.

Fine-grained reactivity bypasses the component boundary entirely. Instead of treating components as recurring units of execution, components run only once during setup. The framework binds data directly to the individual DOM nodes or derived computations that consume it. When a value changes, only the precise function, text node, or computed property tied to that specific value updates. This eliminates reconciliation overhead and guarantees targeted, deterministic updates.

The Structure of a Signal

A signal is an atomic unit of state consisting of three primary elements:

  1. A Value: The stored data of any type (primitive, object, array).
  2. A Getter: A read function that retrieves the current value and registers the current subscriber.
  3. A Setter: A write function that updates the value and notifies all registered subscribers.

In addition to signals, the system relies on observers (often called effects or computations). An observer is a function that runs automatically whenever the signals it depends on produce a new value.

How Signals Track Dependencies at Runtime

Dependency tracking in fine-grained systems does not rely on static code analysis, compilers, or manual dependency arrays like useEffect. Instead, it operates entirely at runtime using a dynamic subscription mechanism managed by an execution context stack.

1. The Global Context Stack

To track what code is currently running, the reactive runtime maintains an internal global variable or stack (often referred to as currentObserver or contextStack).

When an effect or computed signal runs:

  • The system pushes that observer onto the context stack.
  • The observer executes its inner function.
  • Once execution completes, the observer is popped off the stack.

2. The Read Phase (Dependency Registration)

Whenever an observer reads a signal during its execution, the signal's getter function is invoked. The getter performs two steps:

  1. It inspects the global context stack to see if an observer is currently running.
  2. If an active observer exists, the signal registers that observer in its internal set of subscribers. Simultaneously, the observer registers the signal in its set of dependencies (enabling bidirectional tracking for future cleanup).

Because registration occurs synchronously during code execution, dependencies are established automatically.

3. The Write Phase (Notification and Propagation)

When a signal's setter is invoked with a new value:

  1. The signal checks if the new value differs from the old value (typically using strict equality).
  2. If the value has changed, the signal loops through its subscriber set.
  3. Each subscribed observer is either scheduled to re-run or immediately re-executed.

When the observer re-runs, it repeats the read phase.

Handling Dynamic Dependencies and Conditionals

Runtime dependency tracking automatically adapts to branching logic within your code:

effect(() => {
  if (useFirstName()) {
    console.log(firstName());
  } else {
    console.log(lastName());
  }
});

If useFirstName() returns true, the effect reads firstName() and subscribes to both useFirstName and firstName. It does not subscribe to lastName.

If useFirstName() later changes to false, the effect re-runs. During this pass, it reads lastName() instead. Before each run, modern reactive libraries clear the observer's previous subscriptions, allowing the effect to record a fresh, accurate set of dependencies. This prevents memory leaks and avoids unnecessary runs triggered by inactive branches.

Key Benefits of Signal-Based Dependency Tracking

  • Automatic Precision: Developers do not need to maintain manual dependency lists, preventing stale closure bugs.
  • Zero Reconciliation Cost: State changes map directly to DOM updates without diffing Virtual DOM trees.
  • Composable Architecture: Signals can be created, shared, and combined anywhere in a codebase, completely independent of UI component lifecycles.
