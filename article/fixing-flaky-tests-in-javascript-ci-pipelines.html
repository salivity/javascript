Fixing Flaky Tests in JavaScript CI Pipelines

Flaky tests—tests that intermittently pass or fail without code changes—severely undermine confidence in continuous integration (CI) pipelines and slow down development cycles. This article outlines the primary causes of test flakiness in JavaScript ecosystems, practical techniques and tooling to detect non-deterministic behavior, and targeted architectural strategies to mitigate flakiness and stabilize your CI workflows.

Root Causes of Flakiness in JavaScript

JavaScript applications are particularly susceptible to flakiness due to their asynchronous, single-threaded nature and reliance on shared state. The most common triggers include:

  • Improper Asynchronous Handling: Missing await keywords, unhandled promises, or using hardcoded delays (setTimeout) instead of condition-based waiting leads to race conditions.
  • Shared State and Leaked Side Effects: Modifying global objects (like window, document, or Node.js process globals), uncleaned localStorage, or persistent database states between tests can cause failures when test execution order varies.
  • Environment Differences and Resource Starvation: CI agents often have fewer CPU cores and less memory than local developer machines. This slowdown causes tight timeouts to expire unpredictably.
  • Unmocked External Dependencies: Real network requests, external APIs, and live clock time changes produce dynamic results that trigger unpredictable assertions.

Strategies for Detecting Flaky Tests

Detecting flaky tests requires actively surfacing non-deterministic behavior rather than waiting for an accidental failure on a pull request.

Stress Testing (Test Looping)

Run suspected tests repeatedly in identical environments. Most test runners support looping tests natively or via CLI scripts:

  • In Jest, run specific test files in a loop using a shell script or leverage --detectOpenHandles to find unclosed resources.
  • In Playwright or Cypress, configure the test runner to repeat tests dozens of times (e.g., npx playwright test --repeat-each=50) to capture low-frequency race conditions.

Quarantine and Analytics Tools

Modern CI systems track test stability over time:

  • CI Visibility Tools: Tools like Datadog CI Visibility, Buildkite Test Analytics, or trunk.io continuously monitor test results, calculating a flakiness score by comparing runs across branches on the same commit hash.
  • Automated Flagging: When a test passes on a retry after an initial failure in the same CI run, the system automatically tags that test as flaky in the metrics dashboard.

Mitigation Techniques in CI Pipelines

Mitigating flaky tests involves both fixing the underlying code defects and preventing flaky tests from halting release pipelines.

Replace Fixed Delays with Explicit Polling

Never rely on arbitrary wait times (setTimeout(fn, 1000)). Use deterministic assertions that poll the DOM or state until the expected condition is met:

  • In Testing Library, replace synchronous getBy* queries with asynchronous findBy* queries or wrap expectations inside waitFor().
  • In Playwright/Cypress, rely on built-in auto-waiting assertions (such as expect(locator).toBeVisible()).

Isolate State and Reset Mocks

Ensure each test starts with a clean slate:

  • Reset mocks and timers in lifecycle hooks using jest.clearAllMocks(), jest.resetModules(), or vi.restoreAllMocks().
  • Clean up DOM mutations and database entries after every test run.
  • Randomize test execution order locally and in CI (e.g., using Jest's --randomize flag) to reveal hidden dependencies between tests.

Mock External Boundaries

Decouple tests from external volatility:

  • Use Mock Service Worker (MSW) to intercept network calls at the network level rather than hitting live endpoints.
  • Freeze and control system time using fake timers (jest.useFakeTimers() or vi.useFakeTimers()) when testing time-dependent logic.

Implement Quarantine and Controlled Retries

While addressing the root code issues:

  • Controlled Retries: Configure your test runner to retry failed tests only in CI (e.g., retries: 2 in Playwright or jest-circus retry settings). This prevents non-critical flakes from blocking deployments.
  • Quarantine Pipeline: Automatically move persistently flaky tests out of the critical merge-blocking path into an isolated, non-blocking suite. Engineers can then diagnose and fix them without impeding the broader team's pull request workflow.
