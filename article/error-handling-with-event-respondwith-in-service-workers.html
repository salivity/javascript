Error Handling with event.respondWith in Service Workers

Handling errors within a service worker's fetch event handler is critical for ensuring reliable offline experiences and preventing broken web applications. When using event.respondWith(), passing an unhandled rejected promise causes the browser to treat the request as a catastrophic network error, rendering the default browser offline screen. This article covers how event.respondWith() processes promises, the distinction between network failures and HTTP error statuses, and practical strategies for catching exceptions and serving fallback responses.

Understanding event.respondWith() Failure Behavior

The event.respondWith() method intercepts network requests and expects a Promise that resolves to a Response object. If the provided promise rejects—due to a network disconnection, DNS failure, or an unhandled JavaScript exception—the browser terminates the request with a generic network error (like net::ERR_FAILED in Chromium).

To prevent broken user interfaces, you must intercept these rejections before they reach the browser engine, ensuring that event.respondWith() always receives a resolved Response.

Using Try/Catch with Async Functions

The cleanest and most maintainable way to handle errors is to pass an async function directly to event.respondWith() and wrap the retrieval logic in a try...catch block.

self.addEventListener('fetch', (event) => {
  event.respondWith(
    (async () => {
      try {
        // Attempt network fetch
        const networkResponse = await fetch(event.request);
        return networkResponse;
      } catch (error) {
        // Handle network failure or execution errors
        console.error('Fetch failed; returning offline page instead.', error);
        
        const cache = await caches.open('static-v1');
        const cachedResponse = await cache.match('/offline.html');
        
        return cachedResponse || new Response('Network error occurred', {
          status: 503,
          statusText: 'Service Unavailable',
          headers: new Headers({ 'Content-Type': 'text/plain' }),
        });
      }
    })()
  );
});

Differentiating Network Failures from HTTP Errors

A common pitfall with the native fetch() API is assuming that HTTP error codes (such as 404 Not Found or 500 Internal Server Error) trigger a promise rejection. In reality, fetch() only rejects on actual network failures or blocked requests (e.g., CORS violations).

To handle upstream server errors within your strategy, inspect the ok or status properties of the resolved Response:

self.addEventListener('fetch', (event) => {
  event.respondWith(
    (async () => {
      try {
        const response = await fetch(event.request);

        if (!response.ok) {
          // Check for specific status codes if custom handling is needed
          if (response.status === 404) {
            const cache = await caches.open('static-v1');
            return (await cache.match('/404.html')) || response;
          }
        }

        return response;
      } catch (error) {
        // Only triggered on complete network failure
        const cache = await caches.open('static-v1');
        return await cache.match(event.request) || await cache.match('/offline.html');
      }
    })()
  );
});

Implementing Promise Chaining with .catch()

If you prefer standard promise syntax over async/await, attach a .catch() handler to the end of the promise chain passed into event.respondWith(). The callback must return a valid Response object.

self.addEventListener('fetch', (event) => {
  event.respondWith(
    fetch(event.request)
      .catch((error) => {
        return caches.match(event.request).then((cachedResponse) => {
          if (cachedResponse) {
            return cachedResponse;
          }
          
          return new Response(JSON.stringify({ error: 'Offline and un-cached' }), {
            status: 503,
            headers: { 'Content-Type': 'application/json' }
          });
        });
      })
  );
});

Returning Synthetic Fallback Responses

When both the network and the cache fail, generate a synthetic Response object using the Response() constructor instead of letting the error bubble up.

  • For HTML requests: Return an inline HTML fallback message informing the user they are offline.
  • For images: Return a base64-encoded SVG or a default placeholder from the cache.
  • For API calls: Return a structured JSON response with a standard 503 or 504 status code indicating service unavailability.

By consistently returning a constructed Response inside your error handlers, you maintain full control over the application's failure states.
