Understanding JavaScript Proposal Stages 1 to 4

JavaScript evolves through a formal standardization process governed by Ecma International's Technical Committee 39 (TC39). To transition an idea into the official ECMAScript specification, TC39 uses a staged maturity model ranging from Stage 0 to Stage 4. Stages 1 through 4 specifically represent the progression from an officially recognized proposal to a fully vetted, production-ready language feature. Each designation defines explicit entry criteria, requirements for specification text, implementation milestones, and the stability level developers can expect.

Stage 1: Proposal (Investigation)

Stage 1 designates that TC39 considers a problem worth solving and is willing to invest time in exploring solutions. A proposal enters Stage 1 once a committee member champions it and presents a clear problem space along with potential approaches.

  • Requirements: A defined problem statement, examples of proposed usage, high-level API sketches, and an initial analysis of potential implementation challenges or cross-cutting concerns with existing language features.
  • Maturity Level: Highly experimental. Syntax, semantics, and API design are fluid and subject to radical changes or outright rejection.
  • Developer Guidance: Features at this stage should only be used for research and feedback, typically using experimental transpiler plugins.

Stage 2: Draft (Design)

Reaching Stage 2 signals that the committee expects the feature to be developed and eventually included in the standard. At this point, the conceptual solution is established, and the focus shifts to defining the formal language integration.

  • Requirements: Formal specification text written using ECMAScript specification language. The proposal must describe the syntax, semantics, and algorithms in precise technical detail, leaving no major design questions unresolved.
  • Maturity Level: Structurally defined. While the core architecture is settled, secondary semantics and syntax refinements still occur frequently based on committee review.
  • Developer Guidance: Early experiments and polyfills become viable, but developers should not rely on stability across minor releases.

Stage 3: Candidate (Implementation and Validation)

Stage 3 indicates that the proposal is functionally complete and ready for real-world validation. The specification is fully drafted, and the design will not change unless significant implementation barriers, critical bugs, or web compatibility issues arise.

  • Requirements: Complete, fully reviewed specification text signed off by designated TC39 reviewers and the ECMAScript editor. The proposal must also provide comprehensive test suites submitted to Test262, the official ECMAScript conformance test suite.
  • Maturity Level: Near-final. The committee expects implementations in runtimes (such as V8, SpiderMonkey, or JavaScriptCore), typically behind experimental flags, to gather feedback from engine developers and web authors.
  • Developer Guidance: Safe for broader experimentation and adoption in controlled environments. Breaking changes are rare and strictly reactive.

Stage 4: Finished (Standardization)

Stage 4 is the final designation before a feature becomes an official part of the annual ECMAScript standard. It confirms that the feature has passed practical, multi-engine testing and is completely integrated into the language ecosystem.

  • Requirements: At least two independent, compatible implementations passing the official Test262 test suite and running in production environments. A pull request integrating the specification text directly into the main ECMAScript repository must be approved by the editor.
  • Maturity Level: Completely stable and standardized.
  • Developer Guidance: Ready for production use without flags or transpilation, assuming target environments support the updated runtime engines. The feature is scheduled for inclusion in the next yearly ECMAScript release.
