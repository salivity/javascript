Protect JavaScript Game Saves Against Tampering

In client-side JavaScript game development, storing save data in formats like JSON leaves game states vulnerable to trivial modification through browser developer tools or text editors. Implementing cryptographic encryption and integrity verification raises the technical barrier against local tampering, ensuring that players cannot easily alter statistics, currency, or progression flags stored in localStorage, IndexedDB, or local file systems.

The Vulnerability of Client-Side Storage

JavaScript games that execute entirely within a player's environment inherently expose their storage mechanisms. Standard storage APIs, such as Window.localStorage or IndexedDB, persist plain text or lightly serialized objects. A player can open the browser console, inspect the stored data, modify values such as player health or inventory counts, and reload the game with the altered state.

How Encryption Prevents Tampering

Encryption addresses local tampering primarily by transforming human-readable data structures into unreadable ciphertext and coupling that ciphertext with cryptographic integrity verification.

  1. Obfuscation of Data Structure: By utilizing symmetric encryption algorithms like AES (Advanced Encryption Standard), plain JSON strings are scrambled into high-entropy ciphertext. A player attempting to edit their save file in a text editor cannot determine which bytes correspond to specific game variables.
  2. Authenticated Encryption (AEAD): Modern cryptographic modes, such as AES-GCM (Galois/Counter Mode), provide both confidentiality and data integrity. AES-GCM generates an authentication tag during encryption. If a user modifies even a single byte of the encrypted payload, the decryption process fails the mathematical verification and rejects the save file as corrupt.
  3. Hashing and HMAC Verification: If standard encryption modes like AES-CBC are used, integrity is often enforced by pairing the ciphertext with a Hash-based Message Authentication Code (HMAC) using SHA-256. Upon loading, the game computes the HMAC of the file using a secret key and compares it against the stored signature. Any divergence indicates tampering, prompting the game to discard the save.

Implementation with the Web Crypto API

Modern JavaScript provides native cryptographic operations through the crypto.subtle API, eliminating the need for third-party libraries:

  • Key Generation or Derivation: The game derives a CryptoKey using PBKDF2 from a hardcoded or dynamically computed seed phrase combined with a static salt.
  • Encryption Phase: The game serializes the player state to a JSON string, generates a random Initialization Vector (IV), and executes crypto.subtle.encrypt({ name: "AES-GCM", iv }, key, encodedData). The IV and ciphertext are concatenated and converted to a Base64 string for storage.
  • Decryption Phase: When loading, the game splits the IV from the ciphertext and executes crypto.subtle.decrypt(). If the data was altered, the promise rejects, signaling that the save file has been compromised.

The Limits of Client-Side Protection

While encryption stops casual editing, it does not provide absolute security in client-side architectures. Because the decryption keys and verification algorithms exist within the game's JavaScript source code, a determined user can debug the runtime, extract keys from memory, or modify the source code to bypass integrity checks entirely. Consequently, encryption in local JavaScript games serves as a defense against casual tampering rather than a replacement for server-authoritative validation.
