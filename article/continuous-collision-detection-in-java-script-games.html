Continuous Collision Detection in JavaScript Games

Continuous collision detection (CCD) is an algorithmic physics technique used in game development to predict and resolve collisions by calculating an object's trajectory over time rather than checking for overlaps at static intervals. In fast-paced JavaScript games, high-speed objects like bullets or sprinting characters often move farther in a single frame than their own physical dimensions, causing them to completely pass through barriers undetected—a glitch known as tunneling. This article explains the mechanics of tunneling, how CCD algorithms solve it by treating movement as a continuous volume or ray, and how to effectively implement these concepts in JavaScript physics loops.

The Mechanics of Tunneling

Most standard 2D and 3D game engines use discrete collision detection. In a typical JavaScript game loop driven by requestAnimationFrame, the engine calculates physics updates in discrete time steps (often roughly 16.6 milliseconds at 60 frames per second).

In a discrete system, the engine updates an entity's position based on its velocity and then checks if its bounding box intersects with any obstacles:

// Discrete update: Checks position only at fixed points in time
player.x += player.vx * deltaTime;
player.y += player.vy * deltaTime;

if (checkOverlap(player, wall)) {
    resolveCollision(player, wall);
}

If an object moves at 1,000 pixels per second, it travels approximately 16.6 pixels per frame. If it encounters a wall that is only 10 pixels thick, the object can be in front of the wall in frame one and completely behind it in frame two. Because the object was never directly overlapping the wall at the exact moment a frame was processed, the discrete check fails, and the object tunnels through the solid obstacle.

What is Continuous Collision Detection?

Continuous collision detection prevents tunneling by analyzing the entire path an object travels between two consecutive time steps. Instead of asking, "Is the object intersecting an obstacle right now?", CCD asks, "Did the object's path intersect an obstacle between the previous frame and this frame?"

By calculating the Time of Impact (TOI), CCD determines the precise point in time (from \(t = 0\) to \(t = 1\) within the current frame) where contact first occurs. The physics solver can then move the entity up to the point of contact, resolve the impact (such as bouncing or stopping), and simulate the remainder of the time step accordingly.

Core CCD Techniques in JavaScript

JavaScript developers generally implement CCD using one of two primary approaches depending on the size and shape of the moving entity.

1. Raycasting (Point-Based CCD)

For small, fast-moving items such as bullets, lasers, or tiny debris, raycasting is the most efficient CCD method. Instead of treating the projectile as a full bounding box, the engine creates a directed line segment from the projectile's previous position \((x_1, y_1)\) to its prospective new position \((x_2, y_2)\).

The engine then runs a line-intersection algorithm against the edges of scene colliders. If the line intersects an edge:

  • A collision is registered.
  • The exact point of intersection is calculated.
  • The projectile is positioned at the intersection point, and its impact callback is triggered.

2. Swept Volumes (Swept AABB)

For larger objects where dimensions cannot be reduced to a single point, engines use swept volume tests, most commonly Swept Axis-Aligned Bounding Boxes (Swept AABB).

A Swept AABB expands the target's bounding box along its movement vector, forming an extruded polygon or bounding volume that covers all space occupied by the object during the frame. The algorithm calculates the distance to the obstacle on each axis and divides it by the velocity to determine the exact entry and exit times of the collision:

function sweptAABB(box, velocity, obstacle) {
    let xInvEntry, yInvEntry;
    let xInvExit, yInvExit;

    // Find the distance between the objects on the near and far sides
    if (velocity.x > 0) {
        xInvEntry = obstacle.x - (box.x + box.width);
        xInvExit = (obstacle.x + obstacle.width) - box.x;
    } else {
        xInvEntry = (obstacle.x + obstacle.width) - box.x;
        xInvExit = obstacle.x - (box.x + box.width);
    }

    if (velocity.y > 0) {
        yInvEntry = obstacle.y - (box.y + box.height);
        yInvExit = (obstacle.y + obstacle.height) - box.y;
    } else {
        yInvEntry = (obstacle.y + obstacle.height) - box.y;
        yInvExit = obstacle.y - (box.y + box.height);
    }

    // Calculate time of collision on each axis (scaled from 0.0 to 1.0)
    let xEntry = velocity.x === 0 ? -Infinity : xInvEntry / velocity.x;
    let xExit = velocity.x === 0 ? Infinity : xInvExit / velocity.x;
    let yEntry = velocity.y === 0 ? -Infinity : yInvEntry / velocity.y;
    let yExit = velocity.y === 0 ? Infinity : yInvExit / velocity.y;

    let entryTime = Math.max(xEntry, yEntry);
    let exitTime = Math.min(xExit, yExit);

    // If no collision occurred along the path
    if (entryTime > exitTime || (xEntry < 0 && yEntry < 0) || xEntry > 1 || yEntry > 1) {
        return { hit: false, time: 1.0 };
    }

    // Collision occurred at entryTime fraction of the frame
    return { hit: true, time: entryTime };
}

Performance Optimization in JavaScript

Because JavaScript executes on a single main thread alongside rendering and garbage collection tasks, running CCD on every game entity can cause performance drops. Continuous calculations are computationally heavier than simple discrete overlapping checks.

To balance precision and performance:

  • Selective CCD: Only flag fast-moving dynamic actors (projectiles, speeding vehicles) for CCD checks. Slower elements, like walking NPCs, should rely on standard discrete collision detection.
  • Broad-Phase Filtering: Use spatial partitioning structures—such as Quadtrees, Grids, or dynamic bounding volume hierarchies (BVH)—to discard distant objects before running swept volume equations.
  • Sub-Stepping as an Alternative: If implementing swept math is impractical, you can simulate sub-stepping. This breaks a single frame's physics step into multiple smaller discrete steps (e.g., running four 4ms updates instead of one 16ms update). While it increases CPU workload, it shortens the distance traveled per step, mitigating tunneling without writing custom continuous solvers.
  • Physics Engines: For complex 2D and 3D games, leverage existing JavaScript engines with built-in CCD implementations, such as Rapier (via WebAssembly) or Matter.js, which offer optimized continuous solvers for high-velocity bodies.
