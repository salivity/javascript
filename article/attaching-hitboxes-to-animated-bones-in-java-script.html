Attaching Hitboxes to Animated Bones in JavaScript

This article explains how to attach dynamic hitbox and hurtbox collision shapes to skeletal animation bones in JavaScript game development. By binding collision volumes to a character's underlying skeletal hierarchy, developers ensure that combat interactions accurately mirror character movement. You will learn the core mathematical principles behind bone-space transformation, practical attachment techniques in both 2D and 3D web-based rendering engines, and performance best practices for real-time collision detection.

The Role of Bones in Skeletal Animation

Skeletal animation operates on a hierarchy of interconnected nodes, known as bones or joints. Each bone maintains a local transformation (position, rotation, and scale) relative to its parent bone. When an animation plays, these local transforms update continuously.

To determine a bone’s absolute location in the game world, the engine traverses the hierarchy from the root bone outward, multiplying each parent's matrix by the child's matrix to compute the bone's world transform matrix. Hitboxes and hurtboxes must be tied to this world transform matrix to move in lockstep with the animation.

Hitboxes vs. Hurtboxes

Before implementing attachment logic, it is critical to separate the two types of volumes:

  • Hurtboxes: Bound to defensive body regions (e.g., head, torso, limbs). They remain active continuously to detect incoming damage.
  • Hitboxes: Bound to offensive elements (e.g., fists, feet, weapon blades). They are typically enabled only during specific animation frames, such as the active phase of an attack swing.

Methods of Bone Attachment

There are two primary methods for binding collision shapes to bones in JavaScript:

1. Scene Graph Parenting (Renderer-Level Binding)

The simplest approach relies on the game engine’s native scene graph hierarchy. If the engine treats bones as standard display objects or transform nodes, you can directly add the collision volume as a child of the target bone.

In a library like Three.js:

// Locate the bone inside the skinned mesh
const handBone = characterMesh.skeleton.getBoneByName('RightHand');

// Create the hitbox geometry (e.g., an offensive sphere)
const hitboxGeometry = new THREE.SphereGeometry(0.2);
const hitboxMaterial = new THREE.MeshBasicMaterial({ visible: false });
const hitbox = new THREE.Mesh(hitboxGeometry, hitboxMaterial);

// Offset the hitbox relative to the bone origin
hitbox.position.set(0, 0.1, 0);

// Attach the hitbox directly as a child of the bone
handBone.add(hitbox);

Because the hitbox is a child node, the rendering engine automatically applies the bone's world transform matrix to the hitbox during its internal update pass.

2. Manual Matrix Synchronization (Physics Engine Decoupling)

When using a dedicated physics engine (such as Rapier.js, Cannon-es, or Matter.js), physics colliders cannot always exist inside the visual scene graph. Instead, the game loop must extract the bone's world position and orientation every frame and apply it to the external physics body.

function updateColliders() {
    // Ensure the skeleton's world matrices are updated
    characterMesh.skeleton.update();

    // Extract the bone's world position and quaternion
    const boneWorldPosition = new THREE.Vector3();
    const boneWorldQuaternion = new THREE.Quaternion();
    
    handBone.getWorldPosition(boneWorldPosition);
    handBone.getWorldQuaternion(boneWorldQuaternion);

    // Apply the extracted values to the physics collider
    physicsHitbox.setTranslation(boneWorldPosition, true);
    physicsHitbox.setRotation(boneWorldQuaternion, true);
}

In 2D engines using skeletal animation libraries like Spine-Canvas or DragonBones, the process is mathematically identical: query the bone's absolute X, Y coordinates and world rotation, then update the 2D collision body (such as a circle or rotated rectangle).

Animation Events and Activation Windows

Hitboxes should not remain active for the entirety of an animation. Attaching a hitbox to a hand bone would cause damage if an opponent merely touches the character while idle.

To control activation:

  1. Frame Tags / Animation Events: Embed custom events into the animation data (e.g., hitbox_start at frame 12, hitbox_end at frame 18).
  2. Event Listeners: In JavaScript, listen for these animation triggers to toggle the collider's active flag:
animationAction.getMixer().addEventListener('loop', resetHitboxes);

function onAnimationEvent(event) {
    if (event.name === 'hitbox_start') {
        handHitbox.userData.active = true;
    } else if (event.name === 'hitbox_end') {
        handHitbox.userData.active = false;
    }
}

Performance Optimization

  • Use Primitive Shapes: Avoid convex hulls or complex meshes. Use bounding spheres, capsules, or axis-aligned/oriented bounding boxes (AABBs/OBBs). Sphere-to-sphere checks require minimal mathematical overhead (distance squared <= (radiusA + radiusB) squared).
  • Limit Bone Checks: Do not bind colliders to every bone. A typical character requires only three to four hurtboxes (head, torso, legs) and temporary hitboxes for active striking limbs.
  • Skip Inactive Computations: If an attack is not active, bypass the matrix extraction step for its corresponding hitbox entirely.
