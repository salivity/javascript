Targeting Legacy JavaScript with Browserslist

This article explores the critical role of the Browserslist database in modern web development, specifically focusing on how it enables developers to target legacy JavaScript environments. By establishing a unified configuration shared across transpilers, polyfill injectors, and bundlers, Browserslist ensures that applications run reliably on older browsers without unnecessarily bloating the code sent to modern clients. Readers will gain a clear understanding of how the database works, how it integrates with popular build tools, and best practices for supporting outdated runtime environments.

What is Browserslist?

Browserslist is an open-source library that allows developers to define target browser versions using human-readable queries such as > 0.5%, last 2 versions, or Firefox ESR. Instead of maintaining separate browser configuration files for every tool in a build pipeline, Browserslist acts as a single, central source of truth.

The library relies on data provided by the caniuse-lite database—a streamlined version of the Can I Use dataset. When a build runs, Browserslist parses the query string, evaluates it against this database, and outputs a concrete list of matching browser versions.

The Challenge of Supporting Legacy Environments

Legacy JavaScript environments—such as older versions of mobile WebKit, Safari, or legacy enterprise browsers—lack support for modern ECMAScript features. These deficiencies fall into two primary categories:

  • Syntax limitations: Inability to parse modern constructs such as optional chaining (?.), nullish coalescing (??), arrow functions, or async/await.
  • Missing standard library features: Absence of modern APIs and objects, such as Promise, fetch, Array.prototype.includes, or Map/Set.

Without automation, developers would have to manually determine which syntax to compile down to older standards (like ES5) and which runtime polyfills to import. Doing this manually is error-prone and frequently results in shipping either broken code to older browsers or excessive polyfill payloads to modern ones.

How Browserslist Bridges the Gap

Browserslist solves legacy compatibility by translating broad business requirements into precise technical targets for the build pipeline.

Integration with Babel (@babel/preset-env)

When configured with @babel/preset-env, Babel reads the Browserslist configuration to determine the minimum language baseline. If the query targets older browsers, Babel identifies the specific syntax transforms required to prevent parsing errors in those engines. Syntax supported natively by all targeted platforms is left untouched, optimizing build output and runtime speed.

Smart Polyfilling via Core-JS

When paired with libraries like core-js, Browserslist enables on-demand polyfilling (via useBuiltIns: 'usage'). The build tool analyzes the source code for modern API usage, compares it against the baseline capabilities of the browsers matched by the Browserslist query, and injects only the polyfills required by the oldest target.

PostCSS and CSS Compatibility

Although primarily utilized for JavaScript, the same Browserslist database informs CSS tooling, such as Autoprefixer. This ensures that legacy JavaScript rendering engines also receive appropriate vendor prefixes and fallbacks for CSS rules.

Setting Up Queries for Legacy Targets

Browserslist queries are typically defined in a .browserslistrc file or within the package.json file.

To explicitly target older or legacy systems, developers combine market share, version counts, and specific browser queries:

> 0.2%
not dead
IE 11
Safari >= 10
  • > 0.2%: Ensures coverage for browsers that still hold a measurable global or regional market share.
  • not dead: Excludes browsers with no official support or updates in the last 24 months, unless explicitly overridden.
  • IE 11 or specific version queries: Explicitly guarantees that legacy platforms remain in the target list regardless of their declining global market share.

Maintaining the Browserslist Database

Because browser support data changes continuously, the underlying database must remain up to date. Running the command npx update-browserslist-db@latest updates the localized caniuse-lite dependency. Keeping this database current ensures that tools do not continue applying legacy workarounds to browsers that have since auto-updated, while still accurately targeting the legacy environments that remain.
