JavaScript Singleton Pattern: Closures and Modules

The Singleton Pattern is a creational design pattern that restricts the instantiation of an object to a single instance across an application while providing a global point of access to it. In JavaScript, this pattern is widely applied to shared resources like application configuration managers, database connection pools, and central state stores. This article explains the core mechanics of the Singleton Pattern and provides clear, practical examples of how to implement it using traditional function closures and modern ES6 modules.

Understanding the Singleton Pattern

The primary purpose of a Singleton is to ensure that a specific resource is initialized once and reused everywhere. Without this control, different parts of an application could spawn multiple instances of a resource, leading to inconsistent state, memory overhead, or conflicting network and database operations.

Implementing a Singleton with Closures

Prior to modern JavaScript syntax, developers used closures alongside Immediately Invoked Function Expressions (IIFEs) to create private scopes. The closure encapsulates the instance variable, preventing outside code from directly modifying or overwriting it.

const DatabaseConnection = (function () {
  let instance;

  function createInstance() {
    return {
      host: "localhost",
      port: 5432,
      connect() {
        console.log("Connected to database.");
      }
    };
  }

  return {
    getInstance() {
      if (!instance) {
        instance = createInstance();
      }
      return instance;
    }
  };
})();

// Usage:
const connection1 = DatabaseConnection.getInstance();
const connection2 = DatabaseConnection.getInstance();

console.log(connection1 === connection2); // true

In this implementation:

  • instance remains private inside the IIFE's closure.
  • DatabaseConnection.getInstance() checks whether instance exists. If not, it creates one; if it already exists, it returns the cached reference.
  • Both connection1 and connection2 point to the exact same object in memory.

Implementing a Singleton with ES6 Modules

Modern JavaScript simplifies singletons because ES6 modules are singletons by default. When an ES6 module is imported across different files, the module's code executes only once upon the initial import. The runtime caches the exported value and supplies the same instance to all subsequent imports.

configManager.js

class ConfigManager {
  constructor() {
    this.config = {
      theme: "dark",
      apiUrl: "https://api.example.com"
    };
  }

  get(key) {
    return this.config[key];
  }

  set(key, value) {
    this.config[key] = value;
  }
}

// Export a pre-initialized instance, not the class
const configInstance = new ConfigManager();
Object.freeze(configInstance); // Optional: Prevents mutation of the instance structure

export default configInstance;

serviceA.js

import config from './configManager.js';

config.set('theme', 'light');

serviceB.js

import config from './configManager.js';

console.log(config.get('theme')); // Outputs: "light"

In this setup:

  • Exporting the instantiated object rather than the ConfigManager class ensures that consumers cannot arbitrarily instantiate new configurations with the new keyword.
  • Node.js and modern browser environments cache module exports, ensuring that serviceA and serviceB share the identical object reference.

When to Use Singletons

The Singleton Pattern works best when:

  • Multiple components must read and write to a single source of truth (such as a runtime application logger or client-side cache).
  • Initializing multiple instances causes resource exhaustion or conflicts.

For most modern JavaScript applications, relying on ES6 module exports is the cleanest and most idiomatic way to achieve singleton behavior, while closures remain an effective alternative in environments where module systems are unavailable.
