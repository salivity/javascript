How esbuild onResolve and onLoad Hooks Work

The esbuild bundler provides an extensible plugin API centered around two primary lifecycle hooks: onResolve and onLoad. Together, these hooks intercept and redefine how esbuild locates modules on the filesystem and how it processes their contents. By controlling the mapping from import paths to concrete identifiers and supplying transformed or synthetic source code directly to the compiler, developers can customize module resolution, implement virtual modules, compile non-standard file types, and integrate custom compilers.

The Module Resolution Pipeline

When esbuild bundles source code, it traverses an Abstract Syntax Tree (AST) looking for import statements, require() calls, and export directives. For every module reference encountered, esbuild follows a two-step process: resolving the path to an absolute location and loading the contents of that location into memory. Plugins tap into this pipeline using onResolve for the first step and onLoad for the second.

The onResolve Hook

The onResolve hook intercepts import paths before esbuild checks the filesystem. Whenever the bundler encounters an import string (such as import x from './utils' or import config from 'env:production'), it evaluates all registered onResolve callbacks.

Each onResolve registration requires a regular expression filter to limit which import paths it intercepts:

build.onResolve({ filter: /^env:/ }, (args) => {
  return {
    path: args.path.replace(/^env:/, ''),
    namespace: 'env-ns',
  };
});

Key Parameters and Return Values

  • args.path: The raw path string as written in the source file.
  • args.importer: The absolute path of the file containing the import statement.
  • args.namespace: The namespace of the importing file (defaults to file).
  • args.resolveDir: The directory from which relative paths should be resolved.

The callback returns an object that directs esbuild's next action:

  • path: The canonical path or unique key identifying the module.
  • namespace: A custom identifier that groups related modules. Non-file namespaces tell esbuild not to look for the file on the standard filesystem.
  • external: If set to true, tells esbuild to omit the module from the bundle and preserve the import call at runtime.

The onLoad Hook

Once a path is resolved and assigned a namespace, esbuild triggers the onLoad hook to retrieve the file's source code. If no plugin intercepts the load step, esbuild reads the file from disk using the default file namespace.

Like onResolve, the onLoad hook uses regex filters to match paths, but it can also filter by namespace:

build.onLoad({ filter: /.*/, namespace: 'env-ns' }, (args) => {
  return {
    contents: JSON.stringify(process.env[args.path] || null),
    loader: 'json',
  };
});

Key Parameters and Return Values

  • args.path: The resolved path determined during the resolution phase.
  • args.namespace: The namespace assigned during the resolution phase.

The callback returns an object specifying the code and how to parse it:

  • contents: The file contents as a string or Uint8Array.
  • loader: The built-in esbuild loader used to interpret the contents (e.g., 'js', 'ts', 'jsx', 'tsx', 'json', 'css', 'text').
  • resolveDir: The directory used to resolve subsequent relative imports found inside contents.

How the Hooks Coordinate

The interaction between onResolve and onLoad allows for complete decoupling of import specifiers from the physical disk:

  1. Discovery: esbuild parses a file and finds import data from 'custom:userData'.
  2. Resolution (onResolve): A plugin matches ^custom: via its filter. The callback tags the module with namespace: 'custom-virtual' and path: 'userData'.
  3. Dispatch: esbuild checks for an onLoad hook listening for the custom-virtual namespace.
  4. Loading (onLoad): The matching onLoad hook generates the module code on the fly (for example, by querying a database or an API) and returns { contents: 'export default { id: 1 };', loader: 'js' }.
  5. Compilation: esbuild treats the generated string as standard JavaScript, parses its AST, bundles it, and continues scanning for further nested dependencies.
