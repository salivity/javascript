Using Trusted Types Default Policy to Prevent Legacy XSS

This article examines how implementing a default Trusted Types policy acts as a critical mitigation layer against DOM-based Cross-Site Scripting (DOM XSS) in legacy JavaScript applications. By intercepting raw string assignments to dangerous web APIs, a default policy centralizes input sanitization, prevents script execution from untrusted sources, and provides an immediate security baseline without requiring an exhaustive, line-by-line rewrite of an existing codebase.

The Challenge of DOM XSS in Legacy Codebases

Legacy JavaScript applications frequently interact with dangerous DOM sinks—such as Element.innerHTML, Location.href, and eval(). These sinks execute or render unvalidated strings directly in the browser context. Remediating these vulnerabilities across large, established applications is notoriously difficult because manually auditing, refactoring, and sanitizing every direct DOM assignment requires significant development time and risks introducing regressions.

When developers enforce Trusted Types via the Content Security Policy (CSP) directive require-trusted-types-for 'script', the browser locks down these injection sinks. By default, assigning a standard string to a sink throws a runtime TypeError, effectively halting any script that has not been refactored to pass a typed object such as TrustedHTML, TrustedScript, or TrustedScriptURL.

How the Default Policy Works

A default Trusted Types policy serves as an automated fallback mechanism for string-to-type conversions. When an application attempts to pass a raw string to a regulated DOM sink without an explicit policy applied, the browser automatically routes the string through the policy named 'default'.

To create this policy, developers define it once in the application’s initialization phase:

if (window.trustedTypes && trustedTypes.createPolicy) {
  trustedTypes.createPolicy('default', {
    createHTML: (string) => DOMPurify.sanitize(string, { RETURN_TRUSTED_TYPE: false }),
    createScriptURL: (string) => {
      // Validate string against an allowlist of trusted script domains
      if (string.startsWith('https://trusted-cdn.example.com/')) {
        return string;
      }
      throw new Error(`Untrusted script URL: ${string}`);
    },
    createScript: (string) => {
      // Disallow or strictly filter arbitrary inline script execution
      throw new Error('Inline script execution is prohibited.');
    }
  });
}

When this policy is defined, any legacy code that performs an assignment like element.innerHTML = untrustedInput triggers createHTML under the hood. The browser assigns the sanitized result as a TrustedHTML object, neutralizing executable payloads before they can compromise the session.

Safeguards Provided by the Default Policy

  1. Centralized Sanitization: Instead of relying on individual developers to remember to sanitize data at the point of injection, all string transformations are forced through a single, audited implementation.

  2. Zero Breaking Changes for Legacy Syntax: Developers do not need to immediately modify legacy components or third-party dependencies to use explicit Trusted Types objects. The application continues running standard string operations, while the browser silently enforces security at the boundary.

  3. Protection from Third-Party Scripts: Legacy applications often depend on outdated third-party libraries that still assign raw strings to DOM sinks. A default policy catches and processes these external assignments, securing dependencies that internal development teams cannot easily rewrite.

  4. Telemetry and Controlled Migration: A default policy can be used to log and report legacy sink usage. Teams can integrate logging into the policy methods to monitor which parts of the legacy code still invoke dangerous sinks, creating an actionable roadmap for eventual refactoring.

Strategic Implementation

While named policies represent the gold standard for Trusted Types by guaranteeing explicit data handling at every sink, adopting them across an enterprise-scale legacy codebase is a multi-phase endeavor. Implementing a default policy with an established sanitization library provides immediate, system-wide protection against DOM XSS, neutralizing attack vectors at the browser level while preserving functionality.
