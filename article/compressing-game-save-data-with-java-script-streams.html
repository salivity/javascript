Compressing Game Save Data with JavaScript Streams

Native compression streams provide web game developers with a built-in, dependency-free mechanism to shrink large save states before persisting them to local storage or synchronizing them with cloud backends. By leveraging the browser's native CompressionStream and DecompressionStream interfaces, games can drastically reduce the memory and storage footprints of complex game state objects, bypass storage quota limitations, and improve network transfer speeds.

The Problem with Raw Game Save Data

Modern web games often serialize game state into JSON strings. As game worlds grow with procedural generation, inventory systems, detailed quest logs, and tracking statistics, these state files can scale into tens of megabytes.

Storing raw JSON creates two distinct bottlenecks:

  1. Storage Limits: Browser storage options like localStorage have strict capacity limits (typically 5MB). While IndexedDB offers significantly more space, uncompressed data can still quickly consume device storage.
  2. Transfer Overhead: For titles that support cloud synchronization, uploading and downloading uncompressed save files increases latency and bandwidth consumption, leading to sluggish save operations on mobile or poor connections.

Because JSON contains repetitive syntax—such as recurring key names, boolean flags, and nested structures—it responds exceptionally well to dictionary-based compression algorithms like Gzip and Deflate, often achieving size reductions of 70% to 90%.

What Are Native Compression Streams?

Historically, web game developers relied on third-party libraries such as pako or lz-string to compress game data. The modern web platform includes native APIs to handle compression directly:

  • CompressionStream: A built-in TransformStream that accepts binary data and outputs a compressed stream using either 'gzip', 'deflate', or 'deflate-raw'.
  • DecompressionStream: The corresponding inverse stream that unpacks compressed binary data back into its original format.

Because these streams are executed natively by the browser runtime, they are faster than JavaScript-based compression libraries and reduce the game's overall initial download size by removing external dependencies.

Compressing Save Data

To compress a JavaScript game state object, serialize the state to a JSON string, encode it into a Uint8Array, and pipe it through a CompressionStream.

async function compressSaveData(gameState) {
  const jsonString = JSON.stringify(gameState);
  const stream = new Blob([jsonString]).stream();
  const compressedStream = stream.pipeThrough(new CompressionStream('gzip'));
  const response = new Response(compressedStream);
  const blob = await response.blob();
  
  return await blob.arrayBuffer();
}

In this pipeline:

  1. The game state is serialized and wrapped in a Blob.
  2. The blob's readable stream is piped directly into CompressionStream('gzip').
  3. The resulting compressed stream is consumed via Response to yield an ArrayBuffer containing the compressed binary data.

Decompressing Save Data

When loading a save file, reverse the process by streaming the compressed binary data through a DecompressionStream.

async function decompressSaveData(compressedBuffer) {
  const stream = new Blob([compressedBuffer]).stream();
  const decompressedStream = stream.pipeThrough(new DecompressionStream('gzip'));
  const response = new Response(decompressedStream);
  const text = await response.text();
  
  return JSON.parse(text);
}

This restores the compressed binary buffer to its original JSON string, which is then parsed back into the live game state.

Storage Strategies for Compressed Data

Once compressed, developers must select the appropriate storage strategy based on the data format:

  • IndexedDB: The optimal destination for native compression. IndexedDB natively accepts ArrayBuffer and Blob formats, allowing raw compressed bytes to be written directly to disk without additional transformations.
  • LocalStorage: Because localStorage is synchronous and only supports UTF-16 strings, binary compressed data must be converted to a Base64 string before saving. Keep in mind that Base64 encoding adds approximately a 33% overhead to the compressed payload, making IndexedDB the preferable storage target for large save files.
